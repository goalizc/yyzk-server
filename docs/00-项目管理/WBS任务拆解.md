# WBS 任务拆解 — 一期 MVP

> 每个任务卡包含：编号、名称、负责角色、工期、前置依赖、输入、输出、验收标准。
> 工期单位：人天（1 人天 = 1 人工作 1 天）

---

## 阶段 A：项目准备（第 0.5 周）

### A-01 环境与账号准备
- **负责**：运维
- **工期**：0.5 天
- **前置**：无
- **输入**：服务器采购到位
- **输出**：
  - 一台 Ubuntu 22.04 服务器（4 核 8G）
  - Docker 24+ 和 Docker Compose v2 已装
  - Git 仓库建好（私有）
  - 域名/IP 规划完成
- **验收**：能 `docker run hello-world`；Git 仓库可 push/pull

### A-02 需求与技术评审会
- **负责**：产品 + 后端 + 前端
- **工期**：0.5 天
- **前置**：项目章程、PRD、API 契约初稿
- **输出**：评审纪要，需求冻结，范围确认
- **验收**：所有干系人签字确认一期范围，新需求进 backlog

### A-03 故障数据整理启动
- **负责**：售后知识运营
- **工期**：5 天（与开发并行）
- **前置**：历史工单导出
- **输出**：Excel 表格，至少 50 条结构化故障记录
- **字段**：产品名、型号、零件名、故障标题、现象描述、根因、解决步骤（分步）、所需工具、是否需专业人员、附件
- **验收**：开发能拿这份数据直接录入后台测试

## 阶段 B：后端开发（第 1-2 周）

### B-01 项目脚手架与数据库
- **负责**：后端
- **工期**：1 天
- **前置**：A-01
- **输入**：schema.sql
- **输出**：
  - FastAPI 项目骨架（目录结构按规范）
  - SQLAlchemy 模型定义
  - 数据库连接配置
  - Docker Compose 起 db 服务
- **验收**：`docker compose up db` 能连库，建表成功，`\dt` 看到 7 张表

### B-02 JWT 鉴权模块
- **负责**：后端
- **工期**：1.5 天
- **前置**：B-01
- **输出**：
  - POST /api/auth/login（用户名密码 → token）
  - PUT /api/auth/password（修改自己密码）
  - JWT 依赖注入（保护后台接口）
  - bcrypt 密码哈希
  - `deploy/scripts/init_admin.py` 管理员初始化脚本（幂等，随 deploy/scripts 提供，需接入镜像）
- **验收**：能登录拿 token；带 token 访问 /api/admin/* 通；不带 token 返回 401；`init_admin.py` 连续执行两次不重复建号
- **备注**：**不得**在 schema.sql 里写死密码哈希（bcrypt 必须运行时生成）

### B-03 产品与零件 CRUD
- **负责**：后端
- **工期**：1.5 天
- **前置**：B-02
- **输出**：
  - GET/POST/PUT/DELETE /api/admin/products
  - GET/POST/PUT/DELETE /api/admin/parts
  - GET /api/products（公开，只返回 is_active=true）
  - GET /api/products/{id}/parts（公开，级联下拉）
- **验收**：Postman 跑通所有接口；级联返回按 product_id 过滤

### B-04 故障知识库 CRUD
- **负责**：后端
- **工期**：2.5 天
- **前置**：B-03
- **输出**：
  - GET/POST/PUT/DELETE /api/admin/faults
  - GET /api/admin/faults/{id}（编辑回显，返回完整字段）
  - GET /api/faults?product_id=&part_id=&q=（公开列表，仅返回已发布，支持关键词包含匹配）
  - GET /api/faults/{id}（公开详情，含 solution_steps JSON，返回 query_log_id）
  - 附件上传接口 POST /api/admin/upload（multipart，白名单 + 20MB）
  - view_count 自增逻辑（前台访问详情时触发，与写日志同一事务）
- **验收**：能新增一条故障，包含 3 个步骤、1 张附件；前台能查到；关键词筛选命中与不命中各验一次

### B-05 工单模块
- **负责**：后端
- **工期**：2 天
- **前置**：B-04
- **输出**：
  - POST /api/tickets（公开，含 need_on_site）
  - GET /api/admin/tickets（列表，支持 status / start_date / end_date / keyword 筛选，联系方式脱敏）
  - GET /api/admin/tickets/{id}（详情，含关联对象与流转历史）
  - PUT /api/admin/tickets/{id}（状态流转，操作人从 token 取，写 ticket_status_logs）
  - 工单编号自动生成（TK + 日期 + 当日序号，行锁 + 唯一冲突重试）
  - 状态流转合法性校验（open→processing/closed，processing→resolved/closed，resolved→closed）
- **验收**：用户提交工单后后台能看到且上门字段正确；状态可从 open 改到 processing/resolved 且历史留痕；非法流转返回 400

### B-06 查询日志与反馈
- **负责**：后端
- **工期**：1.5 天
- **前置**：B-04
- **输出**：
  - GET /api/faults/{id} 时自动写 query_logs 并返回其 id
  - POST /api/faults/{id}/feedback（body: {query_log_id, resolved}，校验日志归属，更新 resolved 与 resolved_count）
  - POST /api/query-logs（记录检索无结果，hit=false；配 Nginx 限流）
  - 日志写入包含 ip / user_agent
- **验收**：访问一次详情 query_logs 多一条且返回 id；用该 id 反馈后只有这一条被更新；无结果上报能落到库

### B-07 统计接口
- **负责**：后端
- **工期**：1 天
- **前置**：B-06
- **输出**：
  - GET /api/admin/stats/overview（days 参数；返回 total_queries / resolved_queries / resolve_rate / total_tickets / open_tickets / missed_queries）
  - GET /api/admin/stats/top-faults（days + limit，按窗口内查看次数排序）
  - GET /api/admin/stats/missed（days + limit，按 raw_query 归一化分组）
  - **解决率口径**：窗口内 resolved=true 条数 ÷ 窗口内 fault_id 非空条数（不用历史 view_count 口径）
- **验收**：造 20 条测试数据后，三个接口数字与手工 SQL 一致；切换 days 数字随之变化

### B-08 单元测试
- **负责**：后端
- **工期**：1.5 天
- **前置**：B-07
- **输出**：pytest 用例，覆盖核心接口
- **验收**：核心接口覆盖率 ≥ 70%，全部通过

### B-09 健康检查、日志与错误码统一
- **负责**：后端
- **工期**：0.5 天
- **前置**：B-01
- **输出**：
  - `GET /api/health`（只查 DB 连通性，供容器 healthcheck 使用）
  - 结构化日志：method / path / status / 耗时 / request_id，输出到 stdout
  - 全局异常处理器：所有错误统一返回 `{detail, code}`
  - 业务错误码映射表（见 API 契约 §7）
- **验收**：`docker compose ps` 中 backend 为 healthy；日志可见耗时；任意错误响应含 code 且不含堆栈

### C-03 客户方案详情页
- **负责**：前端

### C-08 后台 — 工单管理页

- **工期**：1.5 天

- **验收**：能看到客户提交的工单，上门字段正确显示，改状态后历史新增一条

### C-09 后台 — 数据看板
- **负责**：前端
- **工期**：1.5 天
- **前置**：C-05，B-07
- **输出**：
  - 总览卡片（查询量、解决率、工单数）

- **验收**：数据从统计接口实时渲染

### C-10 客户侧 — 关键词筛选与未命中上报

- **工期**：0.5 天
- **前置**：C-02，B-06

### C-11 后台 — 修改密码弹窗

- **工期**：0.5 天

## 工期汇总（v1.2 重新核算，2026-10-20）

> 核算口径：1 人天 = 1 人工作 1 天。D-01 联调与 D-04 内测均为「2 天 × 2 人」。

### 逐任务核算

| 阶段 | 任务 | 人天 |
|---|---|---|
| A 项目准备 | A-01 环境 0.5 ／ A-02 评审 0.5 | 1.0 |
| A 数据 | A-03 数据整理（售后，与开发并行） | 5.0 |
| **B 后端** | B-01 1 ／ B-02 1.5 ／ B-03 1.5 ／ B-04 2.5 ／ B-05 2 ／ B-06 1.5 ／ B-07 1 ／ B-08 1.5 ／ B-09 0.5 | **13.0** |
| **C 前端** | C-01 0.5 ／ C-02 2 ／ C-03 1.5 ／ C-04 1 ／ C-05 0.5 ／ C-06 1.5 ／ C-07 2.5 ／ C-08 1.5 ／ C-09 1.5 ／ C-10 0.5 ／ C-11 0.5 | **13.5** |
| **D 收尾** | D-01 联调 2×2=4 ／ D-02 部署 1 ／ D-04 内测 2×2=4 ／ D-05 上线 0.5（OPS） | **9.5**（其中开发 **9.0**） |
| D 数据 | D-03 数据导入（售后，与 D-01 并行） | 2.0 |

**三段加总**：B 13.0 + C 13.5 + D（开发部分）9.0 = **35.5 开发人天**。
（D 阶段总额 9.5 含 OPS 的 0.5 天上线操作，因此不等于 35.5 中的开发部分 —— 这是上一版表格自相矛盾的根因，已拆开标注。）

### 按角色汇总

| 角色 | 计算式 | 人天 |
|---|---|---|
| 后端 BE | B 13 + D-01 2 + D-02 1 + D-04 2 | **18.0** |
| 前端 FE | C 13.5 + D-01 2 + D-04 2 | **17.5** |
| 开发合计 | 18.0 + 17.5 | **35.5** |
| 运维 OPS | A-01 0.5 + D-05 0.5 + 备份配置 0.5 | 1.5 |
| 售后知识运营 | A-03 5 + D-03 2 | 7.0 |

### 产能对比

| 方案 | 开发产能 | 需求 | 结论 |
|---|---|---|---|
| 3 周（15 个工作日） | 30 人天 | 35.5 | **缺 5.5 天，不可行** |
| 18 个工作日（3.6 周） | 36 人天 | 35.5 | 余 0.5 天，**无实质缓冲** |
| **4 周（20 个工作日）** | **40 人天** | **35.5** | **余 4.5 天，推荐** |
| 3 周 + 加 1 名后端 | 45 人天 | 35.5 | 可行但人力成本上升 |

**结论：一期工期 4 周（20 个工作日），最低可行 18 个工作日。**3 周方案缺 5.5 天，即使砍掉看板（1.5）+ 关键词（0.5）+ 工单历史（0.5）+ 改密（0.5）也只能省 3 天，仍不够，且砍的全是验收门槛项。

### 关键路径（修正版）

后端是单线程资源，全部后端任务串行：

```
A-02 评审 0.5
→ B-01 1 → B-02 1.5 → B-03 1.5 → B-04 2.5
→ B-05 2 → B-06 1.5 → B-07 1 → B-08 1.5 → B-09 0.5
→ D-01 2 → D-02 1 → D-04 2
= 18.0 个工作日（占满 BE 全部投入）
```

20 个工作日窗口下，后端仅余 2 天浮动。**B-04（2.5 天，最重）一旦超时 1 天，上线日直接顺延**。

> 上一版关键路径漏了 B-05、B-09、D-02（都是后端任务，单人无法并行），把路径算短了 3.5 天。
