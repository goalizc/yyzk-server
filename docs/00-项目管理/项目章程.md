# 项目章程 — 售后自助故障诊断系统

## 1. 项目背景
公司产品种类和零部件持续增加，售后工单量上升。客服大量时间用于回答重复问题（如"开机没反应怎么办""滤芯怎么换"）。需要一个面向终端用户的自助查询系统，让用户自己定位故障并获取解决方案，降低人工客服压力。

## 2. 项目目标
| 目标项 | 量化指标 |
|---|---|
| 自助解决率 | 上线 3 个月后，≥ 30% 常见故障由用户自助解决，不进人工 |
| 客服工单量 | 高频故障类工单量下降 ≥ 40% |
| 系统可用性 | 99.5%（计划内维护除外） |
| 查询响应 | 结构化查询 < 500ms |
| 数据自主可控 | 全部私有化部署，无第三方 SaaS |

## 3. 项目范围（一期 MVP）

### 做什么
1. 客户自助查询页：产品 → 零件 → 故障现象 → 解决方案（支持当前结果内关键词筛选）
2. 后台管理：产品/零件/故障知识库 CRUD、工单管理、数据统计、修改密码
3. 工单兜底：未命中或未解决时，一键提交工单并自动带上下文
4. Docker 一键部署，4 核 8G 服务器可跑
5. **用户与权限管理（一期上线前追加）**：超级管理员 / 售后主管 / 一线客服 / 只读审计四角色，账号管理界面、产品线数据权限（工单范围）、带到期时间的临时授权。原排在三期 3.5，因上线运营刚需提前实施；操作日志与知识库审核流仍留三期。

### 不做什么（一期明确排除）
- 自然语言问答（LLM）→ 二期
- 故障树引导诊断 → 三期
- 移动端小程序 → 三期
- IoT 设备联动 → 四期
- 多语言 → 四期
- 与现有客服系统对接 → 四期（一期工单独立运行）
- **跨组合模糊搜索 / 同义词纠错** → 二期

> **范围调整（2026-10-22）**：用户与权限管理原列为三期路线图 3.5，现因上线运营刚需，提前至一期上线前追加，详见 §3「做什么」第 5 项；操作日志、知识库审核流与自定义角色不在本次范围，仍留三期。

## 4. 成功标准（验收门槛）
- [ ] 售后团队能在后台录入 ≥ 50 条真实故障
- [ ] 客户能走完"选产品→选零件→看方案→反馈/转工单"全流程
- [ ] 后台能看到查询日志、解决率、TOP 故障、未命中检索词
- [ ] `docker compose up -d` 在干净服务器 5 分钟内全部起服
- [ ] 无遗留 P0 bug；P1 用例通过率 ≥ 90%（与验收检查表 §八 口径一致）

> 工期口径：**4 周（20 个工作日）为基准计划，18 个工作日为最低可行线**。开发工作量 35.5 人天（BE 18 / FE 17.5）。原"3 周"只有 15 个工作日、产能 30 人天，缺 5.5 天，已修正 —— 见 `排期计划.md`。

## 7. 风险登记册
| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 历史工单非结构化，数据整理慢 | 高 | 高 | 第 1 周同步启动数据整理，不等开发完成 |
| 售后团队没时间录数据 | 中 | 高 | 指定专人，KPI 绑定；先录 TOP 50 |
| 需求蔓延（中途加功能） | 中 | 中 | 严格按范围执行，新需求进 backlog 排期 |
| 服务器资源不够 | 低 | 中 | 提前采购，4 核 8G 最低配置 |
| **排期结构性超载** | **高** | **高** | 已复核：35.5 人天 vs 3 周产能 30 人天（缺 5.5）。按 4 周排，或加 1 名后端；每周检查点触发降级（见排期计划 §5） |
| 数据整理只能界面手录 | 中 | 中 | 提供 CSV 导入脚本（0.5 天投入，可省约 2 天录入时间） |
| **上线前追加用户权限与产品线改造** | **中** | **中** | 已定稿设计稿与 T1–T16 任务卡；迁移前强制备份，按「db 就绪 → 迁移 → 启动后端」顺序部署，不挤占一期四周主排期 |
| 旧库迁移失败或漏执行迁移 | 中 | 高 | 迁移在事务中执行、失败即退出；`deploy.sh` 已强制先迁移后起后端；恢复旧备份后必须重跑 `docker compose run --rm migrate` |
