## 1. 范围

### 1.1 覆盖

| 层 | 内容 | 说明 |
|---|---|---|
| 前端 UI 文案 | 客户侧 4 页 + 后台 10 页 + 公共组件 | 标签、按钮、提示、校验信息、空态 |
| 通用页 | 登录页、404 页、公共错误态、改密弹窗 | 这些页不在主流程里，但英文用户一定会碰到 |
| 浏览器标签页标题 | `document.title` | 按路由 `titleKey` 生成，随语言切换 |
| 后端错误提示 | 32 个稳定错误码对应文案 | 前端按 `code` 查字典，不依赖后端中文 |
| Element Plus 内置文案 | 日期选择器、分页、表格空态、下拉无匹配 | 随应用语言切换 |

### 1.2 明确不做

| 项 | 原因 | 若要做的前提 |
|---|---|---|
| **业务数据文本**（产品名、零件名、故障标题/现象/原因/排查步骤、工单内容） | 这些是运营在后台录入的内容，不是代码里的文案。翻译需要数据模型改造（译文字段或 `translations` 表）+ 内容录入与校对流程，属独立项目 | 业务方先提供英文译文；详见 §9 |
| RTL 语言（阿拉伯语、希伯来语） | 需要整套布局镜像，与当前 CSS 体系冲突 | 有明确市场需求时单独立项 |
| 后端 `Accept-Language` 协商 | 后端只管返回机器码，语言选择属于展示层职责；两处都做会出现"后端译一套、前端译一套"的双份维护 | 若未来有非浏览器的 API 消费方（如 App、第三方集成）再考虑 |

> **必须让使用方知道的一点**：本期做完后，英文界面下的**故障方案正文、产品名、零件名仍是中文**。
> 外文客户看到的是「英文界面 + 中文内容」。这是范围决策，不是缺陷。

## 2. 语言与切换

| 语言 | 代码 | URL 前缀 | 默认 |
|---|---|---|---|
| 简体中文 | `zh-CN` | 无（`/`、`/faults/21`） | ✅ |
| English | `en-US` | `/en`（`/en/faults/21`） | |

### 2.1 为什么默认语言不加前缀

中文是主场景。`/faults/21` 这类既有链接、书签、已发出去的工单短信、nginx 配置都保持原样，
不会因为国际化改造而产生 404 或重定向链。

### 2.2 客户侧与后台采用不同策略

| 端 | 策略 | 理由 |
|---|---|---|
| 客户侧 | **URL 前缀决定语言** | 外文客户需要一条可直接分享/收藏的英文链接；同一台机器换人看也不会串语言 |
| 后台 | **不加前缀，跟随偏好设置** | 只有内部员工使用，没有分享需求；加前缀会让 `/admin/...` 全部翻倍、nginx 与测试定位复杂度上升 |

这是有意的非对称设计，不是遗漏。后台若将来需要"给外籍客服一条英文后台链接"，再加前缀，届时路由改动已被 `locale` 参数化的写法兜住。

### 2.3 语言解析优先级

```
客户侧：URL 前缀  →  无前缀即 zh-CN（读取时不看存储）
后台  ：localStorage.locale  →  zh-CN（不跟随浏览器语言）
```

两条都是刻意收紧的，原因：

| 规则 | 为什么 |
|---|---|
| 客户侧**读取**不看 `localStorage` | 同一条分享出去的 `/en/faults/21`，在别人机器上必须还是英文。若读存储，链接的"所见即所分享"就失效了 |
| 后台不跟随 `navigator.language` | 内网机器语言不可控——英文版 Chrome 的 `navigator.language` 就是 `en-US`。一旦跟随，中文运营打开后台会看到**英文外壳 + 中文页面内容**的中英混杂态，比全中文更难用。需要英文的人自己切换一次，之后由 `localStorage` 记住 |

> 该规则由 `src/locales/locale.spec.js` 的两条用例锁定，其中「后台不跟随浏览器语言」在
> 测试环境（`navigator.language === 'en-US'`）下会真实失败——不是空断言。

### 2.4 读取与写入分离（v1.1 修正）

**读**和**写**的规则不同，这一点最初设计错了，导致「英文客户侧点 Admin 进后台仍是中文」：

| 场景 | 读什么 | 写不写偏好 |
|---|---|---|
| 打开 `/en/faults/21`（别人分享的链接） | URL 前缀 | ❌ 不写 —— 这只是"看了一条链接"，不代表偏好 |
| 用户点语言切换按钮 | 切换结果 | ✅ **写** —— 这是明确的偏好表达，后台应延续 |
| 打开后台 | `localStorage` | — |

实现上：`setLocale(locale, { persist })`，路由守卫里 `persist: false`，
`PublicLayout` 的切换按钮里 `persist: true`。

> 回归用例：`e2e/i18n.spec.js`「客户侧切到英文后进后台，登录页也是英文」。

## 3. 前端架构

### 3.1 依赖

`vue-i18n@11`（Vue 3 官方推荐，Composition API 模式）。

### 3.2 目录结构

```
src/locales/
├── index.js              # createI18n、语言解析、setLocale、持久化
├── zh-CN/
│   ├── common.js         # 通用：按钮、分页、状态、单位、空态
│   ├── public.js         # 客户侧 4 页
│   ├── admin.js          # 后台布局、导航、登录
│   ├── ticket.js         # 工单
│   ├── fault.js          # 故障知识库
│   ├── product.js        # 产品、零件、产品线
│   ├── user.js           # 用户与授权
│   ├── stats.js          # 数据看板
│   └── error.js          # 错误码 → 文案（key 就是错误码）
└── en-US/                # 与 zh-CN 同构，键集合必须完全一致
```

按**业务模块**拆而不是按页面拆：同一个文案在两页用到时不用重复定义。

### 3.3 key 命名规范

- 层级：`模块.区域.元素`，如 `ticket.status.open`、`admin.nav.faults`、`public.home.selectProduct`
- 通用动作收敛到 `common.action.*`（保存/取消/删除/新增/搜索/重置/关闭）
- 校验信息收敛到 `common.validation.*`

**硬规则：禁止在模板里拼接 key**

```vue
<!-- ❌ 扫描脚本、翻译平台、CI 键完整性检查都抓不到 -->
{{ $t('ticket.status.' + row.status) }}

<!-- ✅ 通过映射表，key 是完整字面量 -->
{{ $t(STATUS_KEY[row.status]) }}
```

> 原因：`$t` 的动态拼接会让「提取待翻译文案」和「检查缺失键」两个环节全部失效，
> 表现为运行时报 `Cannot translate the value of keypath`，而且只在特定数据下才触发。

### 3.4 使用方式

```vue
<!-- 模板 -->
<el-button>{{ $t('common.action.save') }}</el-button>

<!-- 脚本 -->
<script setup>
import { useI18n } from 'vue-i18n'
const { t } = useI18n()
const rules = { username: [{ required: true, message: t('login.usernameRequired') }] }
</script>
```

**不翻译的内容**：接口返回的业务数据、用户输入、数据库里的名称。

### 3.5 Element Plus 联动

`App.vue` 的语言包由硬编码改为计算：

```js
const elLocale = computed(() => (locale.value === 'en-US' ? en : zhCn))
```

覆盖范围：日期选择器、分页、表格空态、`el-select` 无匹配、上传组件提示。

### 3.6 持久化

- `localStorage.locale`：**只在用户主动切换时写**（见 §2.4），路由守卫里不写
- 后台账号的偏好**不落库**（`users.locale` 本期不加，见 §9）：同一账号在不同电脑上可能语言不同，但内网单机场景影响可忽略
- `<html lang>`：应用启动时按解析结果立即设置，不等首次切换（否则屏幕阅读器与浏览器翻译会先按 `zh-CN` 处理）

### 3.7 URL：只有在「拼成字符串」时才容易漏语言

站内跳转走 `localeRoute()`，漏不了；**漏的永远是手工拼的字符串 URL**：

| 场景 | 正确做法 | 漏了的后果 |
|---|---|---|
| `router.push` | `localeRoute('fault-detail', { id })` | — |
| 剪贴板文本 / `window.open` / 分享 | `localeHref('/faults/9')` | 英文客服把文本发出去，客户点开是中文页 |
| 后端返回的 URL | 不做处理（当前无此情况） | — |

`localeHref` 与 `localeRoute` 都在 `src/locales/index.js`，两处都有测试锁定。

### 3.8 英文单复数：中文没有，容易整体漏掉

`{count} people viewed` 在 count=1 时是 **"1 people viewed"**——中文没有单复数，
写文案时不会想到，测中文也测不出来。

```js
// 语言包：单数 | 复数
viewed: '{count} person viewed | {count} people viewed'

// 调用处：传数字（不是对象），vue-i18n 用它选段并绑定 {count}
t('common.count.viewed', fault.view_count)

// 同时带命名参数时：t(key, 数字, { 其他变量 })
t('admin.part.deleteBlocked', row.fault_count, { name: row.name })
```

**传 `{ count: n }` 会永远命中第一段**，这是最容易写错的点。
数字已被 `formatNumber()` 转成字符串的场合没法选段，改用计数中性的说法
（`Solution views: {count}`）。

测试侧：占位符一致性按**集合**比较（复数两段里 `{count}` 出现两次），
另有「复数变体不得引入中文没有的占位符」防止某段写成 `{total}`。

### 3.9 排版：宽度必须按语言给

英文不是"中文换成英文单词"，它在盒子里更占地方。三类宽度都要单独核对：

| 对象 | 做法 | 为什么 |
|---|---|---|
| 表单标签 | `useFormLabelWidth('88px', '120px')` | 英文标签长 1.5–2 倍；写死像素中文正好、英文折行 |
| 表格列 | 按英文最长值定宽（`In progress` / `On-site` / `Reset password`） | 中文 3 字宽 100px 够，英文被截成 `In progr...` |
| 搜索框等定宽控件 | 同上，英文占位符更长 | `Search username or name` 在 200px 里被切掉一半 |

**不要用 `label-width="auto"`。** 实测（1440px 视口、英文界面）同一表单内各标签宽度
变成 `Product 70 / Requires a professional 159 / Part number 78 / Sort order 106`，
标签右边缘参差不齐，值的起始位置跟着跳，比折行更难读。按语言给**一个统一值**才是对的。

#### 折行在 DOM 里看不出来（踩过的坑）

`el-form-item` 把 label 的行高锁死 32px。label 折行后：

- `getBoundingClientRect().height` **仍然是 32px**
- `clientHeight` 也是 32px
- 只有 `scrollHeight` 变成 64px
- 视觉表现是第二行**溢出盒子、压到下一行表单的标签上**（文字重叠），不是这一行变高

所以任何自动检测都必须用 `scrollHeight >= 1.5 × line-height`。用高度判据会 100% 假绿。
守卫见 §7。

## 4. 后端错误文案

### 4.1 现状

契约固定 `{"detail": 中文可读, "code": 稳定机器码}`。全库 80+ 处 `BusinessError` 抛出，去重后约 30 个码。

**这是本次改造最有利的既有条件**：错误码本身就稳定，前端天然可以按码查表，不需要后端做语言协商。

### 4.2 方案：前端按 code 查字典，后端 detail 保留为兜底

后端**不改变** `detail` 的语义（继续返回中文），前端按顺序取文案（实现见 `frontend/src/utils/error.js`）：

```js
export function errorMessage(error, { fallbackKey, fallbackText } = {}) {
  const { code, params, detail } = error?.response?.data || {}
  // 1. 中文环境直接用后端 detail（比字典通用文案精确）
  if (currentLocale() === DEFAULT_LOCALE && detail) return detail
  // 2. 按 code 查字典，params 做插值
  if (code && te(`error.${code}`)) return t(`error.${code}`, params || {})
  // 3. 字典没有（后端新增码）→ 退回后端原文，不显示空提示
  if (detail) return detail
  return fallbackKey ? t(fallbackKey) : fallbackText || t('common.error.generic')
}
```

- 老前端（只读 `detail`）行为完全不变 → 无兼容风险
- 后端新增错误码但前端未同步时，退化为中文原文而不是空白
- 字典缺 key 由测试兜住（§7）

> **这里是"key 必须字面量"规则的唯一例外**：`error.${code}` 的 key 是运行时拼的，
> 因为错误码来自后端、前端无法穷举。补偿手段是 `te()` 守卫 + 测试里**枚举
> `backend/app` 全部 `BusinessError` 码**逐个断言有文案（`locale.spec.js`）。
> 除错误码外，任何地方都不许拼 key。

### 4.3 新增响应字段 `params`（可选）

动态片段由后端结构化返回，前端插值：

```json
{
  "detail": "型号 X1 已存在",
  "code": "MODEL_DUPLICATED",
  "params": { "model": "X1" }
}
```

对应前端文案：

```js
// error.js
MODEL_DUPLICATED: '型号 {model} 已存在'
```

**向后兼容**：老客户端忽略 `params`；响应体只增字段，不改既有字段。

### 4.4 需要补 `params` 的 4 处

| 错误码 | 位置 | 参数 |
|---|---|---|
| `MODEL_DUPLICATED` | `backend/app/api/admin.py` ×3 | `{ model }` |
| `LINE_NAME_DUPLICATED` | `backend/app/api/admin_product_lines.py` | `{ name }` |
| `NOT_FOUND`（产品线批量缺失） | `api/admin_users.py:111` | `{ missing }`（数组，前端 join） |
| `VALIDATION_ERROR`（含字段名） | `core/exceptions.py:73` | `{ fields }` |

> `NOT_FOUND` 是通用码，同一码在不同场景文案不同（产品不存在 / 用户不存在）。这类**由业务语义细分**的码保持现状：前端字典给通用文案，服务端 `detail` 优先展示。
> 判定原则：**一个码只对应一种文案时才走字典**；一码多义时以服务端 `detail` 为准。

## 5. 路由

客户侧根路由参数化，后台保持不变：

```js
{
  path: '/:locale(en)?',
  component: PublicLayout,
  meta: { public: true },
  children: [
    { path: '', name: 'home', ... },
    { path: 'faults/:id', name: 'fault-detail', ... },
    { path: 'tickets/new', name: 'ticket-new', ... },
    { path: 'tickets/success', name: 'ticket-success', ... }
  ]
}
```

- `/:locale(en)?` 用**字面量枚举**（只匹配 `en`），避免把 `/admin` 当成语言段
- `beforeEach` 中：取到 `params.locale` → `setLocale()` → 写入 `localStorage`
- 内部跳转统一走 `router.resolve({ name, params: { ...localeParams } })` 包装，避免某处漏带前缀导致跳回中文

```js
// utils/locale.js
export function localePath(name, params = {}) {
  return router.resolve({
    name,
    params: { locale: currentPrefix(), ...params }
  }).fullPath
}
```

> 后台 `meta.title` 目前是中文硬编码，同步改为 `meta.titleKey`（如 `admin.nav.tickets`），
> 顶栏标题与菜单标签共用同一份翻译，避免两处文案漂移。

## 7. 测试策略

这是最容易被低估的部分。现有 **168 条前端用例大量断言中文文案**（如 `toContain('已关闭，不可再流转')`）。

**策略：测试锁定 zh-CN，断言保持中文。** 在 `vitest.setup` 里强制 `setLocale('zh-CN')`。

理由：把 100+ 条断言改写成断 key，收益极低（key 是否正确由键完整性检查负责），风险却很高（容易把"文案错误"变成"key 存在"的无效断言）。

新增三类用例：

| 类型 | 断言 |
|---|---|
| 键完整性 | `zh-CN` 与 `en-US` 的键集合完全一致，无缺失、无多余 |
| 错误码字典 | 后端全部错误码在前端字典中都有 key（从 `backend/app` 扫描 `BusinessError` 提取码，比对 `error.js`） |
| 切换生效 | `/en/` 路径渲染英文；切换后 `localStorage` 与 Element Plus 语言同步 |
| 排版 | 英文界面 9 个表单 / 49 个标签全部单行（见 §3.9 的判据） |

E2E 三条：

- `e2e/i18n.spec.js`：客户侧 `/en` 双语链路 + 切换保留路径参数 + 切英文后进后台是英文
- `e2e/i18n-layout.spec.js`：英文排版守卫（表单标签折行检测）
- `e2e/main-flow.spec.js`：中文主链路（钉住中文零回归）

**两道自动化闸门**（防后续开发把中文写回组件里）：

| 闸门 | 触发 | 作用 |
|---|---|---|
| `python scripts/dev/check_i18n.py` | 提交前手动 / 关卡 | 扫 `frontend/src` 硬编码中文，退出码 1 即拦下。注释、`locales/`、`*.spec.js` 不报；确需保留的加 `// i18n-ignore` |
| `frontend/e2e/i18n-layout.spec.js` | `npm run e2e` | 英文表单标签折行检测，失败时点名场景与标签 |

两条都做过**反向验证**（故意违规 → 必须红），不是装饰。

## 9. 本期不做、但需要提前知道的事

### 9.1 业务数据多语言（最大的遗留）

故障方案正文、产品名、零件名都是中文存储。若要做真正可用的英文体验，需要二选一：

| 方案 | 改造 | 代价 |
|---|---|---|
| 译文字段 | `products.name_en`、`faults.title_en`… 逐字段加 | 表结构膨胀，每加一个语言就加一列；查询需要 `COALESCE` 兜底 |
| 翻译表 | `translations(entity, entity_id, field, locale, value)` | 一张表通吃，扩展语言无痛；但查询要 JOIN、管理界面要做批量录入 |

建议走**翻译表**，且必须先有业务方提供的英文译文（否则录入界面做出来也是空的）。
这项工作**依赖内容而非代码**，不能靠开发推进。

- `users.locale` 落库（多设备一致）
- 后台 URL 前缀
- 翻译文案的专业校对（当前 `en-US` 由开发翻译，面向客户前建议由业务方校对术语）

## 11. 新增功能时怎么做（照做清单）

这是给后续开发的**操作路径**，不是原则说明。顺序别换，第 2 步最容易漏。

1. **建语言包模块**：`src/locales/zh-CN/<模块>.js` + `en-US/<模块>.js`，两边 key 一一对应
2. **注册到两个 `index.js`**：
   ```js
   import adminXxx from './admin-xxx'
   export default { ..., xxx: adminXxx }
   ```
   ⚠️ **漏注册不会报错、不会白屏，界面直接显示出 key 本身**（`admin.fault.reader.title`），
   因为 `missingWarn: false`。看到界面出现点号串，第一件事就是查这条
3. **组件里取 t**：`const { t } = useI18n()`（模板中也可直接用 `$t`）
4. **表单标签宽度**：`:label-width="useFormLabelWidth('88px', '120px')"`，别写死像素
5. **表格列宽按英文最长值核对**；定宽搜索框同理
6. **校验规则用 `computed` 包一层**，否则语言切换后校验文案不跟着变：
   ```js
   const rules = computed(() => ({ name: [{ required: true, message: t('x.ruleName') }] }))
   ```
7. **后端新增错误码**：API 契约 §7 登记 → `locales/{zh-CN,en-US}/error.js` 各加一条
   （漏了 `locale.spec.js` 会红，它扫 `backend/app` 的 `BusinessError`）
8. **跑三道闸门**：
   ```bash
   python scripts/dev/check_i18n.py     # 硬编码中文
   cd frontend && npm run test          # 键完整性 + 错误码覆盖
   cd frontend && npm run e2e           # 含英文排版守卫
   ```
9. **英文界面实测一次**：切到 English，逐屏看有没有截断/折行。自动化只能守住表单标签，
   长文案挤压布局（按钮换行、卡片撑破）仍需人看

### 不该做的事

| 反例 | 为什么 |
|---|---|
| `t('status.' + row.status)` | key 拼出来的，扫描与键检查全部失效；用映射表返回完整字面量 |
| `label-width="auto"` | 同一表单内标签宽度各不相同，右边缘参差（§3.9 有实测数据） |
| 在中文语言包里写英文占位 | 键一致性检查只比 key，不比语义，两边写反了也全绿 |
| 加英文文案后不看列宽 | 已踩过：`In progress` 被截断、`On-site` 折行、搜索占位符被切 |
