## 1. 已定案清单

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 架构定位 | **物理集成、逻辑独立**：同仓库同库，`inventory_` 前缀独立表组 / router / service / 后台菜单；复用登录、部署、备份、审计脚手架；**不碰工单与故障方案、不改写 `parts`** |
| 2 | 管理对象 | 零件/备件 + 通用物资；SKU 独立编码，`part_id` **可空弱关联**，覆盖纯物资、一零件多 SKU、无关联条目 |
| 3 | 功能深度 | **L1 轻量**：单仓、只记数量、入出库单、流水、余额、低库存预警；无多仓、无批次效期、无金额账 |
| 4 | 权威账 | 公司无 ERP / 进销存（连表格都没有），从零开发，本系统即权威账；无双账同步问题 |
| 5 | 业务边界 | **长期不与售后挂钩**：不做工单领用出库、不做方案页有货提示；`stock_movements` 留通用 `ref_type / ref_id`（不加外键）作零成本伏笔 |
| 6 | 国际化 | **双语不例外**，照章办事；客户侧 4 页完全不动，只有后台新增页面 |
| 7 | 角色 | **新增 `warehouse`（仓管）角色**，对售后模块零权限的纯库存角色 |
| 8 | 数据范围 | **统一 ALL，不继承 LINES**；库存域须显式处理，禁止误用 `apply_ticket_scope` |
| 9 | 权限粒度 | **分细**（见 §2） |
| 10 | 分权模型 | 按资源/动作细分权限码，**不做审批** |
| 11 | 审批扩展 | 本期不做审批，但**预留口子**：单据状态字段 + 过账逻辑与创建解耦，未来启用审批不改表、不改过账内部（见 §6） |

> 设计原则补充：**功能设计覆盖全部可能输入，不按数据占比下注**。只要允许登记一条"不属于任何产品的物资"，就必须有对应的字段、编码、录入与查询路径，与这类条目实际有多少无关。因此不依赖 `parts` 主数据假设。

## 2. 权限码矩阵（分细版）

现有体系见 `backend/app/core/permissions.py`：4 角色硬编码、16 权限码、`_DEPENDENCIES` 依赖闭包 `expand()`、`require()` 403 拦截、`user_permission_grants` 临时授权。**库存权限接入这套体系，不新建表、不新建机制。**

### 2.1 权限码

| 权限码 | 允许的动作 | 依赖闭包（自动补齐） |
|---|---|---|
| `inventory:sku:read` | 查看 SKU 主数据、当前余额、低库存清单 | — |
| `inventory:sku:write` | 新增/编辑/停用 SKU、设 `min_stock`、关联 `parts` | `sku:read` |
| `inventory:inbound:read` | 查看入库单及明细 | `sku:read` |
| `inventory:inbound:write` | 登记入库单 | `inbound:read` |
| `inventory:outbound:read` | 查看出库单及明细 | `sku:read` |
| `inventory:outbound:write` | 登记出库单 | `outbound:read` |
| `inventory:movement:read` | 查看库存流水 | `sku:read` |
| `inventory:adjust:write` | **盘点、冲正、反向单**（能凭空改账，高危单独拆） | `movement:read` + `inbound:read` + `outbound:read` |
| `inventory:export` | 导出 CSV | 全部 `:read` |
| `inventory:cost:read` | 查看成本单价 —— **L1 预留不启用** | `sku:read` |

共 10 个码。`inventory:cost:read` 只登记、不分配给任何角色，等做金额账时启用，避免提前引入字段级权限。

### 2.2 角色分配建议（可调）

| 角色 | 库存权限 |
|---|---|
| `super_admin` 超级管理员 | 全部 10 个 |
| `supervisor` 售后主管 | 全部 10 个（含 `adjust:write`） |
| `warehouse` 仓管（新增） | `sku:read` / `sku:write` / `inbound:*` / `outbound:*` / `movement:read` / `export`，**不含 `adjust:write`** |
| `auditor` 只读审计 | `sku:read` / `inbound:read` / `outbound:read` / `movement:read` / `export`（只读审计天然覆盖全域，可调） |
| `agent` 一线客服 | 零库存权限（纯内部台账，长期不挂钩） |

### 2.3 防提权

`grantable_permissions()` 现排除 `USER_WRITE`。**`inventory:adjust:write` 同样排除**——冲正能凭空改账，不应通过临时授权（带 `expires_at` / `reason`）授予。其余库存权限码可临时授予。

### 2.4 数据范围

`_DATA_SCOPE` 中 `agent` 为 `LINES`（按 `user_product_lines` 产品线过滤，且 `ticket_scope.py` 明示**只作用于工单**）。库存 SKU 的 `part_id` 可空，纯物资没有产品线可判，继承 `LINES` 会导致"谁都看不见"。

**结论：库存域统一按 `ALL` 处理**，所有有 `inventory:*:read` 的角色可见全部台账。在 service 层显式写死，不复用也不误调 `apply_ticket_scope`。

## 3. 数据模型草案（表清单）

| 表 | 用途 | 关键字段 |
|---|---|---|
| `inventory_skus` | SKU 主数据 | `sku_no` 唯一、`name`、`spec`、`unit`、`category`、`part_id` **可空** FK、`warehouse_id`、`min_stock`、`unit_cost` 可空、`batch_no` 可空、`is_active` |
| `inventory_balances` | 当前余额快照 | `sku_id` + `warehouse_id` 唯一、`quantity`、`updated_at` |
| `inventory_documents` | 入出库/调整单主表 | `doc_no` 唯一、`doc_type`、`warehouse_id`、`operator_id`、`remark`、**`status` 默认 `confirmed`**、`confirmed_at` / `confirmed_by` 可空、`review_remark` 可空、`created_at` |
| `inventory_document_items` | 单据明细 | `document_id` FK、`sku_id` FK、`quantity`、`unit_cost` 可空 |
| `stock_movements` | 库存流水（append-only） | `sku_id`、`warehouse_id`、`delta`、`balance_after`、`document_id`、`ref_type` / `ref_id`（**不加外键**）、`operator_id`、`created_at` |
| `inventory_warehouses` | 仓库（单默认仓） | 建表避免硬编码；一期只有一条默认记录 |

### 关键约束

- **`stock_movements` 只增不改**：复用 `audit_logs` + 004 迁移触发器的 append-only 范式；冲正用**反向单**，不物理改删。
- **并发扣减**：`SELECT ... FOR UPDATE` 行锁锁 `inventory_balances`，同一事务内写流水 + 更新余额，防超卖。
- **创建与过账解耦（审批口子，见 §6）**：`create_document()` 只写单据主表 + 明细，不含任何余额操作；`post_document()` 独立负责「行锁扣余额 + 写流水」。L1 创建后立即调用 `post_document()`，未来启用审批时把调用挪到 confirm 端点即可。
- `status` 列 L1 恒为 `confirmed`，`confirmed_at` / `confirmed_by` 由创建时填充（等于创建时间 / 创建人），`review_remark` 恒 NULL —— 四个字段在 L1 都有合理值，不是空壳。
- **默认禁止负库存**；真要"先出后补"另开显式待补登记，不允许余额默默变负。
- 单据号生成参考 `backend/app/services/ticket_no.py`。
- 单据表自带 `operator_id`（业务语义"谁出的库"），**不能只靠审计表反查**。
- `unit_cost` L1 只留痕、**不暴露读接口与前端显示**，等做金额账时启用 `inventory:cost:read`。

### 需要登记 §8 的错误码（草案）

`INSUFFICIENT_STOCK`（库存不足）、`SKU_IN_USE`（被单据引用不可停用）、`DOCUMENT_ALREADY_VOIDED`（单据已冲正）、`SKU_NOT_FOUND`。**不得新增未登记码**；`PERMISSION_DENIED` 沿用现有码，不重复登记。

## 4. 接入现有体系的落点

新增一个权限码 / 端点，需要同时登记四处：

| 落点 | 文件 | 动作 |
|---|---|---|
| 权限码与角色 | `backend/app/core/permissions.py` | `ALL_PERMISSIONS` + `_ROLE_PERMISSIONS` + `_DATA_SCOPE` + `_DEPENDENCIES` + `grantable_permissions()` |
| 端点与范围 | `backend/app/api/admin_inventory*.py` | 每个写端点挂 `Depends(require(...))`；service 层显式 `ALL` |
| 前端与双语 | `router/index.js` meta、`Layout.vue` 菜单、`utils/permissionLabels.js`、两套语言包 | 新权限码名 + 新角色名 `warehouse` 必须进 `zh-CN` / `en-US`，否则授权下拉显示裸码 |
| 审计留痕 | `backend/app/services/audit.py` `_RULES` | 按方法 + 路径补行；`known_actions()` 自动带出 `inventory.*` 分组，前端筛选零改动；403 失败也留痕 |

审计失败不得影响业务（现有中间件已整段 try 包住，勿回退）。

## 6. 审批扩展口子（已定案：本期不做，但预留）

**结论**：不做审批、不做状态机、不做复核界面。但要保证未来启用「仓管制单 → 主管确认」时，**不改表结构、不改过账逻辑、不改流水语义**。口子分四层，全部零额外功能成本。

### 6.1 数据层：状态字段先建好

`inventory_documents` 一期就带以下列，L1 全部有合理值（不是空壳）：

| 列 | 类型 | L1 取值 | 未来启用审批后 |
|---|---|---|---|
| `status` | VARCHAR(20) NOT NULL DEFAULT `'confirmed'` | 恒 `confirmed` | 新增 `draft` / `pending` / `void` |
| `confirmed_at` | TIMESTAMPTZ NULL | 创建时间 | 主管确认时间 |
| `confirmed_by` | INT NULL FK users | `operator_id` | 审核人 |
| `review_remark` | TEXT NULL | NULL | 审核意见 / 驳回原因 |

**关键**：默认值 `confirmed` 让 L1 的每条单据天然是"已生效"，未来只需把默认值改成 `draft`，不用 `ALTER TABLE` 加列。

### 6.2 服务层：创建与过账解耦（真正的口子）

```
create_document()   # 只写 inventory_documents + inventory_document_items，不含任何余额操作
post_document()     # 独立：SELECT ... FOR UPDATE 锁余额 → 写 stock_movements → 更新 balances
```

- L1：`create_document()` 事务内**立即调用** `post_document()`，行为上仍是"保存即生效"。
- 未来：`create_document()` 落 `draft` 不调用过账；新增 `confirm_document()` 做状态校验后调用 `post_document()`。**两个函数内部一行不改，只改调用时机。**
- `post_document()` 自带幂等保护（同一 `document_id` 已有流水则跳过），防止重复确认造成重复扣减。
- 独立模块建议放 `backend/app/services/inventory/posting.py`，与单据 CRUD 分开，避免未来审批逻辑散进 router。

### 6.3 权限层：命名规范已保证可加

权限码按 `inventory:<资源>:<动作>` 组织，未来新增 `inventory:document:review` 是纯新增，不动任何现有码与角色模板。**本期不预先登记 review 码**——避免临时授权下拉里出现没有实际功能的选项。

### 6.4 API / 前端：不把"即时生效"写死

- 单据详情与列表响应**始终返回 `status` 字段**（L1 恒 `confirmed`），前端不硬编码"已保存即生效"的判断逻辑。
- 提交按钮文案走 i18n key，未来改文案不动组件。
- 本期**不建空端点、不建隐藏菜单、不建状态筛选器**——口子在数据与代码结构里，不在 UI 里留半截功能。

### 6.5 未来启用审批的改动清单（现在一处都不做）

| # | 改动 | 说明 |
|---|---|---|
| 1 | 迁移：`status` 默认值 `confirmed` → `draft` | 只改默认值，不加列 |
| 2 | `create_document()` 不再调用 `post_document()`，落 `draft` | 调用时机 |
| 3 | 新增 `confirm` / `reject` 端点 + `inventory:document:review` 权限码 | 新增，不改既有 |
| 4 | `confirm_document()` 里校验状态、写 `confirmed_by/at`、调 `post_document()` | 复用现成过账函数 |
| 5 | 单据列表加状态筛选、详情加审核操作区、两套语言包补文案 | 纯前端 |
| 6 | `audit.py` `_RULES` 补 confirm / reject 两行 | 沿用零侵入审计 |

预计 **2–3 人天**，且**不需要数据迁移脚本**（历史单据已是 `confirmed`，天然兼容）。

### 6.6 防回归约束

加一条测试断言：L1 创建的单据 `status == 'confirmed'` 且 `confirmed_by` 非空、`stock_movements` 恰好生成对应条数。防止未来有人把默认值改成 `draft` 却忘了接审核流，导致单据静默不过账。

> 其余待办（不阻塞 PRD）：低库存阈值由谁设定、预警给谁看、SKU 编码规则（`WL-0001` 之类）、演示数据补库存初值。
