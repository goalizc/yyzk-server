## 1. 客户侧功能（16 条）

### TC-01 产品下拉加载
- **前置**：库中有 2 个已上架、1 个已下架产品
- **步骤**：打开首页
- **预期**：下拉显示 2 个已上架产品的「名称 + 型号」，无下架产品
- **优先级**：P0

### TC-02 零件级联与分组
- **前置**：产品 A 有 3 个零件分属 2 个 group，产品 B 有 2 个
- **步骤**：选择产品 A
- **预期**：零件下拉出现 3 项，按 group_name 分组显示组标题，组内按 sort_order 升序
- **优先级**：P0

### TC-03 切换产品重置后续选择
- **前置**：已选产品 A、零件 A1、关键词已输入、列表已加载
- **步骤**：切换到产品 B
- **预期**：零件、故障列表、关键词框全部清空，零件下拉刷新为 B 的零件，并**立即加载 B 的全部故障**
- **优先级**：P0

### TC-04 故障列表排序与零件参考
- **前置**：某产品下有 5 条已发布故障（跨 2 个零件），view_count 分别为 5/50/500/1/20
- **步骤**：只选产品（不选零件）
- **预期**：5 张卡片按 500→50→20→5→1 降序，每张显示标题、现象摘要与**所属零件名标签**；再选零件后列表按零件收窄
- **优先级**：P0

### TC-05 故障详情渲染
- **前置**：一条故障含 3 个步骤，第 1 步有图，含 1 个 PDF 附件
- **步骤**：点击卡片
- **预期**：标题/现象/根因正确；步骤按 1→2→3；第 1 步图片正常加载，缺失图片不破版；附件可点
- **优先级**：P0

### TC-06 专业维修警告（正向）
- **前置**：故障 X `needs_professional=true`
- **步骤**：打开 X 详情
- **预期**：顶部红色警示条，文案为「此故障需专业人员维修，请勿自行拆机，建议联系售后」
- **优先级**：P0

### TC-07 专业维修无警告（反向）
- **前置**：故障 Y `needs_professional=false`
- **步骤**：打开 Y 详情
- **预期**：无警示条，页面布局不下移
- **优先级**：P1

### TC-08 标记已解决（含日志精确更新）
- **前置**：A、B 两台设备各打开同一故障详情一次（产生 2 条 query_logs）
- **步骤**：A 设备点击「问题已解决」
- **预期**：
  - 弹「感谢反馈」
  - `faults.resolved_count` +1
  - **仅 A 的 query_logs.resolved=true**，B 的记录保持 NULL
  - 重复点击不重复计数（按钮置灰或二次点击返回成功但不加数）
- **优先级**：P0

### TC-09 未解决转工单
- **步骤**：详情页点击「未解决，联系售后」
- **预期**：跳转工单页，产品/零件/故障名称正确回显
- **优先级**：P0

### TC-10 工单必填校验
- **步骤**：只填「称呼」，不填联系方式与描述
- **预期**：提交按钮禁用，或点击后提示「请填写联系方式」+「请填写故障描述」，焦点跳到第一个错误字段
- **优先级**：P0

### TC-11 工单提交成功（含上门字段）
- **前置**：填完联系方式、描述，选择「需要上门」
- **步骤**：提交
- **预期**：
  - 跳转成功页，显示工单号 `TK+8位日期+4位序号`（如 TK202610190001）
  - 提示「售后会在 24 小时内联系您」
  - **后台详情里 `need_on_site` 为「是」**（验证 v1.1 新增列已落库）
- **优先级**：P0

### TC-12 关键词筛选命中
- **前置**：某组合下 5 条故障，其中 2 条标题含「噪音」
- **步骤**：关键词框输入「噪音」
- **预期**：列表实时过滤为 2 条（≤300ms 防抖），清空后恢复 5 条，全程不重新请求接口
- **优先级**：P0

### TC-13 关键词无结果 → 空态 + 未命中日志
- **前置**：当前产品（+零件）范围内无任何含「漏水」的故障
- **步骤**：输入「漏水」
- **预期**：
  - 列表区显示空态「没有匹配「漏水」的故障…」
  - **DB 中新增一条 `query_logs`：`hit=false`、`raw_query='漏水'`、product_id 正确（选了零件时 part_id 也正确，未选则为 NULL）**
  - 30 秒内重复输入同一关键词不重复写日志
- **优先级**：P0

### TC-14 未发布故障前台不可见
- **前置**：某故障 `is_published=false`
- **步骤**：前台按该产品+零件查询，并直接访问 `/faults/{id}`
- **预期**：列表不出现；直接访问返回 404 页面，不泄露内容
- **优先级**：P0

### TC-15 附件下载
- **前置**：故障含 `维修手册.pdf`
- **步骤**：点击附件
- **预期**：浏览器下载，文件名与页面显示一致，Nginx 返回 200（非 403/404）
- **优先级**：P1

### TC-16 检索词随详情透传
- **步骤**：输入「噪音」→ 点击其中一条结果
- **预期**：URL 为 `/faults/{id}?q=噪音`，`query_logs` 中该条记录的 `raw_query='噪音'`、`hit=true`
- **优先级**：P1

- **优先级**：P2

- **预期**：响应均含 `detail`（中文可读）与 `code`（稳定机器码），无堆栈信息
- **优先级**：P1

## 4. 部署测试（5 条）

### TC-50 干净环境启动
- **前置**：干净 Ubuntu 22.04，仅装 Docker 与 Compose
- **步骤**：
  1. 拷贝 deploy 目录
  2. `cp .env.example .env`，改 `DB_PASSWORD`（openssl rand -hex 24）、`JWT_SECRET`（openssl rand -hex 32）、`ADMIN_INIT_PASSWORD`
  3. `mkdir -p data/uploads data/pg`
  4. `docker compose up -d`
  5. 等待 db 与 backend healthy 后执行 `docker compose run --rm init`
- **预期**：
  - **4 个容器**（db / backend / frontend / nginx）全部 running，db 与 backend 为 healthy
  - `init` 任务退出码 0，输出"已创建管理员"
  - `http://服务器IP/` 显示客户查询页
  - `http://服务器IP/admin` 显示登录页
  - 用 `.env` 里的 `ADMIN_INIT_PASSWORD` 能登录成功（不是任何硬编码默认值）
  - 全过程 ≤ 5 分钟
- **优先级**：P0

### TC-51 重启恢复
- **步骤**：`docker compose restart`，再重启服务器
- **预期**：服务自动起来，数据不丢，`restart: unless-stopped` 生效
- **优先级**：P0

### TC-52 备份与恢复
- **前置**：按 `docs/04-运维与运营/备份恢复方案.md §2` 创建 `/opt/fault-system/backup.sh`
- **步骤**：
  1. 跑一次 backup.sh，确认 `backups/` 下生成 db_*.sql.gz 与 uploads_*.tar.gz 且体积合理
  2. 停掉 db 容器再跑一次，确认脚本退出码非 0 且不产生"成功"文件（验证 pipefail）
  3. 造新数据后按 §4.1 恢复（含 DROP SCHEMA 与 ON_ERROR_STOP=1）
- **预期**：数据回到备份时刻；附件可下载；`ticket_status_logs` 条数与备份前一致；恢复过程无 "already exists" 报错
- **优先级**：P1

### TC-53 初始化脚本幂等
- **步骤**：连续执行 `docker compose run --rm init` 三次
- **预期**：第一次创建，后两次输出「已存在，跳过」；`users` 表始终 1 条 admin；已改过的密码不被覆盖；未设置 `ADMIN_INIT_PASSWORD` 时退出码为 2 且不建号
- **优先级**：P0

### TC-54 SPA 路由与静态资源
- **步骤**：直接访问并刷新 `/admin/faults/edit/1`、`/faults/1`
- **预期**：均正常渲染，不出现 404；`/uploads/xxx.jpg` 返回 200 且带 `Cache-Control: public, immutable`
- **优先级**：P0

## 6. 性能与安全（4 条）

### TC-70 查询响应 P95
- **前置**：5 万条故障、50 万条 query_logs 的造数环境
- **步骤**：用 k6/JMeter 对 `/api/faults`、`/api/faults/{id}` 各压 5 分钟
- **预期**：P95 < 500ms，错误率 < 0.1%
- **优先级**：P0

### TC-71 100 并发
- **步骤**：100 并发持续查询 10 分钟
- **预期**：无 5xx，无连接池耗尽告警，后端内存 < 1G
- **优先级**：P1

### TC-72 XSS 注入
- **步骤**：在故障标题、现象、步骤中录入 `<img src=x onerror=alert(1)>`，并在工单描述中提交同样内容
- **预期**：前台与后台均**按纯文本显示**，不弹窗、不执行（验证未使用 `v-html`）
