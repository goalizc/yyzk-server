# 前端质量关卡（lint / 单测 / E2E）

> 补齐 2026-10-21。此前前端只有组件测试一层，缺少静态检查与浏览器验证。
> 三条命令构成交付前的固定关卡，任一条红都不算完成。

## 1. 前置：起一套可联调的环境

E2E 需要真实后端，用 docker 全栈：

```bash
cd deploy
docker compose up -d
docker compose run --rm init        # 首次建管理员；账号已存在会跳过
```

服务入口 `http://localhost`（nginx 同源反代 `/api` 与 `/uploads`）。

**改了前端代码后必须重建镜像**——前端产物是构建进镜像的，`docker compose up -d`
不会感知源码变化：

```bash
cd deploy && docker compose build frontend && docker compose up -d frontend
```

### 踩过的坑

> **症状**：E2E 登录后停在 `/admin` 不动，断言 `/admin/tickets` 超时。
> **根因**：镜像里跑的是旧产物。路由里 `/admin → /admin/tickets` 的重定向是后加的，
> 旧 bundle 没有。
> **排查方法**：`curl -s http://localhost/ | grep -o 'assets/index-[^"]*'`，
> 与本地 `npx vite build` 产出的文件名比对，不一致就是镜像没重建。

## 2. ESLint

```bash
cd frontend && npm run lint
```

配置文件 `frontend/eslint.config.js`（flat config，ESLint 10 + eslint-plugin-vue 10）。

两条关键设计：

1. **`vue/no-v-html` 设为 error**——项目红线是禁止 `v-html`，靠规则守住而不是靠 review。
2. **自动注入的全局符号从 `auto-imports.d.ts` 读取**，不手写白名单。
   `vite.config.js` 里 `AutoImport({ dts: 'auto-imports.d.ts' })` 会把 `ElMessage`
   等符号写成 `declare global { const ElMessage: ... }`，`eslint.config.js` 解析这份
   文件生成 `globals`。这样 lint 认的全局与构建期真正注入的始终一致，不会两边漂移。
   该 d.ts **入库**，否则新 clone 必须先跑一次 dev/build 才能 lint。

规则水位刻意收紧到"能发现真问题"，不做风格整齐：属性换行顺序、缩进、自闭合等
纯格式规则全部关掉，避免一次 lint 把历史代码全改一遍。

## 4. E2E（Playwright）

```bash
cd frontend && npm run e2e
```

配置 `playwright.config.js`：

- **用系统已装的 Chrome**（`channel: 'chrome'`），不下载 Chromium，省一份 ~150MB
  的浏览器，且验的就是用户真实使用的浏览器。
- `workers: 1`，串行——冒烟用例改同一份数据，并行会互相干扰。
- `outputDir` 默认 `/tmp/e2e-results`（可用 `E2E_OUTPUT_DIR` 覆盖）。**不要放仓库内**：
  Playwright 每轮会清空该目录，沙箱对单次批量删除有阈值拦截（>50 文件直接拒绝）。
- `trace: 'off'`——沙箱里 Playwright 复制 trace 归档会 EPERM；断言超时类失败看截图更直接。
- 账号可用 `E2E_ADMIN_USER` / `E2E_ADMIN_PASS` 覆盖，默认取 `deploy/.env` 的开发账号。

### 只写一条主链路的原因

技能 §14 的取舍：单测已覆盖各页分支，E2E 的价值在"跨页面 + 真实后端 + 真实浏览器"。
加 CRUD 会让维护成本翻倍而边际收益很低。

`e2e/main-flow.spec.js` 覆盖：

```
客户两级选择（产品→零件）→ 故障现象列表点条目进方案
  → 方案页反馈"未解决"
  → 提交工单，拿到工单号
  → 后台登录，按单号搜到该工单
  → 详情面板：状态可选项恰好 2 个（open→processing/closed）
  → 备注为空时保存被拦下
  → 填备注后保存成功，处理人变为当前用户
  → 看板四张卡无 NaN/undefined
```

### 断言"数量"而非"包含"的地方

- 状态下拉断言 `toHaveCount(2)` 而不是"包含处理中"——后者在错误地列出全部 4 个状态时
  也会通过。这条正好守住契约 §5 的状态机约束。

### 英文排版守卫（`e2e/i18n-layout.spec.js`）

主链路之外唯一一条"形式类" E2E：**英文界面下表单标签不得折行**。

中文标签短（「零件编号」），英文长 1.5–2 倍（`Part number` / `Confirm password` /
`Requires a professional`）。写死 `label-width` 时中文正好、英文折行，而且——

> **折行在 DOM 里看不出来。** `el-form-item` 的行高锁死 32px，label 折行后盒子高度
> **仍然是 32px**，第二行直接溢出、压到下一行的标签上（视觉是文字重叠，不是行变高）。
> 所以判据必须是 `label.scrollHeight >= 1.5 × line-height`，不是 `getBoundingClientRect().height`。

覆盖 9 个场景 / 49 个标签：故障编辑器、用户新建弹窗、临时授权面板、产品 / 零件 / 产品线
新建弹窗、工单详情面板、修改密码弹窗、客户侧提交工单。失败信息直接点名场景与标签：

```
以下英文表单标签折行（宽度不够，请调大该页 useFormLabelWidth 的英文宽度）：
用户新建弹窗: Confirm password
```

**已做反向验证**：把用户弹窗英文宽度从 150px 退回 130px，用例立即失败并点名
`Confirm password`；恢复后转绿。

## 5. 交付前关卡清单

```bash
cd frontend
npm run lint      # 0 problems
npm run test      # 168 passed / 24 文件
npm run e2e       # 4 passed（主链路 1 + 国际化 3，含排版守卫）

# 仓库根
python scripts/dev/check_i18n.py   # 扫描硬编码中文，0 违规
```

`check_i18n.py` 是**国际化不倒退的硬闸门**：它扫 `frontend/src` 下非注释、非
`locales/` 的中文字面量，发现即退出码 1。确实不能翻译的值（与后端约定的比较值、
开发日志）在该行加 `// i18n-ignore` 并写明原因。

改了构建配置或依赖时额外跑 `npx vite build --outDir dist-verify`（不要直接
`vite build`：清空 `dist/assets` 会触发沙箱批量删除拦截）。
