# 售后自助故障诊断系统 — 完整分期路线图

> 版本：v1.0 ｜ 日期：2026-10-19
> 范围：从 MVP 到成熟期的完整演进路径，共 4 期 + 持续运营
> 每期独立可交付、独立产生业务价值，不依赖下一期上线

---

## 总览：四期演进路线

```
一期 MVP          二期 智能化        三期 体系化        四期 生态化
(3.5-4周)        (4周)             (6周)             (持续)
─────────       ─────────         ─────────         ─────────
结构化查询       自然语言问答       故障树引导         IoT设备联动
产品→零件→故障   模糊搜索          连续诊断问答        主动告警
工单闭环         报错码查询        多版本/批次        多租户分客户
统计看板         图片识别故障      BOM精确匹配        对接ERP/CRM
                                 多语言/H5          知识库众包
```

---

## 一期：MVP 结构化自助查询（第 1-4 周）

### 目标
用最低成本验证业务：用户能不能通过下拉选择自己解决常见故障。

### 功能范围

#### 客户侧
- [ ] 三级级联查询：产品 → 零件 → 故障现象
- [ ] 当前结果内关键词筛选（选填，用于快速缩小范围并产生未命中统计）
- [ ] 故障详情页：根因 + 分步图文解决方案 + 附件下载
- [ ] 安全警告（需专业维修的故障自动显示警示）
- [ ] "问题已解决"/"未解决"反馈按钮
- [ ] 未解决 → 工单提交（自动带产品/零件/故障上下文 + 是否需要上门）

#### 后台侧
- [ ] JWT 登录
- [ ] 产品 CRUD + 上下架
- [ ] 零件 CRUD（按产品级联）
- [ ] 故障知识库 CRUD（含步骤 JSON 编辑器、附件上传）
- [ ] 工单列表 + 状态流转（待处理/处理中/已解决/已关闭），流转留痕（操作人 + 时间）
- [ ] 工单详情（含上门意愿、用户描述、处理备注、流转历史）
- [ ] 数据看板：查询量、自助解决率、TOP10 故障、未命中检索词，支持时间范围联动
- [ ] 修改自己密码

#### 技术交付
- [ ] Docker Compose 一键部署
- [ ] Nginx 反向代理
- [ ] PostgreSQL 建表（见 schema.sql）
- [ ] 备份脚本

### 工作量
| 角色 | 工作量 |
|---|---|
| 后端（FastAPI） | 18 人天（B 13 + 联调 2 + 部署 1 + 内测 2） |
| 前端（Vue3） | 17.5 人天（C 13.5 + 联调 2 + 内测 2） |
| 售后数据整理与导入 | 7 人天（与开发并行，不计入开发人天） |
| **合计** | **35.5 开发人天 ≈ 4 周（2 人并行）** |

> 原表"2 周"与 35.5 人天工作量不符，已按任务卡重算。详见 `docs/00-项目管理/排期计划.md`。

### 硬件
4 核 8G，40G SSD，无 GPU。

### 验收标准
1. 售后团队能在后台录入 50 条真实故障。
2. 客户能走完"选产品→选零件→看方案→反馈"全流程。
3. 未命中日志和解决率在后台可见，且随看板时间筛选联动。
4. 工单闭环成立：上门意愿、用户描述、处理备注、流转历史齐全。
5. `docker compose up -d` 在干净服务器 5 分钟内全部起服。

### 成功指标（上线 1 个月后看）
- 自助解决率 ≥ 20%（**首月观察值**；对外承诺以章程口径为准：上线 3 个月 ≥ 30%）
- 日均查询 ≥ 50 次
- 高频故障 TOP 10 覆盖 60% 工单量

## 二期：智能化升级（第 5-8 周）

### 目标
解决 MVP 的两个痛点：
1. 用户不想下拉选，想直接打字描述故障
2. 报错码、图片这类快速入口没做

### 新增功能

#### 2.1 自然语言问答（核心）
- 用户在输入框直接打字："我家扫地机开机就报警，红灯一直闪"
- 后端调用本地 LLM（Ollama + Qwen2-7B）做实体抽取：
  - 识别产品名 → 映射到 products 表
  - 识别零件名 → 映射到 parts 表
  - 识别故障关键词 → 向量检索 faults 表
- 返回结构化结果：匹配到的故障卡片，展示方案
- **置信度低时**：自动引导"您是不是要找以下产品？"并展开级联选择器

#### 2.2 报错码快速查询
- 新增 `fault_codes` 表：code、故障含义、关联 fault_id
- 客户侧新增"输入报错码"入口（如 E01、红灯闪 3 次）
- 后台支持批量导入报错码表

#### 2.3 故障图片识别
- 用户上传故障照片（如报错屏幕、损坏零件）
- 本地多模态模型（Qwen-VL）识别图片内容
- 自动匹配对应故障方案
- MVP 阶段先做"图片 OCR + 报错码识别"，不做复杂视觉判断

#### 2.4 搜索体验增强
- 故障列表支持关键词模糊搜索（不依赖级联选择）
- 相关推荐：看完某故障后，推荐"用户还遇到过"的其他故障
- 搜索历史热词展示

### 技术改动

#### 新增组件
| 组件 | 作用 | 资源占用 |
|---|---|---|
| Ollama | 跑 Qwen2-7B-Instruct 做实体抽取和 RAG | 6G 内存 |
| Qdrant | 向量数据库，存故障知识库 embedding | 512M 内存 |
| Embedding 模型 | bge-m3 或 text2vec-chinese | 1G 内存 |

#### 数据库改动
```sql
-- 新增表
CREATE TABLE fault_codes (
    id SERIAL PRIMARY KEY,
    fault_id INT REFERENCES faults(id),
    code VARCHAR(50) NOT NULL,          -- E01 / 红灯闪3次
    code_type VARCHAR(20),               -- 数字码/指示灯/声音
    description TEXT,
    UNIQUE(fault_id, code)
);

-- faults 表加向量字段（Qdrant 侧，不入 PG）
-- query_logs 表加 raw_query 字段已有，记录用户原始输入
```

#### 后端新增 API
| Method | Path | 说明 |
|---|---|---|
| POST | `/api/search/natural` | 自然语言搜索（LLM 抽取+向量检索） |
| GET | `/api/fault-codes/{code}` | 报错码查询 |
| POST | `/api/fault-codes/upload` | 批量导入报错码 |
| POST | `/api/image/recognize` | 图片识别故障 |

#### 部署变化
- 原来的业务机不动
- **新增一台 GPU 机器**（或在原机器加 GPU）跑 Ollama + Qdrant
- 业务机通过内网调用模型服务，数据不出公司

### 工作量
| 模块 | 工作量 |
|---|---|
| Ollama + Qdrant 部署调试 | 3 天 |
| 实体抽取 Prompt 调优 + RAG 管线 | 5 天 |
| 报错码模块（表+API+前端） | 3 天 |
| 图片识别（MVP 版 OCR） | 5 天 |
| 搜索体验前端 | 3 天 |
| 联调测试 | 3 天 |
| **合计** | **4 周** |

### 硬件升级
- 方案 A（推荐）：新增一台 GPU 机器，8G 显存（RTX 3060/T4），16G 内存
- 方案 B：原机器升到 32G 内存，纯 CPU 跑 7B 模型（慢但能跑）

### 验收标准
1. 用户输入一段口语化故障描述，能正确匹配到对应故障卡片，准确率 ≥ 70%。
2. 报错码查询响应 < 200ms。
3. 图片上传后能识别出报错码并匹配方案。
4. LLM 服务挂了，系统自动降级到结构化下拉查询，不影响主流程。

### 成功指标
- 自然语言搜索占比 ≥ 40%
- 自然语言搜索自助解决率 ≥ 30%
- 报错码查询覆盖 80% 高频报错

## 三期：体系化完善（第 9-14 周）

### 目标
从"能用"升级到"好用且专业"，解决复杂故障诊断和多场景适配。

### 新增功能

#### 3.1 故障树引导诊断
**痛点**：MVP 是"选产品→选零件→选故障"，但有些故障用户自己判断不了是哪个零件出问题，需要系统引导提问。

**做法**：
- 后台配置故障树：从某个产品/某个症状开始，连续提问
- 例：
  ```
  系统："开机后完全没反应，还是能开机但报错？"
  用户："完全没反应"
  系统："电源适配器指示灯亮吗？"
  用户："不亮"
  系统：→ 定位故障：电源适配器损坏，方案 X
  ```
- 每棵树是一个 JSON 流程图：节点（问题/结论）+ 边（是/否/选项）
- 前端用聊天式 UI 展示

**数据库改动**：
```sql
CREATE TABLE fault_trees (
    id SERIAL PRIMARY KEY,
    product_id INT REFERENCES products(id),
    title VARCHAR(200),           -- "开机无反应诊断流程"
    root_node_id INT,
    is_active BOOLEAN DEFAULT TRUE
);

CREATE TABLE fault_tree_nodes (
    id SERIAL PRIMARY KEY,
    tree_id INT REFERENCES fault_trees(id),
    node_type VARCHAR(20),        -- question / conclusion
    question_text TEXT,           -- 问题
    options JSONB,                 -- 选项 [{"label":"是","next_node_id":3}]
    conclusion_fault_id INT REFERENCES faults(id)  -- conclusion 节点关联的故障
);
```

#### 3.2 多版本/批次管理
**痛点**：同一型号产品 V1 和 V2 硬件不同，故障方案不能通用。

**做法**：
- `products` 表增加 `versions` 关联（或独立 `product_versions` 表）
- 故障知识库关联到具体版本
- 用户查询时先选版本（或通过 SN 码自动识别版本）

#### 3.3 BOM 精确匹配
**痛点**：用户报零件号，系统要能直接定位到该零件的故障。

**做法**：
- 零件号精确搜索入口
- 支持扫码（扫产品铭牌/零件条码）
- 对接内部 BOM 系统（如有），自动同步产品和零件清单

#### 3.4 移动端适配 / 小程序
- H5 自适应（响应式布局）
- 可选：微信小程序版（用户扫码直接进）
- 消息通知：工单状态变更推送给用户

#### 3.5 权限与多角色
- 超级管理员 / 售后主管 / 一线客服 / 只读审计
- 数据权限：客服只能看自己负责的产品线
- 操作日志：谁改了哪条故障方案，留痕

#### 3.6 知识库审核流
- 新增故障方案 → 草稿状态
- 主管审核通过 → 发布到前台
- 避免售后人员写错方案直接误导用户

### 工作量
| 模块 | 工作量 |
|---|---|
| 故障树后台配置器 + 前端引导问答 | 10 天 |
| 多版本/批次管理 | 5 天 |
| BOM 同步接口（如有内部系统） | 5 天 |
| 移动端 H5 适配 | 5 天 |
| 权限体系 + 审核流 | 5 天 |
| 联调测试 | 5 天 |
| **合计** | **6 周** |

### 验收标准
1. 售后主管能在后台可视化配置一棵故障树，前台能跑完引导问答。
2. 同一产品 V1/V2 的故障方案隔离正确。
3. 不同角色登录看到不同菜单和数据范围。
4. 新增故障方案必须经过审核才前台可见。

### 成功指标
- 复杂故障（需要引导诊断的）自助解决率 ≥ 40%
- 移动端访问占比 ≥ 30%

## 四期：生态化与智能化深化（第 15 周起，持续迭代）

### 目标
从"内部售后工具"升级为"客户服务平台"，与公司其他系统打通。

### 方向 4.1：IoT 设备联动
- 对接设备 IoT 平台，用户登录后自动看到自己绑定的设备
- 设备上报异常 → 主动推送故障解决方案到用户
- 设备故障码自动同步到知识库，不用人工录入

### 方向 4.2：对接现有售后系统
- Webhook 对接公司现有工单系统（如 Zendesk、自研 CRM）
- 自助系统创建的工单自动同步过去，不重复造轮子
- 工单状态双向同步

### 方向 4.3：知识库众包
- 允许优质用户贡献解决方案（审核后发布）
- 社区讨论区：用户互相交流维修经验
- FAQ 自动沉淀：高频问答自动建议录入知识库

### 方向 4.4：多语言
- 支持英文、日文等（如有海外业务）
- 故障方案多语言版本管理

### 方向 4.5：高级分析
- 故障趋势分析：某型号某故障突然增多 → 预警质量问题
- 产品改进建议：TOP 故障反哺研发
- 客户满意度 NPS 调研嵌入

### 方向 4.6：多租户（如做 SaaS 化）
- 如果未来想把这套系统卖给其他公司用
- 数据隔离：每个公司独立知识库
- 套餐管理、计费

## 人员配置建议

### 最小团队（一期跑通）
- 后端 1 人（Python/FastAPI）
- 前端 1 人（Vue3）
- 产品/售后知识运营 0.5 人（整理故障数据，兼职）
- 运维 0.2 人（Docker 部署，兼职）

### 二期加配
- 加 1 人做 LLM/RAG 调优（可由后端兼任）

### 三期加配
- 加 1 人做故障树前端交互和移动端适配

### 关键提醒
**开发工作量不是瓶颈，知识库录入才是。**
每一期都需要售后团队持续把真实故障结构化录入。建议：
- 一期前：整理历史工单 TOP 50 故障
- 二期前：整理报错码清单
- 三期前：梳理 3-5 个复杂故障的诊断流程（画成树状图）

## 风险与依赖

| 风险 | 影响期 | 应对 |
|---|---|---|
| 历史工单是非结构化文字，整理耗时 | 一/二期 | 先用 LLM 辅助抽取（把工单喂给本地模型，自动生成结构化表格，人工审核） |
| LLM 准确率不够 | 二期 | 置信度阈值调低，匹配不到就降级到下拉选择，不硬答 |
| 故障树配置复杂，售后不会用 | 三期 | 做可视化拖拽配置器，或者产品经理先帮他们配好前几棵树 |
| IoT 对接需要设备端配合 | 四期 | 提前和 IoT 团队对齐接口，预留半年周期 |
| 知识库越积越乱 | 全期 | 后台加"重复故障检测"，相似故障合并；定期 review |
