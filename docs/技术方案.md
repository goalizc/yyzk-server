## 一、需求与目标

### 1.1 业务场景
公司产品种类和零部件持续增加，售后工单量上升。需要一个面向**终端用户**的自助查询系统：
- 用户描述故障现象 + 选择产品/零件 → 系统定位原因 → 返回解决办法
- 自助解决不了 → 一键转工单，自动带上下文，减少售后沟通成本

### 1.2 核心目标
| 目标 | 衡量标准 |
|---|---|
| 自助解决率 | 上线 3 个月后，30% 常见故障用户自助解决，不进人工 |
| 响应速度 | 查询结果 < 500ms 返回 |
| 自主可控 | 全部组件开源、私有化部署，数据不出内网 |
| 快速上线 | 1 人后端 + 0.5 人前端，2 周内 MVP 上线 |
| 硬件门槛 | 最低 4 核 8G 服务器可跑 |

```
                             │  · query_logs 查询日志       │

  ┌─────────────────────────────────────────────┐

  │  ─────────────────────────────────────       │
  │  · Ollama + Qdrant：自然语言模糊问答          │
  │  · 用户输入一段故障描述 → LLM提取实体 →       │
  │    走上面同一套结构化检索流程                  │
  └─────────────────────────────────────────────┘
```

### 2.2 设计原则
1. **结构化检索为底座，LLM 为可选增强**：即使不部署任何大模型，系统核心功能（产品→零件→故障→方案）完整可用、零幻觉。
2. **前后端分离**：前端独立构建为静态文件，后端只提供 JSON API。
3. **Docker 一键编排**：所有服务通过 docker-compose 启动，不污染宿主环境。
4. **数据驱动闭环**：查询日志 → 统计分析 → 反哺知识库，持续提升命中率。

## 三、核心业务流程（逻辑闭环）

### 3.1 闭环总图

```
  ┌─────────────┐    录入     ┌──────────────┐
  │ 售后团队     │ ────────►  │  知识库       │
  │ (后台管理)   │            │  产品/零件/   │
  └──────┬──────┘            │  故障/方案    │
         │                    └──────┬───────┘
         │                           │ 查询
         │                    ┌──────▼───────┐
         │                    │  终端用户     │
         │                    │  选择产品→    │
         │                    │  零件→故障    │
         │                    └──────┬───────┘
         │                           │
         │              ┌────────────┴────────────┐
         │              │                          │
         │       命中方案 ✅                 未命中 ❌
         │              │                          │
         │              ▼                          ▼
         │      展示解决方案+附件          一键提交工单
         │      标记"是否解决"            自动带产品/零件/
         │                          故障描述上下文
         │              │                          │
         │              └────────────┬────────────┘
         │                           │
         │                    ┌──────▼───────┐
         │                    │  查询日志    │
         │                    │  query_logs │
         │                    └──────┬───────┘
         │                           │
         └──────  定期统计 ◄──────────┘
              (高频故障/未命中词/解决率)
```

### 3.2 用户侧主流程（客户查询页）

**步骤 1：选择产品型号**
- 下拉框，从 `products` 表读取，只显示"已上架"状态的产品。

**步骤 2：选择故障零件**
- 级联下拉：根据选中的 product_id，过滤 `parts` 表，只显示该产品下的零件。
- 零件按"系统/模块"分组显示（如：电源模块、显示模块、按键模块）。

**步骤 3：选择故障现象**
- 根据 product_id + part_id，过滤 `faults` 表，显示该组合下的故障现象列表。
- 每条故障显示：故障标题（如"开机无反应"）、发生频率标签。

**步骤 4：查看解决方案**
- 展示：
  - 故障现象描述
  - 可能原因（根因分析）
  - 分步解决办法（有序步骤，支持图文混排）
  - 所需工具/备件
  - 附件下载（维修手册 PDF、视频链接、拆解图）
  - 安全警告（如涉及拆机，显示警告）
- 底部两个按钮：
  - ✅ "问题已解决" → 记录反馈，关闭页面
  - ❌ "未解决，联系售后" → 跳转工单页，自动带入 product_id/part_id/fault_id/用户描述

**步骤 5：提交工单（未命中时）**
- 表单：联系方式、故障补充描述、是否需要上门。
- 后端自动关联上下文，写入 `tickets` 表。

### 3.3 后台管理流程（售后团队使用）

1. **登录鉴权**：JWT，只有内部账号可访问 `/admin` 路径。
2. **产品管理**：CRUD 产品型号，上下架控制。
3. **零件管理**：按产品维护零件清单，支持分组。
4. **故障知识库**：
   - 新建故障时，必须选择所属产品和零件（强关联）。
   - 填写故障现象、根因、解决步骤（JSON 数组，每步支持文字+图片）。
   - 上传附件。
   - 标记"是否需要专业人员维修"（true 则前台显示警告，不建议用户自行操作）。
5. **工单处理**：查看用户提交的工单，标记处理状态（待处理/处理中/已解决/已关闭）。
6. **数据统计**：
   - 本月查询次数、自助解决率
   - TOP 10 高频故障
   - 未命中关键词列表（用户查了但没结果的词，指导补充知识库）

### 3.4 闭环关键点
- **结构化强关联**：产品→零件→故障 是外键关联，不会出现"这个故障属于哪个产品都不知道"的脏数据。
- **用户反馈驱动优化**："是否解决"按钮和未命中日志，直接告诉售后团队该补什么知识。
- **可追溯**：每条工单都能看到用户是从哪个故障路径点进来的，减少二次询问。

## 五、API 设计（REST）

|---|---|---|

## 六、技术栈选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | Vue 3 + Element Plus + Vite | 组件丰富，下拉级联、表单、表格开箱即用，售后后台开发快 |
| 后端 | FastAPI (Python 3.11) | 自动生成 OpenAPI 文档，异步性能好，开发效率高 |
| ORM | SQLAlchemy 2.0 | Python 生态最成熟 |
| 数据库 | PostgreSQL 15 | JSONB 支持 solution_steps，比 MySQL 更适合半结构化步骤 |
| 鉴权 | JWT (python-jose) | 无状态，前后端分离标配 |
| 密码 | bcrypt | |
| 文件上传 | 本地磁盘 `/uploads`，Nginx 直接服务 | MVP 阶段不接对象存储，后期可换 MinIO |
| 反向代理 | Nginx | 静态前端 + API 反代 + 附件服务 |
| 容器 | Docker + Docker Compose | 一键编排 |
| LLM 增强（可选） | Ollama + Qdrant | 留接口，MVP 不部署；后续通过 `/api/search/natural` 接入 |

### 为什么不用 MySQL？
`faults.solution_steps` 是嵌套 JSON（步骤数组，每步可有图），PostgreSQL 的 JSONB 可以直接索引、查询，后期要做"步骤里包含某关键词"的检索很方便。数据量小，性能差异可忽略。

## 七、部署方案

### 7.1 硬件要求

| 环境 | 配置 | 说明 |
|---|---|---|
| 开发/测试 | 2核4G | 跑全部容器 |
| 生产 MVP | 4核8G，40G SSD | 日查询 < 500 次 |
| 生产高并发 | 8核16G | 日查询 > 2000 次 |

> **不部署 LLM 时，不需要 GPU，不需要大内存。**
> 后续如开启自然语言问答，再单独加一台 GPU 机器跑 Ollama，业务机本身不用动。

### 7.2 部署步骤

1. 安装 Docker 和 Docker Compose。
2. 把 `deploy/` 目录拷到服务器。
3. `cp .env.example .env`，改数据库密码。
4. `docker-compose up -d`。
5. 访问 `http://服务器IP/` 看客户查询页；访问 `http://服务器IP/admin` 进后台。

### 7.3 服务编排（docker-compose.yml）

详见 `deploy/docker-compose.yml`。包含 4 个容器：
- `db`：PostgreSQL，数据卷持久化到 `./data/pg`
- `backend`：FastAPI，uvicorn 启动
- `frontend`：构建好的 Vue 静态文件，Nginx 服务
- `nginx`：统一入口，80 端口，路由 `/api/` 到 backend，`/` 到 frontend，`/uploads/` 到上传目录

### 7.4 数据备份
- PostgreSQL 每日 `pg_dump` 定时任务。
- `./uploads` 目录定期打包备份。

## 十、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 知识库初始数据少，用户查不到 | 自助解决率低 | 上线前必须把历史工单 TOP 50 故障结构化录入；后台"未命中列表"驱动持续补充 |
| 解决步骤写错，误导用户 | 安全风险 | `needs_professional` 字段：涉及拆机/强电的，前台强制警告"建议联系售后"；所有方案需售后主管审核后才 `is_active` |
| 后期想加自然语言问答 | 需要改代码 | 后端已预留 `/api/search/natural` 接口位置；未来加 Ollama 容器，只需实现该接口，前端无感切换 |
| 并发上来后数据库瓶颈 | 查询慢 | PostgreSQL 加索引（product_id, part_id）；静态前端走 CDN；日查询 < 1 万次时单库足够 |

## 十一、验收标准

1. 客户查询页能完成：选产品 → 选零件 → 看到故障列表 → 点开看方案 → 点"已解决"或"提交工单"。
2. 后台能完成：登录 → 新增产品 → 新增零件 → 录入故障（含 3 个步骤、1 张附件）→ 前台能查到。
3. 查询日志表里能看到刚才的查询记录，统计页能看到本次查询。
