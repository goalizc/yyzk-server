# 11 - 浏览器逐屏走查报告

> 时间：2026-10-21
> 范围：客户侧 4 屏 + 后台 5 屏，真实 Chrome + 真实后端 + docker 全栈
> 方式：Playwright 走查脚本（`frontend/e2e/screen-walkthrough.spec.js`），全页截图人工过目
> 结论：**发现 4 个问题，全部已修**；三关全绿

## 1. 为什么单测之后还要走查

单测断言的是"我写的逻辑按我预期执行"，E2E 断言的是"按钮点得动、数据对得上"。
两者都不检查**页面看起来对不对**——文案读起来顺不顺、同一句话有没有重复渲染、
排序像不像人排的。这类问题只有真的看图才能发现。

本轮 4 个问题里，有 3 个单测和 E2E 都发现不了：它们不是逻辑错误，是**表达错误**。

## 3. 发现的问题与修复

### 3.1 备注框 placeholder 与报错文案完全相同（已修）

- **现象**：变更状态但没填备注时，同一句话「变更状态必须填写备注」以灰色 placeholder
  和红色 error 并排出现两遍，读起来像重复渲染坏了。
- **根因**：placeholder 被写成了"报错文案"本身。placeholder 的职责是说明**该写什么**，
  报错是说明**为什么不行**，两者不该是同一句话。
- **修复**：抽 `remarkPlaceholder` computed，按是否已选状态给两种说明
  （`仅更新备注可留空` / `如：已电话指导客户更换主刷电机，客户确认解决`）。
- **守护**：`TicketDrawer.spec.js` 新增 1 条用例，断言 `remarkPlaceholder !== remarkError`。

### 3.2 方案页第 3 步把人往"联系售后"推（已修）

- **现象**：故障 9/11/14 的解决方案第 3 步写的是「联系售后」/「返厂」，而这个系统的
  全部价值就是**让客户不用联系售后**。走到最后一步却把人推回去，等于自己否定自己。
- **修复**：种子脚本 3 处文案改为指向提交工单（`提交工单，由工程师跟进更换主刷电机`），
  已有库对应 3 条同步更新。
- **影响面**：`scripts/dev/seed_demo.py` + 现有库数据。

### 3.3 零件 `sort_order` 全为 0（已修）

- **现象**：客户侧第 2 步下拉里，动力系统和清洁系统的零件交替出现，顺序由数据库返回
  顺序决定——即"看起来随机"。
- **根因**：种子数据没写 `sort_order`，默认 0，排序全并列。
- **修复**：种子按排查习惯赋 1/2/3（动力系统在前），已有库 5 条同步。

### 3.4 工单抽屉刷新时内容闪一下、滚动跳回顶部（本轮新发现，已修）

- **现象**：`TICKET_STATUS_INVALID` 后重新拉详情，`<template v-if="detail">` 整块先销毁
  再重建，抽屉内容闪一下，滚动位置跳回顶部。
- **更严重的连带**：这条路径在 happy-dom 下会触发 Vue 内部 `Cannot read properties of
  null (reading 'type')`，表现为 **2 个 unhandled rejection**。由于用例断言本身仍通过，
  旧版测试把这当成"通过 + 噪音"放过去了。
- **根因**：`load()` 开头 `detail.value = null`。置空是为了让空态生效，但这是**用销毁换
  加载态**，代价是内容闪动 + fragment 在 teleport 里半重建。
- **修复**：`load()` 不再置空 `detail`，保留旧内容 + `v-loading` 遮罩，数据回来直接覆盖。
  首次打开时 `detail` 本来就是 `null`，空态行为不变。
- **守护**：新增 1 条用例，让第二次请求挂起，断言请求在途时 `detail` 仍非空。
- **反向验证**：把 `detail.value = null` 加回去，新用例立刻失败（`expected null not to be
  null`），同时旧用例复现 `null.type` 崩溃——因果链完整，不是巧合。

> 这条是本轮技术上最有价值的发现：**"测试通过但过程有 unhandled error"是可观测的缺陷
> 信号**，不应被当作测试环境噪音略过。修完之后用例数从 103 变 104，未处理错误从 2 变 0。

## 4. 走查还发现但不修的一项

**「故障列表解决次数全为 0」**——查证后确认**不是 bug**：

- `query_logs` 里 `resolved=true` 确有记录，同步逻辑经受控实验验证正常（0 → 1，实验数据已回滚）
- `faults.resolved_count` 是**历史累计**，而开发期数据库被重灌过，累计值随之归零
- 属开发期数据漂移，生产环境不会出现。要修只能"编造历史数据"，那才是真问题

## 5. 走查脚本的去留

**保留，但默认不跑**：

- 全流程打 `@walkthrough` 标签，`playwright.config.js` 按 `E2E_MODE` 决定 `grep`/`grepInvert`
- `npm run e2e` 只跑主链路（5.4s），`npm run e2e:walk` 才跑走查（约 1 分钟）
- 理由：走查是**人工过目**的辅助工具，不是回归门槛。放进 CI 只会让每次提交都慢一分钟，
  而它真正的价值在"改了样式/文案之后重新看一眼"

### lint 豁免说明

走查脚本的 `console.log` 是它的**输出通道**（分辨率、行数、错误字段数），不是遗留调试
代码。已给 `e2e/screen-walkthrough.spec.js` 单独 `no-console: off`，其余测试文件仍受限。

## 7. 踩坑记录（供后续参考）

- **改前端必须重建镜像**：前端产物打进镜像，`docker compose up -d` 不感知源码变化。
  表现是"改了没生效"，会白排查半小时。验证法：`curl -s http://localhost/ | grep -o
  'assets/index-[^"]*'` 与本地构建文件名比对
- **Playwright 的 `outputDir` 不能放 `/tmp`**：本机 `/tmp` 是 10MB tmpfs，截图写不进去，
  且 `page.screenshot` 失败时**不报错**（用例"通过"但零张图）。已改用仓库内 `.e2e-output/`
- **截图需 `animations: 'disabled'` + 重试 + `existsSync` 显式确认落盘**，
  否则会出现"静默成功"
- **`new URL().pathname` 会把中文路径百分号编码**，取目录必须用 `fileURLToPath`
- **`.el-select-dropdown:visible` 会命中上一个已关闭但仍在 DOM 的下拉**，
  多下拉页面应用 `aria-controls` 精确对应
