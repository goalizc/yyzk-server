## 6. 逐项缺口详述（按修复优先级）

### P0-1 初始化脚本里的管理员密码是假哈希 ✗

`schema.sql:147` 的 `$2b$12$N1mQeX7Yk9Z8V7U6T5S4R3Q2P1O0N9M8L7K6J5H4G3F2E1D0C9B8A` 是**手工编造的占位串**（bcrypt 需 60 字符且为真实算法输出，此串长度与字符分布均不符，且文件自己注释「占位」）。

后果链：容器首次启动 → Postgres 执行 `schema.sql` → 写入假哈希 → 任何人用 `admin/admin123` 登录均返回 401 → `TC-50 干净环境启动` 必失败 → 验收表「默认 admin 密码已修改」无法执行。

WBS B-02 承诺了「默认 admin 账号初始化脚本」，但**该脚本不在包内**。修复：提供一个 `init_admin.py`，在 backend 启动时用 passlib 生成真实哈希 upsert 到 `users`，并把 `schema.sql` 里的 INSERT 删掉。

### P0-2 工单「是否上门」字段无处落库 ✗

`POST /api/tickets` 收 `need_on_site`（API:247），`tickets` 表无此列（schema:106-121），PRD F-5 与页面 P-03:121 都要求该字段。ORM 若按 Pydantic 直接映射会报 `unknown column`，若忽略则静默丢数据 —— 两种结果都不能接受。

修复：`ALTER TABLE tickets ADD COLUMN need_on_site BOOLEAN NOT NULL DEFAULT FALSE;`，并补契约字段与 TC-11 断言。

### P0-3 统计看板的「未命中词」没有数据来源 ✗

完整链路推演：

1. 客户侧只有三级下拉（P-01 布局，无输入框）；
2. `GET /api/faults` 强制 `product_id` + `part_id` 双必填（API:131-132）；
3. 唯一的写日志点是「打开故障详情」（API:147），此时 `fault_id` 必有值，`hit` 必然为 true，且 `raw_query` 无值可填；
4. 列表为空（真未命中）时**没有任何一次写日志动作** —— 前端只是渲染空列表。

结论：`hit=false AND raw_query IS NOT NULL` 的记录**永远不会产生**，`GET /api/admin/stats/missed` 恒返回空数组，验收标准「未命中日志和解决率在后台可见」（路线图:66）与「后台能看到未命中词」（章程 §4）无法达成。

修复（三选一，需产品拍板）：
- **A 最小改动**：在 P-01 故障列表为空时，前端调一个 `POST /api/query-logs {product_id, part_id, hit:false}`，`raw_query` 记为 `"{产品名}/{零件名}"`，看板按「空结果组合」统计 —— 语义从「未命中词」变为**未命中组合**，文案需同步改。
- **B 加输入框**：P-01 增一个选填关键词框，仅用于日志不参与检索，`raw_query` 有真实来源。
- **C 砍功能**：一期去掉未命中词，看板只留三卡 + TOP10，二期随自然语言问答一起做（路线图 2.4 就规划了搜索）。

**推荐 B 或 C**：A 会让「未命中词」名不副实。

### P0-4 工单详情缺接口 ✗

P-12 有「详情抽屉：完整上下文 + 处理备注」（PRD F-10 / 页面清单），但契约只有列表 `GET /api/admin/tickets`（API:259），返回字段（API:269-278）不含 `description`、`remark`、`need_on_site`。抽屉打不开。

修复：新增 `GET /api/admin/tickets/{id}`，返回 ticket 全字段 + 关联产品/零件/故障名称 + 该故障的方案快照链接。
