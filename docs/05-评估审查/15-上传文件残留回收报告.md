# 15 · 上传文件残留回收（用户报障：移除后文件仍在机器上）

> 报障时间：2026-10-21
> 报障描述：「测试之后我点了页面上的移除，页面上功能是没有问题的，图片从页面上移除了，
> 但文件本身却还在机器上……时间久了这些残留的上传文件肯定会塞满硬件」
> 处理结论：**已修复并端到端验证**

---

## 1. 问题性质

用户描述准确，这是**设计缺口而非实现缺陷**：系统从来没有"删除文件"这条路径。

`POST /api/admin/upload` 上传即落盘，而引用要等 `PUT /api/admin/faults/{id}`
保存时才写进 JSONB。前端"移除"按钮的实现是：

```js
@click="$emit('update:modelValue', null)"   // 只清空表单值
```

**没有任何后端调用**。整个后端也没有一处删除文件的代码（`grep unlink` 只命中
临时文件 `.part` 的清理）。

---

## 2. 受影响场景盘点

不能只修"点移除"这一处，因为残留有多条来源：

| 场景 | 能否即时删除 | 本次处理 |
|---|---|---|
| 上传后点"移除" | ✅ 可以 | 前端调删除接口 |
| 上传后直接关页面 | ❌ 后端不知道文件没人要 | 靠定期扫描兜底 |
| 编辑时换了另一张图 | ❌ 后端只收到新数组，无法判断是替换还是手滑 | 靠定期扫描兜底 |
| 保存时校验失败 | ❌ 整个表单没提交 | 靠定期扫描兜底 |
| 删了步骤但不保存 | ❌ 无法区分"撤销"与"真删" | 靠定期扫描兜底 |

**结论：单靠"主动删除"解决不了，必须有兜底回收。** 这是本次做两套机制的原因。

### 2.1 为什么 `removeStep` / `removeAttachment` 故意不删

`FaultEdit.vue` 删除步骤、删除附件时**只改数组，不调删除接口**。原因是存在撤销场景：
用户点删除后可能不保存就离开（或点取消），此时文件可能仍在别的版本里用着，
删了就再也找不回来。代码里已写明这个取舍，避免后人"顺手补上"造成数据丢失。

---

## 3. 实现

### 3.1 主动删除：`DELETE /api/admin/upload`

新增端点，前端移除时调用。三条安全约束：

**① 只接受本系统生成的文件名**

```python
_UPLOAD_NAME_RE = re.compile(
    r"^\d{8}-[0-9a-f]{8}\.(?:" + "|".join(sorted(ext.lstrip(".") for ext in ALLOWED_EXTENSIONS)) + r")$"
)
```

用**格式白名单**而非 `Path(url).name` 截断。后者能挡 `../x`，但挡不住畸形输入在
不同平台的解析差异；白名单的优点是"看起来不像我们生成的"一律拒绝，不需要枚举穿越变体。
扩展名从 `ALLOWED_EXTENSIONS` 动态拼，避免两处白名单不同步。

**② 不允许删仍被引用的文件**

```python
if referenced_by_fault(db, {name}):
    raise BusinessError("UPLOAD_IN_USE", "该文件仍在故障方案中使用，无法删除", 409)
```

同一张图可能被复用到多条方案。删了另一条方案就破图且无任何提示——
这种静默损坏比多占几 MB 磁盘严重得多。

**③ 文件不存在视为成功**

删除是幂等操作：两个标签页同时点移除、或清理任务刚跑过，都会出现"文件已不在"。
报 404 会让用户看到毫无意义的错误。

### 3.2 兜底回收：`backend/app/services/upload_cleanup.py`

引用藏在 `faults` 的两个 JSONB 字段里，没有独立附件表，因此只能全表扫比对：

- `solution_steps[].image_url`
- `attachment_urls[].url`

取 URL 的 basename 收成集合，与磁盘文件名比对，磁盘有而集合无者为孤儿。

> 不拼 `LIKE` 的原因：文件名是随机 16 进制串，`%` 通配对 JSONB 无法走索引，
> 且 `_` 会被当通配符。当前 `faults` 是千级规模，全表取两列约百毫秒。
> 到十万级再考虑建 `upload_files` 引用表。

### 3.3 三层安全护栏

清理不可逆，所以：

| 机制 | 默认 | 作用 |
|---|---|---|
| dry-run | 开启 | 不显式 `apply=True` 绝不删文件 |
| 年龄下限 | 60 分钟 | 保护"刚上传、还没保存"的图 |
| 比例闸门 | 50%（目录 ≥10 文件时生效） | 待删过半判定为扫描异常，拒绝执行 |

第二层最容易被忽略但最危险：清理任务若恰好在"用户上传完成、正在填表"时运行，
用户点保存就会看到图片 404。

### 3.4 运维脚本：`deploy/scripts/cleanup-uploads.sh`

```bash
./scripts/cleanup-uploads.sh                 # 预演，只报告
./scripts/cleanup-uploads.sh --apply         # 真正删除
./scripts/cleanup-uploads.sh --min-age 1440  # 只清 24 小时前的
```

退出码：`0` 正常 / `1` 容器未运行 / `3` 被比例闸门拒绝。

## 4. 自审中发现并修复的缺陷

### 4.1 比例闸门会在最需要它的场景下失效

第一版无条件按比例判定，测试立刻暴露问题：

```
待删 1/1 个文件，超过比例上限 50%，疑似引用扫描异常，已拒绝执行
```

目录里只有 1 个孤儿文件时比例就是 100%，任务被拒——而**单文件残留恰恰是最常见的
清理场景**（用户报障的那张图就是单独一个）。

修改：闸门仅在 `len(files) >= RATIO_GATE_MIN_FILES`（10）时生效。
理由是比例在小目录下没有统计意义，而闸门真正防的是"扫描失效导致批量误删"，
那必然是规模化现象。并补了 `test_sweep_small_dir_not_blocked_by_ratio` 锁住这个行为。

### 4.2 反向验证时改错了文件

按流程做"回退修复，确认用例失败"的反向验证。第一次把缺陷注入到
`upload_cleanup.py`，结果测试全绿——因为引用保护逻辑在 `admin.py` 里，
注入点根本不对。

**这恰好证明反向验证本身是必要的**：如果只跑正向测试，"注入缺陷仍全绿"会被
误读成"用例没用"，实际是用例压根没被触发。改注入到 `admin.py` 第 430 行后，
用例如期失败（返回 200 而非 409）。

### 4.3 测试数据缺 `title` 字段

`faults.title` 是 NOT NULL，构造测试数据时漏了，`IntegrityError`。
属测试自身问题，补上即可，未改动产品代码。

## 6. 残留与建议

| 项 | 说明 |
|---|---|
| 用户那张测试图尚未删除 | 目录里仍留着 `20261021-588b1ba9.png`。它是用户测试数据，**未擅自删除**，执行 `./scripts/cleanup-uploads.sh --apply --min-age 0` 即可回收 |
| 定时任务未配置 | 脚本已就绪，cron 需在真机配置（见运维脚本说明 §4），沙箱内不配 |
| 十万级规模需换方案 | 当前全表扫 JSONB，千级规模百毫秒。到十万级应建 `upload_files` 引用表 |
| 磁盘写满未区分 | 目录可写但磁盘满时 `ENOSPC` 会归到 503，语义可接受但日志应能区分 |
