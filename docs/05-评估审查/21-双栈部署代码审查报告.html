三、发现清单

CRITICALC-01 seed 脚本的「API 目标」与「清库目标」可跨栈错配，默认路径下会清空生产库

位置：scripts/dev/seed_demo.py · scripts/dev/demo_inventory.py（159504a 新增的 _compose_cmd() / read_env()）、README.md 测试栈段落

  • 现象：--base-url 决定演示数据写到哪个栈；SEED_COMPOSE_PROJECT / SEED_ENV_FILE 决定 --reset 的 TRUNCATE 在哪个 db 容器执行。两者各自独立，没有任何一致性校验。
  • 实测证据：在仓库根执行 docker compose -f deploy/docker-compose.yml config 得 name: deploy，与 deploy.sh（所有 compose 命令不带 -p）的生产项目名一致 → 漏设 SEED_COMPOSE_PROJECT 时，psql() 一定落在生产 fault-db；且 read_env() 默认读 deploy/.env（DB_USER=fault / DB_NAME=fault_db），连接会成功。
  • 最易触发的复现路径（README 教的测试栈命令，只改了端口）：
    python scripts/dev/seed_demo.py --reset --activity --base-url http://127.0.0.1:8080
# → psql() 在 deploy 项目的 fault-db（生产库）执行 TRUNCATE
# → login() / seed_via_api() 把数据写进 127.0.0.1:8080（测试栈）
  • 影响：生产业务数据被清空、测试栈得到演示数据；--reset 是破坏性操作，脚本无二次确认、无目标栈提示。这是本次审查中唯一能直接造成不可逆数据丢失的缺陷。
  • 建议：① 在 psql() / --reset 前加断言：--base-url 端口 ≠ 80 且 SEED_COMPOSE_PROJECT 为空 → 拒绝执行；② 执行前打印「即将清空：项目名 / DB_NAME / DB_USER」并要求确认；③ README 把三个 SEED_* 写成必填并加显式警告；④ 更彻底的做法是让清库目标从 --base-url 反推，而非依赖环境变量。
CRITICALC-02 运维脚本族完全未随双栈参数化，在「测试栈语境」下执行会打到生产栈

位置：deploy/scripts/backup.sh:71-72,112-113 · restore.sh:69-76,93 · harden.sh:195-219 · enable-https.sh:120 · cleanup-uploads.sh:54,69 · cleanup-audit.sh:59 · install-cron.sh:84

  • 现象：这批脚本里的 docker compose ... 都不带 -p，容器名 / 库名 / 路径全部硬编码生产值：
    restore.sh:  docker cp "$DB_FILE" fault-db:/tmp/.restore_probe.dump
             docker compose exec -T db pg_restore ...      # 默认项目 deploy
             docker compose stop backend                    # 停的是生产后端
backup.sh:   grep -q "fault-db" ; tar ... data/uploads     # 不认 DATA_DIR
harden.sh:   psql -U fault -d fault_db                      # 测试栈是 fault_test/fault_test
cron:        cd $DEPLOY_DIR && ./scripts/cleanup-uploads.sh --apply   # 只清生产
  • 实测证据：生产项目名 deploy、测试 fault-test，两者不同 → 这些脚本永远碰不到测试栈。
  • 影响：① 在测试栈上执行 restore.sh 会把备份灌进生产库并停生产后端（数据覆盖风险）；② 测试栈的上传残留与 audit_logs 永不回收，单机双栈磁盘增长翻倍；③ harden.sh 在测试栈同步密码必然失败；④ 见 M-01 的功能失效。
  • 建议：给运维脚本族统一引入 STACK_PREFIX / DATA_DIR 并在所有 compose 调用加 -p "$STACK_PREFIX"；restore.sh 的 docker cp 目标容器名必须参数化并在执行前打印目标栈。若短期不改造，至少在 README 明确标注「这些脚本只服务生产栈」。
MAJORM-01 enable-https.sh 因 ports 参数化而失效（实测必然报错退出）

位置：deploy/scripts/enable-https.sh:120-126（159504a 改了 compose 的 ports 行，未同步此脚本）

  • 证据：脚本用 re.subn(r'^(\s*)-\s*"80:80"\s*$', ...) 找 80 映射并追加 443。实测对当前 compose 匹配数 = 0；实际 ports 行是 - "${HTTP_BIND:-0.0.0.0}:${HTTP_PORT:-80}:80"。n == 0 即 sys.exit("[ERROR] 在 compose 里找不到 ports 的 80 映射") 并回滚。
  • 影响：HTTPS 启用功能完全不可用，且报错信息指向「找不到 80 映射」，与真实原因（变量化写法）不符，排障成本高。
  • 建议：正则改为匹配含 ${HTTP_PORT:-80}:80 的变量形式，或不依赖 80 行、直接在 ports 段追加 443 映射。
MAJORM-02 deploy.sh 健康验证 URL 硬编码 80，自定义端口时误报部署失败

位置：deploy/deploy.sh:401,416-424,501；08178a4 把端口占用检查参数化为 ${HTTP_PORT}，却漏了这里

  • 现象：LOCAL_URL="http://127.0.0.1" 不带端口，第 8 步的四项检查（/health、SPA 首页、API 401、登录接口）全打 80，最后打印的访问地址也不带端口。
  • 影响：生产 .env 里 HTTP_PORT≠80 时，服务本身正常但四项检查全部失败 → FAILED>0 → exit 1 报「部署失败」，并给出错误访问地址。与本次「端口可配置」的改造目标直接冲突。
  • 建议：改为 LOCAL_URL="http://127.0.0.1:${HTTP_PORT}"；HTTP_BIND 非 0.0.0.0 时 127.0.0.1 仍可用，无需额外处理。
MAJORM-03 测试栈健康检查是假阳性：/health 根本不经过后端

位置：deploy/deploy-test.sh:85-92 + deploy/nginx.conf:143-146

  • 证据：nginx 配置 location /health { return 200 "ok\n"; }，是网关自己直接返回，不查后端、不查 DB；nginx 容器 healthcheck 同样只 wget 自己。deploy-test.sh 仅 curl -fsS http://127.0.0.1:${HTTP_PORT}/health 成功就打印「完成」。
  • 影响：后端未启动、迁移失败、DEBUG=true 导致启动异常、管理员初始化失败时，测试栈照样报部署成功。对比 deploy.sh 第 8 步还验证了登录接口与 API 401，测试栈的验证强度明显不足——而测试栈恰恰最需要验证「新库 + 全新迁移」是否真的可用。
  • 建议：至少补 GET /api/health（后端 DB 连通性）与登录接口 200；可直接复用 deploy.sh 的 check_code 四项。
MAJORM-04 cron 只注册一条、只清生产栈，测试栈上传残留与审计日志永不回收

位置：deploy/scripts/install-cron.sh:84 → cleanup-uploads.sh:54,69 / cleanup-audit.sh:59

  • 现象：cron 条目是「cd $DEPLOY_DIR && ./scripts/cleanup-uploads.sh --apply; ./scripts/cleanup-audit.sh --apply」，两个脚本内部 docker compose 都不带 -p，且 cleanup-uploads.sh 只认 data/uploads。
  • 影响：测试栈 data-test/uploads 与 audit_logs 永不清理；单机双栈长期运行会持续吃磁盘。另外 install-cron.sh 用固定 marker 去重，无法为第二个栈再注册一条。
  • 建议：cron 对两个栈各跑一次（传 -p 与 DATA_DIR），或明确声明测试栈为临时栈、不纳入清理并限制其生命周期。
MAJORM-05 双栈密钥隔离只有注释约定，没有运行时校验（token 可跨栈互认）

位置：deploy/deploy-test.sh:16-33（只校验 STACK_PREFIX / HTTP_PORT / DATA_DIR）、.env.test.example 注释

  • 现象：不校验 JWT_SECRET 是否与生产不同。若用户 cp .env .env.test 只改端口与前缀，两栈共享同一密钥；JWT 里无 iss/aud 声明、两库 admin 的 user_id 都是 1 → 生产签发的 token 可直接登录测试后台，反之亦然。
  • 现状：实测当前两份 env 的 JWT_SECRET/DB_PASSWORD/DB_NAME 确实不同，问题未触发；但这属于「靠人记住」的隔离，与提交说明「独立 JWT 密钥」的承诺不匹配。
  • 建议：deploy-test.sh 启动时比对 .env 与 .env.test 的 JWT_SECRET、DB_PASSWORD、DB_NAME，任一相同即拒绝启动。
MAJORM-06 测试栈缺少 harden.sh 等价保护，模板占位符可直接带病启动

位置：deploy/deploy-test.sh:16-33；对比 deploy/deploy.sh:158-170

  • 现象：测试脚本只检查 .env.test 存在与 3 个键非空，不检测占位值。用户按 README cp -n .env.test.example .env.test 后若忘记改，JWT_SECRET=请改成独立的随机长字符串、DB_PASSWORD=请改成至少16位强密码 会被直接拼进 DATABASE_URL（含非 ASCII 中文），psycopg2 解析异常，报错离根因很远；ADMIN_INIT_PASSWORD 同样是占位符。生产侧有 harden.sh 自动替换占位/弱值，测试侧没有。
  • 建议：复用 harden.sh，或在 deploy-test.sh 开头加轻量占位符检测，命中即拒绝并打印 openssl rand -hex 32 等生成命令。
MAJORM-07 测试栈 db 512 MiB 与默认 45 连接池组合存在 OOM 风险

位置：deploy/docker-compose.test.yml:6-8、docker-compose.yml:84-85（默认 DB_POOL_SIZE=20/DB_MAX_OVERFLOW=25，.env.test 未覆盖）

  • 实测渲染：测试 db mem_limit: 536870912（512 MiB），backend 仍按 45 连接配置。生产 db 是 1 GiB，压测报告记录「db 内存峰值约 300 MiB（限 1 GiB）」。
  • 影响：45 个 PG backend 进程 + shared_buffers 128 MB，512 MiB 余量极小；灌演示数据或做并发测试时 db 容易被 OOM killer 杀掉，且现象会误判成「测试栈不稳定」。
  • 建议：在 .env.test 加 DB_POOL_SIZE=5 / DB_MAX_OVERFLOW=5（测试栈限定本机、并发诉求低，最划算），或把测试 db mem_limit 提到 1g。
MAJORM-08 DATA_DIR 防串目录校验可被 .. 绕过，宣称的「撞生产目录直接失败」未兑现

位置：deploy/deploy-test.sh:39-44（08178a4 提交说明原文：「缺键或撞生产目录时直接失败」）

  • 现象：用字符串前缀比较 "$DEPLOY_DIR/data"。当 DATA_DIR=./data-test/../data 时，DATA_PATH=$DEPLOY_DIR/data-test/../data，既不匹配 .../data 也不匹配 .../data/"*，校验通过；而路径实际解析就是 deploy/data → 测试栈挂载生产 PG 数据目录与上传目录。
  • 影响：虽然是「误配才触发」，但后果是生产数据被测试栈直接读写，且校验给不出任何提示。
  • 建议：DATA_PATH="$(realpath -m "$DATA_PATH")" 规范化后再比较；并与生产 .env 的 DATA_DIR 规范化结果做交叉比对。
MINORm-01 .gitignore 未同步支持任意 env 文件，与提交说明不符
  • 08178a4 说明写「gitignore 支持任意 data*/env* 目录」，实测 .gitignore 只把 deploy/data/ + deploy/data-test/ 合成 deploy/data*/；环境变量段仍是 .env / deploy/.env / deploy/.env.test 三条精确项。用户新建 deploy/.env.staging、.env.test.local 时明文密码会被提交。.dockerignore 已正确用 deploy/.env*。
  • 建议：补 deploy/.env*，并用 !deploy/.env.example / !deploy/.env.test.example 保留模板。
MINORm-02 项目名与 STACK_PREFIX 不一致；双栈各构建一份完整镜像
  • 实测生产项目名 name: deploy（deploy.sh 不带 -p），测试 name: fault-test，但容器名用 STACK_PREFIX 生成 fault-*。隔离成立，可 docker compose ps 看到的是 deploy、文档写的是 fault-*，排障易混淆。
  • 另外两栈各自 build 出 deploy-backend 与 fault-test-backend 两套镜像，4C8G 单机磁盘翻倍；改代码后只 build 其中一个栈会造成两栈代码版本漂移。
  • 建议：deploy.sh 统一加 -p "$STACK_PREFIX"；README 说明双栈镜像各自独立、改代码需分别 rebuild。
MINORm-03 .dockerignore 的 deploy/.env* 把模板一起排除了
  • .env.example / .env.test.example 也匹配该模式。模板本就不需要进镜像，无害；但注释写「运行期数据与本地环境」，语义上把模板算作「本地环境」，容易让后来人误以为模板被故意隐藏。
  • 建议：改成 deploy/.env + deploy/.env.* 并显式 !deploy/.env*.example。
MINORm-04 nginx.conf 是双栈共享的单文件，测试栈改配置会直接影响生产
  • 实测两栈都把 deploy/nginx.conf 只读挂到 /etc/nginx/conf.d/default.conf。为测试栈调整任何规则（如放开 /api/docs、改 client_max_body_size）会立刻作用到生产，且需两个栈各自重启 nginx 才生效。
  • 建议：测试栈在 override 里换挂 nginx-test.conf，或至少在 README 标注这一共享面。
MINORm-05 DEBUG=true + 「改成 0.0.0.0」的文档引导缺少安全警告
  • .env.test 实测 DEBUG=true（开放 /api/docs、/api/openapi.json，nginx 的 location /api/ 会代理），默认 HTTP_BIND=127.0.0.1 已缓解。但 .env.test.example 与 README 都写「需要局域网访问时改成 0.0.0.0」，未提示这会把接口文档与测试管理员账号一起暴露到局域网。
  • 建议：两处补一句：改 0.0.0.0 前先把 DEBUG 改回 false。
MINORm-06 两个 seed 脚本的管理员口令变量名不一致
  • seed_demo.py:88 读 ADMIN_INIT_PASSWORD；demo_inventory.py 头部注释用 ADMIN_PASSWORD；README 测试栈段落写的是 ADMIN_INIT_PASSWORD。照 README 跑 demo_inventory.py 时口令取不到会回退到 .env（生产口令）→ 登录 8080 测试栈失败。
  • 建议：统一变量名，或让两个脚本都接受两个别名。
MINORm-07 deploy-test.sh 的 chown 方案与生产不一致，且依赖镜像已存在
  • deploy-test.sh:59-60 用 docker run --rm -u 0 ... nginx:1.25-alpine chown ...，deploy.sh:251 用 docker compose run --rm --no-deps -u root -T backend sh -c "chown ... && chmod 775 ..."。差异：① 前者在 build 之前执行，全新机器若镜像未提前拉取会触发额外拉取；② 前者不做 chmod 775，目录属主正确但缺写位时测试栈仍会上传失败；③ 两套逻辑分叉，改 uid 容易漏改一处。
  • 建议：统一走已支持 DATA_DIR 的 prepare-storage.sh，或复用生产侧容器内 chown。
