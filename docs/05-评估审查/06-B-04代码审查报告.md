## 2. Round 1：发现的问题

### Major

**M1 附件/步骤配图地址未校验，可写入 `javascript:`（XSS）**

- 位置：`backend/app/schemas/fault.py`（`AttachmentMeta.url`、`SolutionStep.image_url`）
- 取证：POST `/api/admin/faults` 带
  `attachment_urls[0].url = "javascript:alert(1)"`、`solution_steps[0].image_url = "javascript:alert(document.cookie)"`
  → **201 且原样写库**。前端若用 `<a :href>` / `<img :src>` 渲染，点击即执行脚本。
- 依据：设计文档明确"运营录入视为不可信输入"，禁止 `v-html` 只能挡住文本，挡不住 URL 协议。
- 风险等级：Major（存储在库里的持久型 XSS，只要运营账号被利用或导入脏数据就生效）。

### Minor

| 编号 | 位置 | 问题 |
|---|---|---|
| m1 | `backend/tests/conftest.py` | SQLite 未开启 `PRAGMA foreign_keys`，`ON DELETE SET NULL / RESTRICT` 在单测里根本没生效，等于这部分从未被验证 |
| m2 | `backend/app/api/public.py` 的 `/api/query-logs` | 只校验产品、零件各自存在，不校验零件是否属于该产品。错配会把"产品+零件"组合写进日志，污染看板的未命中分组口径 |
| m3 | `backend/tests/` | 缺关键回归：`q` 超长（列表 50 / 详情 100）、404 分支不应写日志、附件地址安全 |
| m4 | `backend/app/api/public.py` 的 `/api/faults/{id}` | 契约要求 `query_log_id` 幂等反馈，但 id 是自增的，任何人都能凭猜到的 id 把 `resolved=true` 刷给别的故障，直接影响"自助解决率"这个 KPI；且详情接口未限流，可被刷 `view_count` |

## 3. Round 2：修复

| 项 | 修法 | 验证 |
|---|---|---|
| M1 | 新增 `_validate_media_url()`：只允许 `/uploads/`、`http://`、`https://` 前缀，`javascript:`/`data:`/协议相对 `//` 一律 422 | 复验：两种攻击地址均返回 422「图片/附件地址必须是 /uploads/ 或 http(s) 链接」；`/uploads/a.pdf` 仍 201 |
| m1 | conftest 在 `connect` 事件里执行 `PRAGMA foreign_keys=ON` | 老测试 38 条不受影响；新增的"删故障后工单置 NULL"用例才真正执行到外键 |
| m2 | 日志上报增加 `part.product_id != product_id` → 400 `PART_PRODUCT_MISMATCH`（契约已登记码） | 单测覆盖；真栈验证不存在零件返回 404 |
| m3 | 补 7 条回归测试 | `pytest` 81 passed |

m4 **未改代码**：契约 §4 明确要求"不允许省略 query_log_id 的兼容分支"，加时效/IP 绑定属于契约变更，
需要和产品确认后再动。记录建议见 §5。

## 4. Round 3：重审（回归面）

| 检查点 | 结论 |
|---|---|
| URL 校验是否误伤正常上传 | 上传接口返回 `/uploads/...`，命中白名单；大小写变体（`JavaScript:`、`HTTP://`）同样被拒 |
| 空 `image_url` / 空附件地址 | 前者按 `null` 存储，后者报「附件地址不能为空」 |
| 新增校验是否影响已有数据 | 库中无历史脏数据，且只在写入路径校验，读路径不受影响 |
| 未命中日志新增 400 分支是否影响前端 | 前端只按级联结果上报，不会产生错配；错误码已在契约登记 |
| 契约符合性 | 9 个端点状态码、字段名、`+08:00`、`{detail, code}` 全部对齐；未新增未登记错误码 |
| 性能 | 列表与详情均为单次查询（`fault_count` / `attachment_count` 不产生 N+1）；`view_count` 用原子 `UPDATE ... + 1` 避免并发丢更新 |

## 5. 保留风险与建议（未改）

1. **反馈可被猜 id 刷量**（m4）：建议后续给 `query_logs` 增加"仅允许创建后 N 小时内反馈"或绑定 IP+UA 的校验；
   在此之前，看板的 `resolved_count` 只能作为趋势参考，不能当审计数据。
2. **详情接口无限流**：`view_count` 可被脚本刷高，进而影响客户侧"按浏览量排序"的展示。
   建议 Nginx 对 `~ ^/api/faults/\d+$` 加 `limit_req`（如 60r/m）。
3. **附件外链**：目前允许 `http(s)://` 外部地址，若担心内容不可控，可进一步收窄为仅 `/uploads/`。
