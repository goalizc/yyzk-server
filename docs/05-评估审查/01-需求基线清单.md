# 需求基线清单（Requirements Baseline）

> 用途：把散落在章程 / PRD / 用户故事 / 页面清单 / 路线图里的需求，收敛成**唯一编号、可逐条比对**的基线。
> 提取日期：2026-10-20
> 基线版本：v1.0（对应施工包现有文档，未做任何需求新增）
> 编号规则：`R-领域-序号`，一经分配不再复用。

## 7. 需求侧冲突清单（需产品裁决，共 6 项）

> **状态更新（2026-10-20）**：以下 6 项已在 v1.1 全部裁决并落到文档，裁决结论与依据见 `04-修复记录.md` §2。
> 本表保留原始冲突描述，仅用于追溯"为什么改"。
> - C-01 → 加选填关键词筛选框，未命中统计真实可产
> - C-02 → 统一按查询日志口径，3 个月 ≥ 30%，首月 ≥ 20% 为观察值
> - C-03 → 详情返回 `query_log_id`，反馈必须回传
> - C-04 → 新增 `ticket_status_logs` 表，操作人从 token 取
> - C-05 → 外键改 RESTRICT，删除前显式校验并返回 409
> - C-06 → 一期不含用户管理，仅保留"修改自己密码"


| 冲突号 | 冲突内容 | 甲方说法 | 乙方说法 | 影响 |
|---|---|---|---|---|
| C-01 | 「未命中词」数据从哪来 | PRD F-11 + 验收标准要求看板可见未命中词 | 一期客户侧只有三级下拉，无任何输入框；`GET /api/faults` 要求 product_id 与 part_id **同时必填** | 该功能 100% 无法产出数据 |
| C-02 | 自助解决率口径 | 章程：上线 3 个月 ≥ 30% | 路线图：上线 1 个月 ≥ 20%；且 `resolved_count/view_count` 与 `query_logs.resolved` 是两套算法 | 验收时无法判定是否达标 |
| C-03 | 反馈如何定位到日志 | US-05 AC3 要求写 `query_logs.resolved=true` | 反馈接口仅收 `{resolved}`，无 log_id / 会话标识 | 无法精确更新，只能猜「最近一条」 |
| C-04 | 「流转时记录操作人」落在哪里 | PRD F-10 明确要求 | `tickets` 只有 `assignee_id`（处理人），无 `operator`、无变更历史表；API 只收 status + remark | 要求无法落地 |
| C-05 | 产品删除策略 | PRD F-7：有关联故障时禁止删除 | `parts.product_id ON DELETE CASCADE`，删产品会静默级联删零件 | 数据可能被误删且无提示 |
| C-06 | 一期是否含用户/权限管理 | PRD §2 列出「系统管理员：管理用户账号、权限」 | 无故事、无页面、无接口；路线图放在三期 3.5 | 范围边界不清 |
