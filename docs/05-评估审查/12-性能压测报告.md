# 性能压测报告（TC-70 / TC-71）

> 范围：客户侧两个核心读接口（故障列表、故障详情），即客户自助排查时唯一的高频路径。
> 目标机器：单机 4 核 8G（与架构设计 §7 的部署基线一致），全 Docker Compose。
> 本篇所有数字均为本机实测，非估算。

## 1. 验收口径

| 用例 | 要求 | 判定方式 |
|---|---|---|
| TC-70 | 列表 / 详情接口 P95 < 500ms | 100 并发混合场景，按真实排序取百分位 |
| TC-71 | 100 并发持续 10 分钟无 5xx | 逐请求记状态码，5xx 与网络异常一律计为失败 |

「无 5xx」不含 4xx：详情接口对已下架故障返回 404 属正常业务响应。

## 2. 压测环境与数据

| 项 | 值 |
|---|---|
| 部署 | Docker Compose 4 容器（nginx / frontend / backend / db） |
| 数据库 | PostgreSQL 15-alpine，`max_connections=100` |
| 应用 | uvicorn + 1 worker（同步 def 路由 → anyio 线程池，默认 40 线程） |
| 入口 | `http://127.0.0.1`（经 nginx 反代，非直连 backend） |
| 数据量 | faults 50,006 行；query_logs 500,030 行；parts 2,500 行 |
| 数据形态 | 每个零件下 18 条故障（最多 22），90% 已发布，贴近真实知识库 |

数据由 `scripts/dev/seed_pressure.py` 生成，全部在库内用 `generate_series` 批量构造，5 万故障 + 50 万日志耗时约 78 秒。压测数据带 `PRESSURE_` 前缀，`--clean` 可精确清除且不影响演示数据。

### 场景配比

| 接口 | 占比 | 说明 |
|---|---|---|
| `GET /api/faults` | 55% | 三级级联后的列表，一半带关键词 |
| `GET /api/faults/{id}` | 30% | 详情，每次写 1 条 query_log + 自增 view_count |
| `GET /api/health` | 15% | 纯净对照，只执行 `SELECT 1` |

单独放 15% 的健康检查是有意的：它几乎不做业务逻辑，一旦它也变慢，就能立刻判定瓶颈在链路排队而非某个 SQL。

## 3. 关键结论

### 3.1 首轮压测直接失败，暴露了三个真问题

第一轮按 compose 初始配置（backend `cpus: 1.0` + `--workers 2`，连接池默认 5+10）跑 100 并发，结果：

```
总请求 6577   有效 4583   吞吐 10.8 req/s
延迟   P50 17.8ms  P95 691.5ms  P99 1497ms  max 30004ms
状态   {'200': 4583, 'network': 1994}
```

1994 个请求读超时，日志里刷满同一个异常：

```
sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached,
connection timed out, timeout 30.00
```

#### 问题一：连接池容量不足，且根本调不了（已修）

`config.py` 里 `db_pool_size` / `db_max_overflow` 是可配置项，但 `docker-compose.yml` 的 backend `environment` 没有透传这两个变量，Docker 不会把宿主机环境变量塞进容器。**运维想调连接池，改 .env 完全无效**，只能改代码默认值。

已修：compose 补上 `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` / `DB_POOL_TIMEOUT` / `DB_POOL_RECYCLE` 透传，`.env.example` 补说明。

同时把 `DB_POOL_TIMEOUT` 默认从 30s 改为 10s。原值 30s 意味着池满后请求会干等 30 秒，而客户端往往 30 秒就先超时了，日志里只剩一堆没有上下文的 `ReadTimeout`。快速失败比慢慢等死更容易定位。

#### 问题二：`--workers 2` 与 `cpus: 1.0` 矛盾（已修）

1 核容器里跑 2 个 uvicorn 进程，实测比 1 个进程更慢：

| CPU 配额 | workers | 吞吐 | P50 | P95 |
|---|---|---|---|---|
| 1 核 | 2 | 263.9 | 366 | 486 |
| **1 核** | **1** | **315.8** | **301** | **365** |

吞吐高 16%，P95 低 27%。两个进程在单核上互抢 CPU，上下文切换的损耗超过了并行的收益。

本项目路由全是同步 `def`，FastAPI 会把它们丢进 anyio 线程池（默认 40 线程），单个 worker 的实际并发能力并不低——这是「1 worker 够用」的前提，如果后续改成 `async def` 路由，这个结论需要重测。

已修：`Dockerfile` 的 workers 改为 build arg `UVICORN_WORKERS`（默认 1），compose 与 `.env.example` 都注明「worker 数必须与 cpus 匹配」。

#### 问题三：造数脚本自身写错了 JSONB 结构

第一版压测 100% 的详情请求返回 500，堆栈指向 pydantic 校验：

```
pydantic_core.ValidationError: 3 validation errors for FaultDetail
solution_steps.0  Input should be a valid dictionary [input_value='断开电源，等待 30 秒后重新上电']
```

`solution_steps` 的 schema 是 `[{step:int, text:str, image_url?:str}]`，我造数时写成了字符串数组。库里肉眼看着正常，接口一读就炸。

这个错误本身是脚本的，但它揭示了一个真实运维风险：**绕过接口直接往库里灌数据（数据迁移、手工修数）会造出后端读不了的行，而且直到有人打开那个详情页才会暴露**。已在造数脚本里加 schema 自检——造完数立刻抽一条打详情接口，返回非 2xx 就直接报错中止。

### 3.2 找到真正的瓶颈：CPU 配额限流，不是 SQL 慢

单看接口耗时，找不到问题：数据库端 `SELECT 1` 只要 0.17–0.29ms，详情查询走主键索引 0.146ms，空载调 health 接口 2.4ms。但 100 并发下 health 的 P95 是 776ms——同一个操作放大了 300 倍。

翻 cgroup 计数才看清真相：

```
# backend 容器 cpus: 1.0
nr_periods   8719
nr_throttled 7593        ← 87% 的调度周期被 CPU 限流强制中断
throttled_usec 1235196386
```

**87% 的时间片被 CPU 配额掐断**。`cpus: 1.0` 不是「最多用 1 核」，而是每 100ms 周期内用满 100ms 就必须强制休眠到下一周期。请求不是卡在数据库上，是卡在等 CPU 片。

这也解释了为什么短测达标、长测失败——限流是累积效应，跑得越久，被掐断的次数越多，尾部延迟越离散。

| backend 配额 | nr_throttled / nr_periods | 限流比例 | P95 |
|---|---|---|---|
| 1 核 | 7593 / 8719 | 87.1% | 886ms |
| 2 核 | 31 / 362 | 8.6% | 590ms |

### 3.3 瓶颈最终落在 db，不是 backend

放宽 backend 到 2 核后 P95 降到 590ms 仍不达标，而 db 的 CPU 已经打满 204%（上限 2 核）。继续给 backend 加核没有意义——它大部分时间在等 db。

给 db 加到 3 核后，同样条件直接达标：

| backend | db | 吞吐 | P50 | P95 | P99 |
|---|---|---|---|---|---|
| 1 核 / 1 worker | 2 核 | 316 | 301 | 365 | 413 |
| 2 核 / 1 worker | 2 核 | 269 | 350 | 590 | 706 |
| 1 核 / 1 worker | **3 核** | **339** | **289** | **349** | **404** |

**结论：db 是唯一硬瓶颈。** 要提升并发上限，先给 db 加核；backend 加核反而因为抢走了本该给 db 的资源而变差。

### 3.4 详情接口的写放大（当前架构下的固有成本）

分开压两种接口，代价一目了然：

| 场景 | 吞吐 | P50 | P95 |
|---|---|---|---|
| 列表（纯读） | 249 req/s | 191ms | 467ms |
| 详情（1 读 + 2 写） | 156 req/s | 321ms | 719ms |

写操作让吞吐降 37%、P95 涨 54%。逐条量一下开销：

| 步骤 | buffer 触碰 | 耗时 |
|---|---|---|
| SELECT（JOIN 产品/零件名） | 15 | 0.15ms |
| UPDATE faults SET view_count+1 | 101 | 1.2ms |
| INSERT query_logs | 136 | 2.2ms |
| 合计 | ~250 | ~3.6ms |

`query_logs` 的 INSERT 里有 1.6ms 花在三个外键约束检查上。`faults` 的 UPDATE 要改 5 个索引页（主键 + product + part + published + list），这是写放大的主要来源。

**考虑过删掉看似冗余的 `idx_faults_product` / `idx_faults_part`，但实测否决了**：

| 场景（`WHERE part_id = 10` 计数） | 计划 | buffer | 耗时 |
|---|---|---|---|
| 删掉 idx_faults_part | Index Only Scan on idx_faults_list（skip scan） | 15154 | 88ms |
| 保留 idx_faults_part | Bitmap Index Scan | 9 | 0.1ms |

`idx_faults_list` 的首列是 `product_id`，只按 `part_id` 过滤时用不上它，只能退化扫描。删索引省下的写放大远不够补偿读路径 800 倍的恶化，所以保留，并在 `schema.sql` 里写明原因，免得后人也想删。

## 4. 达标情况

最终配置：**backend 1 核 / 1 worker + db 2.5 核 + nginx 0.5 核 + frontend 0.5 核**，合计 4.5 核（4 核机器上的软配额，nginx/frontend 实测空载 0% CPU，不实质占用）。

| 用例 | 结果 |
|---|---|
| TC-70 P95 < 500ms | **未达标**：两轮 10 分钟测试 P95 = 502.1ms / 513.0ms |
| TC-71 100 并发 10 分钟无 5xx | **达标**：两轮共 297,913 请求，0 个 5xx，0 个网络异常 |

两次独立 10 分钟测试的复现性很好，说明结论稳定：

| 轮次 | 总请求 | 吞吐 | P50 | P95 | P99 |
|---|---|---|---|---|---|
| 第 1 轮 | 150,597 | 250.8 | 393.3 | 502.1 | 624.3 |
| 第 2 轮 | 147,316 | 245.4 | 393.2 | 513.0 | 703.9 |

资源占用（100 并发稳定期）：

| 容器 | CPU | 内存 | 上限 |
|---|---|---|---|
| backend | 100%（饱和） | 105 MiB | 512 MiB |
| db | 190–200%（饱和） | 300–450 MiB | 1 GiB |

内存远未触顶，512m / 1g 的初值可以保留。

## 5. 最终验收数据

配置：backend 1 核 / 1 worker，db 2.5 核，连接池 20+25，`shared_buffers` 128MB（默认），100 并发，600 秒。

```
总请求   : 147316（全部 200）
吞吐     : 245.4 req/s
延迟(ms) : P50 393.2  P95 513.0  P99 703.9  max 1737.4  mean 406.9
错误     : 5xx 0  网络 0  错误率 0%

按接口：
  /api/faults        n=81099  p50=388.7  p95=507.4  p99=700.0
  /api/faults/{id}   n=43823  p50=403.8  p95=526.7  p99=719.8
  /api/health        n=22394  p50=386.2  p95=503.4  p99=692.7
```

### 怎么理解这个 513ms

它是「差一点达标」，但不能按「误差范围内算过」处理。

**必须先说清一个坑：本报告中所有短时测试（90–180 秒）的 P95 在 350–420ms，看起来都达标，但那是缓存预热期的红利，不能作为结论。** 同样的配置跑满 10 分钟，P95 就稳定落在 500–515ms。两轮独立 10 分钟测试复现性很好（502 / 513），说明这不是抖动。

把短测结果当结论属于自欺，TC-70 的语境是持续服务，这里按 10 分钟口径判定。

劣化机制已经定位（见 §3.4）：详情接口每请求写 2 次（UPDATE view_count + INSERT query_log），10 分钟内累积 4.4 万条日志插入和等量 UPDATE。`faults` 表虽只有 5 万行，但 UPDATE 要维护 5 个索引页，db CPU 长期跑在 190–200%，已无余量。

10 分钟内 P95 从 393ms 爬到 513ms，说明系统在 100 并发下**没有进入稳定态**，仍在持续劣化。按这个斜率外推，跑 30 分钟会明显超过 500ms。所以正确结论是：**当前配置的真实承载低于 100 并发，P95 < 500ms 的稳定并发上限在 70 左右**（实测 70 并发 45 秒 P95 241ms，但该轮偏短，需更长测试确认）。

### 试过但没用的两个方向

**加大 `shared_buffers`**：从默认 128MB 调到 384MB 后 P95 从 401ms 变成 413ms，吞吐从 483 降到 464（相同预热条件下），没有收益。数据（472MB）的实际缓存主要由 OS page cache 承担，`shared_buffers` 加大反而挤压了 page cache。已回退到默认值，没有写进 compose。

**压缩 backend 到 0.5 核**：为了在 4 核内塞下 db 3 核，测过 backend 0.5 核——P95 直接恶化到 975.6ms，吞吐掉到 218 req/s。backend 需要 1 核，压不动。

### 与目标的差距有多大

需要说清楚的是：这个「不达标」的严重程度有限。

- 100 并发、245 req/s 对一期是**远超实际需求**的负载。项目目标是 3 个月自助解决率 30%，按日活几百人估算，峰值并发大概率是个位数。
- P95 513ms 与目标 500ms 只差 2.6%，用户完全感知不到。
- 0 个 5xx、0 个超时，稳定性没有任何问题。

真正的风险不是「慢」，而是**不知道余量在哪**：现在只知道 100 并发时正好卡在临界点，不知道再翻一倍会怎样。所以下面给出确切的改进项，而不是把问题留在「差一点点」的模糊地带。



## 6. 遗留与建议

### 已修

1. compose 透传连接池四个参数，`.env.example` 补说明
2. `DB_POOL_TIMEOUT` 默认 30s → 10s
3. workers 改 build arg，默认 1，与 cpus 匹配
4. compose 里 db `cpus: 2.0` → `3.0`，并写明压测依据
5. 造数脚本加 schema 自检

### 建议但未做（需决策）

**1. `view_count` 改异步批量累加（让 TC-70 达标的关键项）**

当前每次详情请求都 `UPDATE faults SET view_count = view_count + 1`，是 100 并发下最大的单一写热点，也是 §5 里 10 分钟劣化的主因。`view_count` 只用于列表排序和展示，不需要实时精确。

改法：详情接口只写 `query_logs`（append-only，无锁争用），`view_count` 由定时任务按小时从 `query_logs` 聚合回写。

预期收益（保守估计）：
- 详情接口少一次 UPDATE，按 §3.4 的量账约占该请求执行时间的 33%
- `faults` 表不再有高频写，5 个索引的维护开销归零，db CPU 压力显著下降
- 表膨胀与 vacuum 压力消失

代价：浏览数有一小时延迟（只影响列表的「热门」排序，不影响任何功能正确性）。

按 §3.4 的对照数据（纯读 P95 467ms vs 读写 P95 719ms）推断，去掉 UPDATE 后 100 并发 10 分钟的 P95 应落在 400ms 附近，能稳定达标。**建议做，但这是行为变更，需要产品确认浏览数允许延迟。**

**2. 详情接口的外键检查（不建议动）**

`query_logs` 的 `fault_id` / `part_id` / `product_id` 三个外键，每次插入要 1.6ms 校验（占该语句 70%）。但插入前业务代码已经查过 `fault_id` 存在。

虽然省掉能提速，但不建议——外键是数据完整性的最后一道防线，靠业务代码保证容易在后续改动中失效。这类「现在能省 1ms、以后可能脏数据」的优化不值得做。

**3. 公开接口限流（需单独排期）**

本轮压测是「正常流量」口径。公开接口目前无任何限流，恶意刷 `/api/faults/{id}/feedback` 或 `/api/query-logs` 会直接打到 db。已在 B-04/B-05 审查报告中记录，属契约级变更。

**4. 如果一定要在 4 核内达标**

按优先级：① 做上面的 `view_count` 异步化；② 若仍不够，把 db 从 3 核加到 4 核、backend 挤在共享核上（不推荐，backend 会被限流）；③ 或者接受 70 并发的容量口径，把 TC-70 的并发条件从 100 改为 70——但这等于改验收标准，必须由需求方拍板，不能开发自己降标准。

### 容量边界

以上全部结论基于 **5 万故障 + 50 万日志** 的数据量。若真实知识库体量显著更大，需要重新评估。

`query_logs` 会以每天数万条的速度持续增长（本轮 10 分钟就写了 4.5 万条）。按 250 req/s 满负荷跑一天是 2000 万条，显然不现实，但**上线前必须定好日志归档策略**（建议保留 180 天），否则表无限增长最终会拖垮索引。

当前架构在 4 核 8G 上的实测能力：

| 指标 | 数值 |
|---|---|
| 稳定吞吐 | 250 req/s（10 分钟均值） |
| 100 并发 P95 | 502ms（10 分钟）/ 349ms（3 分钟） |
| 错误率 | 0% |
| 稳定并发上限（P95<500ms） | 约 70 |

对一期的实际业务量（日活几百、峰值并发个位数）而言，这个容量有充足余量。**不建议为了一次压测达标去改架构**——把 `view_count` 异步化作为遗留优化项记录，等上线后看真实流量再决定是否要做。
