## 2. Round 1：审查发现

无阻塞问题。两条 Minor 都是"取舍"，记录以备后续：

| 编号 | 现象 | 判断 |
|---|---|---|
| m1 | `missed` 的 `sample_product_name` / `sample_part_name` 取该分组**最新入库**的一条（`max(id)`），而 `last_seen_at` 取 `max(created_at)`。若存在历史数据回填（插入时间与创建时间不一致），样例行与 `last_seen_at` 可能不是同一条 | 可接受：正常链路下日志是查询时即时写入，`id` 与 `created_at` 同序；回填属运维特例，且字段语义是"样例"而非"最后一条" |
| m2 | 未命中分组用的是 `coalesce(nullif(lower(trim(raw_query)),''),'(未输入关键词)')`，外层 `coalesce` 让 `idx_query_logs_missed_q`（表达式索引）无法直接命中 | 可接受：窗口过滤仍走 `idx_query_logs_missed`（`created_at` 上的部分索引），50 万行量级需在 TC-70 压测确认 P95 < 500ms |

已核对且**正确**的关键点：

- 解决率分母用 `hit=true`，不是 `fault_id IS NOT NULL`
- `open_tickets` 为当前积压，不随 `days` 变化；`total_tickets` 才按窗口
- `days=0` 表示全部，返回 `period_days=0`；其余取值 1–365，越界 422
- `top-faults` 按窗口内 `query_logs.fault_id` 出现次数排序，不按历史 `view_count`
- `missed` 归一化：`trim` + `lower` + 空值落 `(未输入关键词)`
- 三个端点均需鉴权

## 4. Round 3：真库验证

播种一份确定性数据（6 条命中/4 条 resolved、3 条未命中、1 条 40 天前、3 张工单），
再用原始 SQL 独立统计对账：

```
API  : total=9 view=6 resolved=4 missed=3 rate=0.667 tickets=2 open_tickets=2
SQL  : total=9 view=6 resolved=4 missed=3
```

`days=0` → total=10 / view=7 / resolved=5 / rate=0.714 / tickets=3，`open_tickets` 仍为 2（含窗口外的 processing）✓

**关键语义实测**：删掉被 3 条日志引用的故障后，`view_queries` 仍为 6、`resolve_rate` 仍为 0.667，
`top-faults` 里该故障消失——证明分母不受故障删除影响，这正是契约把口径定为 `hit=true` 的原因。

`missed` 分组实测：`"  漏水 "` 与 `"漏水"` 合并、`LEAK`/`leak` 合并为 `leak`、`NULL` 归入 `(未输入关键词)`，
样例产品/零件名正确，`last_seen_at` 带 `+08:00`。
