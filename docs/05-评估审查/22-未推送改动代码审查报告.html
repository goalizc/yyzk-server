CriticalC-01009 删列时旧后端仍在服务：发布窗口内全站鉴权 500，回滚需手工补列

位置 deploy/deploy.sh:269-316 deploy/migrations/009_multi_role.sql:39

证据 deploy.sh 的升级序列是 up -d db → backup → run --rm migrate → up -d，全程没有停旧 backend。旧镜像的 User 模型仍映射 role 列（git show cee256c:backend/app/models/user.py），每个请求 db.get(User, ...) 都会 SELECT 该列；009 一旦 DROP COLUMN，旧进程立刻 UndefinedColumn。反向同样成立：009 执行前，新代码查 user_roles 会 UndefinedTable。

deploy.sh:  up -d db  →  migrate（DROP COLUMN role）  →  up -d backend
             ↑ 旧 backend 仍在跑，模型 SELECT users.role  ↑ 全站 500 窗口

影响 发布期间登录、/api/auth/me、所有 require() 接口全部 500。若 up -d 因端口/内存失败，旧后端会持续不可用。回滚到旧镜像必须手工 ALTER TABLE users ADD COLUMN role 并从 user_roles 回填，否则旧镜像同样起不来。

修法 二选一：
① 最小改动：migrate 前 compose stop backend，失败时 compose start backend；
② 规范做法：expand/contract —— 009 只建表 + 回填（保留 users.role），010 在新后端上线稳定后再 DROP COLUMN。

证据 验收命令写 INSERT INTO users (username, ..., role)，v1.6 的表已无 role 列，实测直接报 column "role" of relation "users" does not exist；即使删掉该 INSERT，users_role_check 在 v1.6 也不存在，断言返回空。008 的 DO 块在无 role 列时整块跳过，所以「连续执行两次 008 均成功」只是 no-op。

影响 按计划书做验收，第一步就失败；强行解释成「通过」会让迁移幂等的验收结论不可信。

修法 改为插 users + user_roles，断言 user_roles.role 的 CHECK 含 7 角色、且 users.role 不存在。

修法 在用例 setup 里用 admin 调 POST /api/admin/users 建 roles=["warehouse_clerk"] 的账号，或提供 scripts/dev/ 前置脚本并在 README 写明。

MajorM-10流水「操作人」列展示的是数字 ID

位置 frontend/src/views/admin/inventory/MovementTable.vue:74 backend/app/schemas/inventory.py:275

证据 列 prop="operator_id"，表头是「操作人」；后端响应只有 operator_id，没有姓名。
