## 一、先澄清两个事实

### 1.1 「前后端未通」不成立

实测：4 容器 healthy、`POST /api/auth/login` 返回 200、错误体带 `code` 正常返回。
前后端通信本身没有问题。

用户看到的"未通"，实际是**语言状态没有从客户侧传导到后台**——后端无关，是前端状态设计问题。见 §2.1。

### 1.2 后台页面本体仍是中文，属批 2 未完成

批 1 只做了后台**外壳**（导航、顶栏、登录页、页面标题），9 个业务页面的列头、表单标签、
表格内容仍是中文。这是分批交付的中间态，此前已在验收表 §十一 标注，但**用户仍然会认为"没做"**，
说明分批边界对使用方不够可见。本报告 §4 给出完整清单。

## 二、本轮已修（7 项）

### 2.1 【严重】语言无法从客户侧传导到后台

**现象**：英文客户侧点「Admin」进入登录页，界面是中文。

**根因**：`PublicLayout.toggleLocale()` 只做路由跳转，`router.beforeEach` 里调
`setLocale(prefixed, { persist: false })` —— 刻意不写 `localStorage`（当时认为"URL 才是权威，
不该污染后台偏好"）。但用户**主动点过切换按钮**这件事本身就是明确的偏好表达。

**修复**：切换按钮里显式 `setLocale(next, { persist: true })`。规则收敛为：

| 场景 | 是否写入偏好 |
|---|---|
| 用户点语言切换 | ✅ 写入（客户侧 + 后台都延续） |
| 直接访问别人分享的 `/en/...` | ❌ 不写入（不影响后台） |

**回归测试**：`e2e/i18n.spec.js` 新增「切到英文后进后台，登录页也是英文」。

### 2.2 【严重】浏览器标签页标题从未国际化

`document.title` 只在 `index.html` 写死过一次「售后故障诊断系统」，进任何页面、
任何语言都是同一个中文标题。

**修复**：新增 `src/utils/pageTitle.js`，按路由 `meta.titleKey` 生成 `页面名 · 品名`；
`router.afterEach` 调用；后台切语言时手动补一次（切语言不换路由，afterEach 不触发）。

同时给客户侧 4 个路由补了 `titleKey`（原先只有后台有）。

### 2.3 【中】`<html lang>` 首屏不同步

`index.html` 固定 `lang="zh-CN"`，直链 `/en/...` 时首屏按中文处理 → 屏幕阅读器读错、
浏览器可能提示"翻译成中文"。

**修复**：`locales/index.js` 在 `createI18n` 之后立即同步 `document.documentElement.lang`。

### 2.4 【中】404 页中文，且「返回首页」会把英文用户丢回中文首页

修复：文案走 `common.notFound.*`；返回地址按当前语言给 `/` 或 `/en`。

### 2.5 【中】公共错误态 `ErrorState` 中文

「加载失败」「重新加载」硬编码。该组件被 4 个列表页与详情面板共用，英文界面下会露出中文。

### 2.6 【中】登录页中文（原计划批 2，提前到本轮）

登录页是"进后台"的第一屏。只修 2.1 而不修登录页，用户看到的仍然是中文，等于没修。
已完整迁移（含校验文案、成功/失败提示），并把原变量 `errorText` 改名为 `formError`
（与 `utils/error.js` 导出的函数同名，易混淆）。

### 2.7 【低】窄屏后台没有语言切换入口

原实现 `v-if="!isNarrow"` 只给桌面放了语言下拉，手机上无法切换。
修复：并入窄屏导航下拉，用 `lang:` 前缀区分导航项与语言项。

## 四、设计层面**刻意保留**、但需要让使用方知道的

### 4.1 业务数据不翻译（已知，最大遗留）

产品名、零件名、故障标题/现象/原因/步骤都是中文存储。英文界面下客户看到
**英文外壳 + 中文方案正文**。原因见 `docs/02-技术设计/国际化设计.md` §1.2、§9。

### 4.2 日期格式不随语言变化

`utils/format.js` 固定 `Intl.DateTimeFormat('zh-CN')` 并输出 `2026-10-23 09:17`。

**有意保留**：`YYYY-MM-DD` 在中英文下都无歧义，而 `en-US` 的 `10/23/2026` 与
`en-GB` 的 `23/10/2026` 月日顺序相反，反而更容易误读。表格列宽也依赖固定长度。

> 若业务方坚持英文用 `Oct 23, 2026`，改 3 行即可，但需同步检查表格列宽。

### 4.3 一码多义的错误码在英文下只能给通用文案

`NOT_FOUND` 在中文下能精确到「产品不存在」「工单不存在」，英文字典只有
`The requested data does not exist`。这是"用 code 查表"方案的固有代价，
除非后端把语义拆成更细的码（如 `PRODUCT_NOT_FOUND`）。

**建议**：如果英文客户会高频遇到"某个东西不存在"，再考虑拆码；否则通用文案可接受。

### 4.4 后端校验信息在英文下走通用文案

`VALIDATION_ERROR` 的 detail 由 `_validation_detail` 拼中文（含字段名），
英文环境走字典的通用句（`Some fields are invalid`），字段级精确定位丢失。
靠前端表单校验兜住大部分场景，可接受。

### 4.5 没有做「翻译文案的专业校对」

`en-US` 是开发翻译的。面向外部客户前，建议由业务方校对术语（如 "fault" vs "issue"、
"part" vs "component" 的一致性）。

## 五、审查方法（可复用）

1. **残留扫描**：正则扫 `.vue/.js` 中含中文的行，排除 `locales/`、注释、`<style>` 块
2. **运行时验证**：Playwright 真实浏览器走查中英文两条链路，打印导航/按钮/标题的实际文本
3. **反向验证**：删一个错误码、故意打乱语言解析，确认测试会红
4. **键完整性**：`locale.spec.js` 比对两语言键集合与占位符；扫描后端 `BusinessError` 码
