## 三、逻辑链闭环

设计意图是「事件 → 留痕 → 查询 → 处置」四段闭合，实测后各段状态：

| 环节 | 状态 | 依据 |
|---|---|---|
| ① 事件产生（业务写操作） | ✅ | 20 个并发写 → 20 条审计，无丢失（实测） |
| ② 识别与写入 | ⚠ | 规则表覆盖 24 类动作；但 `_build` 异常时**整条链路断裂**（P1-2） |
| ③ 可查询 | ✅ | 列表/详情/动作清单/按人汇总/导出；5 万条下 50ms |
| ④ 可处置 | ✅ | 停用账号、重置密码（会 bump `token_version` 踢下线），且**处置动作本身留痕** |
| ⑤ 可复盘 | ❌ | 无告警、无 case 关联：异常行为只能靠人事后翻页面（P2-8） |
| ⑥ 可举证 | ❌ | 记录可被删改、导出无签名/哈希（P0-1、P1-4） |

**闭环缺口总结**：查询段做得最完整，**取证段（⑥）与主动发现段（⑤）是断的**。
一个真实的攻击场景：客服账号被外传 → 攻击者用其登录 → 批量查看工单详情拿客户手机号 → 删除自己登录记录。
当前系统只能拦住「查得到」的部分，第 3 步（读操作不审计，P1-7）和第 4 步（可删记录，P0-1）都拦不住。

## 四、问题清单

### P0-1【合规】审计记录可被应用账号直接删改 ｜ ✅ 已修（触发器，见 §8.1）

**证据**（实测查询）：

```
DELETE   | t
UPDATE   | t
TRUNCATE | t
触发器数量 | 0
```

应用连接使用的 `fault` 账号对 `audit_logs` 拥有全部写权限，且无触发器、无哈希链。
任何拿到 DB 凭据的人（运维、或应用被攻破后）都能 `UPDATE`/`DELETE` 审计记录，事后无法证明曾被修改。

**影响**：不满足等保「避免未预期的删除、修改或覆盖」；出事后审计记录不足以作为证据。

**修复建议**（三选一，成本递增）：

1. `REVOKE UPDATE, DELETE, TRUNCATE ON audit_logs FROM fault`，只保留 `SELECT, INSERT`（约半天；
   代价是清理脚本要改用超级用户或专用清理账号）
2. 同上 + 增加触发器：任何非白名单会话的 `UPDATE/DELETE` 直接 `RAISE EXCEPTION`（约 1 天）
3. 哈希链（每行存 `prev_hash`）+ 每日锚定值外发（约 2~3 天，可证明「没被删过」）

推荐 **1**：成本最低且能挡住 90% 的场景；2 是它的加固版。

### P1-1【安全】CSV 导出存在公式注入 ｜ ✅ 已修

**证据**（实测导出一行）：

```
2026-10-26T11:37:32+08:00,admin,fault.create,fault,1,"=HYPERLINK(""http://evil.example"",""click"")",成功,200,...
```

`target_name` 以 `=` 开头时原样写入 CSV，Excel 打开会当公式执行（可诱导点击外链、或在旧版本触发
DDE 命令）。`target_name` 来自运营录入的故障标题，属于可控输入。

**修复建议**：导出时对以 `= + - @ Tab CR` 开头的单元格前置单引号（`'=...`），约 10 行代码 + 1 个用例。

### P1-2【缺陷】审计构建异常会让已成功的业务请求返回 500，且不留审计 ｜ ✅ 已修

**证据**（临时用例 monkeypatch `_build` 抛异常）：

```
[_build 异常] http=500，业务是否已落库=True，审计最后一条 action=auth.login
```

业务数据已提交，客户端却收到 500，且审计里没有这条记录。用户会重试 → 产生重复数据；
「所有操作有迹可循」在最需要它的路径上失效。

**根因**：`core/audit.py:89` 的 `_build()` 在 `try` 之外，异常直接冒泡。

**修复建议**：把 `_build` 包进 `try/except`，失败时退化为一条最小记录（只含 action/status/username）；
`except` 分支里同样加保护。约 15 行。

### P1-3【缺陷】未捕获异常时审计缺错误类型 ｜ ✅ 已修

**证据**（临时用例触发 500）：

```
[500 场景] http=500 审计: status=500 result=failure error_code=None detail={}
```

`error_code` 由异常处理器写入 `request.state`，而处理器在审计中间件**外层**执行，此刻尚未设置。
事后从审计只能看到「500 失败了」，要判断异常类型得再用 `request_id` 去翻后端日志——两跳。

**修复建议**：`except Exception as exc` 分支里把 `type(exc).__name__` 写进 `detail.error_class`（3 行）。

### P1-4【合规】查看与导出审计日志本身不留痕 ｜ ⚠ 部分已修（导出已留痕，列表查看未记）

**证据**：连续调用列表与导出接口，审计表最后一条 id 不变（`1 -> 1`）。

即：谁在什么时候导出了全部审计记录（CSV 含所有人 IP），查不出来。这是典型的「审计者的审计」缺失。

**修复建议**：把 `GET /api/admin/audit-logs/export` 纳入审计（`action=audit.export`），
列表查询可按需只记「带筛选条件的大范围查询」。约 20 行（规则表 + 1 条规则 + 前端文案）。

### P1-5【缺陷】被限流拦下的暴力破解不留痕

**证据**（同一 IP 连打 18 次错误登录）：

```
401 401 401 401 401 401 429 429 429 429 429 429 429 429 429 429 429 429
审计表里该用户名的记录数：6
```

18 次尝试中 12 次被 Nginx 的 `limit_req` 挡在门外（429），**不经过后端 → 不写审计**。
攻击者只要放慢到限流阈值以下就能全程留痕，但真实撞库往往先被拦一大批——这批痕迹只在
Nginx 访问日志里，且受 `10MB × 3` 轮转限制。

**修复建议**：保持 Nginx 限流（性能考虑），把「429 也入审计」放到第二步：
Nginx 侧对 429 单独打日志文件并落盘，或把登录限流下沉到后端（能写审计，但增加后端压力）。
本次建议只补文档说明 + 提高 Nginx 日志轮转上限。

### P1-6【设计】登录失败的「用户名」与已验证身份混用同一字段 ｜ ✅ 已修

登录失败时 `username` 存的是**用户输入值**（未验证），与成功登录的已验证身份写在同一个字段。
后果：日志里会出现「`admin` 在某 IP 登录失败」，实际可能是别人在猜 `admin` 的密码——追责时容易误判。

**证据**：`username='nobody'` 的失败记录，`detail.reason=user_not_found`，字段本身无「未验证」标记。

**修复建议**：失败记录增加 `detail.identity_verified=false`（成功为 `true`），前端在详情里标注
「尝试的账号名（未验证）」。约 10 行。

### P1-7【业务风险】敏感数据读取不在审计范围

工单详情（含客户手机号明文）是 `GET` 请求，不进审计；列表页脱敏，详情页不脱敏。
客服账号被外传后，攻击者可批量翻工单详情获取客户联系方式，**行为不留痕**。

**修复建议**（需产品决策，不建议直接做）：记录「工单详情查看」为 `ticket.view`，
但客服日均查看量大，会给审计表带来 10 倍写入。折中方案：只在同一账号短时间查看超过 N 条时
记一条汇总告警（需要新增计数器，成本较高）。

## 六、刻意保留（不是缺陷，避免以后被当 bug 改掉）

1. **读操作不进审计**：客户侧查询已有 `query_logs`，后台读量大且无追责价值（P1-7 是它的例外）。
2. **不记请求体**：密码、客户手机号因此不会进审计表——这是刻意取舍，不是遗漏。
3. **审计失败不影响业务**：可用性优先；代价是极端情况下少一条记录（P2-7 要求告警补偿）。
4. **`username` 冗余存一份**：账号删除/改名后历史仍可追。
5. **删除类在 delete 前记 `target_name`**：否则删完就查不到对象名。
6. **规则表驱动、不在每个路由埋点**：新增写端点补一行即可，避免遗漏。
7. **容器日志留存受轮转限制**（`10MB × 3`，高流量下不足六个月）：这是既有部署问题，
   与审计表无关；审计表本身按 180 天留存。要满足《网络安全法》第 21 条的「网络日志留存六个月」，
   需要额外接入日志收集或落盘归档，属独立任务。

## 八、修复记录（v1.1，2026-10-26）

### 8.1 P0-1 防篡改：改用触发器而非收权限（附审查结论的自我修正）

**修正**：v1.0 给的方案 1「`REVOKE UPDATE, DELETE, TRUNCATE`」**实际不可行**——审查时没有先查账号角色，
事后确认 `fault` 是 **superuser**（`rolsuper = t`），PostgreSQL 里超级用户绕过一切权限检查，`REVOKE` 对它无效。

**实际做法**：迁移 `004_audit_immutable.sql` 加两个触发器：

| 触发器 | 触发时机 | 作用 |
|---|---|---|
| `trg_audit_logs_immutable` | `BEFORE UPDATE OR DELETE`（行级） | 抛错并给出 HINT |
| `trg_audit_logs_no_truncate` | `BEFORE TRUNCATE`（语句级） | 同上（行级触发器拦不住 TRUNCATE） |

**实测**（三条破坏性语句全部被拒，记录数不变）：

```
UPDATE audit_logs SET username='tampered';
ERROR:  审计记录为只追加（append-only），不允许修改或删除
DELETE FROM audit_logs;
ERROR:  同上
TRUNCATE audit_logs;
ERROR:  同上
-- 之后 select count(*) 仍为 2
```

**清理任务改造**：`cleanup-audit.sh` 在**同一事务**内 `DISABLE TRIGGER` → `DELETE` → `ENABLE TRIGGER`，
DELETE 失败时事务回滚、触发器自动恢复，不会留「触发器被关着」的中间态。实测删 1 条过期记录后
`tgenabled = O`（已恢复）。

**仍然挡不住**：拿到超级用户凭据的人可以 `ALTER TABLE ... DISABLE TRIGGER` 再删。
要根治必须把应用换成**非超级用户角色**（新增 `fault_app`，仅授权业务表 + `audit_logs` 的 SELECT/INSERT）。
这是部署变更（`DATABASE_URL`、`.env`、`deploy.sh`、迁移和清理脚本的账号各自分离），**本次未做，等决策**。

### 8.3 修复过程中的事故（必须记录）

给 `004` 迁移加触发器时，函数体里用了 plpgsql 的 `%` 占位符
（`RAISE EXCEPTION '... 不允许 % 操作', TG_OP`），被 psycopg2 当成参数模板，迁移报
`immutabledict is not a sequence` 而**失败**。我未确认迁移结果就执行了 `UPDATE / DELETE / TRUNCATE`
三条验证语句——触发器并不存在，三条全部执行成功，**清空了当时表内的 36 条审计记录**。

- 影响：开发环境的操作审计记录（含一条重置密码、若干验证操作），**无备份可恢复**（审计表在换演示数据之后才建）
- 业务数据无影响
- 教训：① 破坏性验证必须「先确认防护已生效」再执行；② 迁移里的 SQL 不要用 `%` 占位符（已改为
  `RAISE EXCEPTION USING MESSAGE/HINT`）；③ 上生产前应先 `--check` 或对空表验证
