## 2. Round 1：发现的问题

### Major

**M1 上传把整个文件读进内存，20MB × 并发会顶爆容器内存**

- 位置：`backend/app/utils/upload.py`（`content = await file.read(limit + 1)`）
- 算式：容器 `mem_limit=512m`（`docker inspect` 实测 `536870912`），单次上传最多占 20MB 堆内存，
  加上 `UploadFile` 自身的 spool 副本，**十几个并发上传就能把后端顶成 OOM**；上传是后台接口，
  但导入历史资料时很容易并发。
- 另有两个小问题同源：超限时已经把整个文件读进内存才发现（浪费带宽与内存）；
  空文件走的是"类型不支持"分支，提示误导。

### Minor

| 编号 | 位置 | 问题 |
|---|---|---|
| m1 | 四处关键词查询（`backend/app/api/admin.py`、`admin_faults.py`、`public.py`、`admin_tickets.py`） | 关键词查询直接拼 `%{keyword}%`，用户输入里的 `%`、`_` 会被当成 LIKE 通配符。按 SQL 语义，搜「100%」会连带命中「100X」，搜索结果不可预期 |
| m2 | `backend/app/services/ticket.py` | `{"status": null, "remark": null}` 这类"全空"请求会通过校验，然后静默把处理人改成当前登录用户 |
| m3 | `backend/app/utils/upload.py` | 空文件（0 字节）返回"不支持的文件类型"，运维/前端会误以为是格式问题 |

### 运维注意（不是代码缺陷）

上传文件由容器内 `uid=10001` 创建，宿主机普通用户 `rm` 会 `Permission denied`。
清理/迁移需 `sudo` 或 `docker exec fault-backend rm`。已在 README 的镜像说明里补了这一条。

## 3. Round 2：修复

| 项 | 修法 | 验证 |
|---|---|---|
| M1 | 改为**分块流式落盘**：1MB 一段写入 `.<name>.part`，首块即校验文件头（12 字节足够覆盖 jpg/png/pdf/mp4），超限立即中断并删临时文件；校验通过后 `replace` 成正式文件名 | 21MB → 413 且目录内无 `.part` 残留；2KB jpg → 200，`/uploads/...` 静态直出 200 |
| m1 | 新增搜索工具 `backend/app/utils/search.py` 的 `like_pattern()`，转义 `\ % _`，四处调用统一 `.like(pattern, escape="\\")` | 真库实测：搜 `100%` 只命中 `PCT-100`；搜 `100_` 命中 0 条 |
| m2 | 全 null 判定改为 `any(v is not None for v in data.values())` 为假则 400 | 单测覆盖 |
| m3 | 先判 `written == 0` 再判文件头，返回 400「文件内容为空」 | 单测覆盖（0 字节 jpg） |

## 4. Round 3：重审

| 检查点 | 结论 |
|---|---|
| 流式实现边界 | 头部 12 字节阈值：jpg 3 / pdf 5 / png 8 / mp4 8，全部覆盖；空文件先判空 |
| 失败路径清理 | 类型不符、超限、空文件三种异常都删 `.part`；`finally` 里一定 `close()` |
| 落盘原子性 | 同目录 `replace`（同文件系统），不会出现半截正式文件 |
| LIKE 转义 | 四处均显式传 `escape`（SQLite 没有默认转义符，PG 有，显式更稳） |
| 工单号并发 | 真栈 5 线程并发提交 → 拿到 `0003–0007` 连续且唯一，`pg_advisory_xact_lock` 生效 |
| 日期区间 | 真库实测：当天范围 1 条、昨天 0 条、跨两天 1 条；`status=done` → 422 |
| 契约符合性 | 状态机、`400 VALIDATION_ERROR`（联系方式/描述/备注）、`TICKET_STATUS_INVALID` 文案、`contact` 列表脱敏/详情完整、首条流转日志全部对齐 |

## 5. 保留风险（未改，需产品确认）

1. **工单提交接口公开且无限流**：可被脚本刷单，直接污染工单量与积压指标。建议 Nginx 对
   `/api/tickets` 加 `limit_req`（例如 10r/m，burst 3）。上一轮 B-04 的详情限流建议仍待确认，
   可以一起做。
2. **`assignee_id` 不传即改派给当前用户**：契约如此规定，但结果是"任何一个客服改个备注，工单就转到他名下"。
   若产品希望"只在首次处理时认领"，需要契约变更。
