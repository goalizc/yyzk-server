# 14 · 上传故障修复报告（解决步骤图片上传报 500）

> 报障时间：2026-10-21
> 报障描述：「解决步骤上传图片提示服务器内部错误」
> 处理结论：**已修复并端到端验证闭环**
> 提交：`2eef367`

---

## 1. 现象与定位

### 1.1 现象

后台「故障知识库 → 编辑 → 解决步骤 → 添加图片」上传时，接口返回 500，
前端提示「服务器内部错误」。

### 1.2 定位过程

| 步骤 | 动作 | 结果 |
|---|---|---|
| 1 | 查 backend 日志 | 堆栈末端 `PermissionError: [Errno 13] Permission denied: '/data/uploads/.20261021-017833cf.png.part'` |
| 2 | `ls -ld /data /data/uploads` | `/data` 为 `10001:10001 drwxrwxr-x`；`/data/uploads` 为 `1000:1000 drwxr-xr-x` |
| 3 | 查容器运行用户 | `uid=10001(app)` |
| 4 | 结论 | 上传目录属主与容器运行 uid 不匹配，无写权限 |

### 1.3 根因

`deploy/docker-compose.yml` 里把 `./data/uploads` 挂载到容器 `/data/uploads`。
**挂载点会覆盖镜像构建期的 `chown`**，最终属主完全取决于宿主机上这个目录是谁建的：

- 宿主机手工 `mkdir` 建 → root:root
- 开发者本人建 → 1000:1000（本次实况）
- 只有显式 `chown 10001:10001` 才是对的

即：镜像里写再多 `chown` 都无法保证正确，这本质上是**部署步骤缺了一步**，
而不是代码缺陷。但代码把环境问题报成了 500 `INTERNAL_ERROR`，掩盖了真实性质。

---

## 2. 修复方案

三层处理，分别解决「以后不再坏」「坏了看得懂」「用户知道怎么办」。

### 2.1 部署流程：`deploy/scripts/prepare-storage.sh`（新增）

把「建目录 + chown + 验证可写」固化成幂等脚本。

| 参数 | 用途 |
|---|---|
| 无参数 | 修正权限 |
| `--check` | 只检查不修改（CI / 日常巡检） |
| `--dry-run` | 只打印将要做什么 |

关键设计：**第 4 步用容器 uid 实际 `touch` 一个探针文件**。

```bash
PROBE="$UPLOAD_DIR/.write-probe-$$"
if touch "$PROBE" 2>/dev/null; then
  rm -f "$PROBE"
  log "验证通过：目录可写"
else
  fail "目录仍不可写（属主正确但无法创建文件）。"
fi
```

只查属主不够——ACL、只读挂载、SELinux 都可能让属主看起来正确但实际写不进去。
之前踩过的坑正是"属主对了就以为对了"。

`BACKEND_UID` / `BACKEND_GID` 与 `backend/Dockerfile` 保持同源，注释里注明改一处要同步另一处。

### 2.2 错误码：500 → 503

`backend/app/utils/upload.py` 的 `save_upload` 中：

```python
try:
    out_file = temp.open("wb")
except PermissionError as exc:
    # 目录不可写。这是部署问题不是程序缺陷，报 503 让运维按错误码
    # 去查权限；500 只会让人以为是代码 bug。
    await file.close()
    logger.error(...)
    raise BusinessError(
        "SERVICE_UNAVAILABLE",
        "服务器暂时无法保存文件，请联系管理员",
        503,
    ) from exc
```

`SERVICE_UNAVAILABLE` 是 API 契约 §7 已登记码，**未新增未登记错误码**。
detail 里不含服务端绝对路径（测试 `test_upload_returns_503_when_dir_unrecoverable`
显式断言 `str(target) not in detail`）。

### 2.3 前端文案

`frontend/src/components/ImageUpload.vue`：

```js
// 503 是服务端存储不可写（多为上传目录权限问题），重试没用，得找运维。
// 后端已给中文 detail，但用户不知道"下一步做什么"，这里补一句动作指引。
if (code === 'SERVICE_UNAVAILABLE' || e?.response?.status === 503) {
  return '服务器暂时无法保存文件，请稍后重试；持续失败请联系管理员'
}
```

## 3. 刻意不做的部分（重要）

### 3.1 不在应用层自愈

早期版本尝试让 `ensure_upload_dir()` 自愈：目录不可写就 `rmdir` 后重建。
**实测全部失败**：

| 尝试 | 结果 |
|---|---|
| `rmdir` | 目录非空时抛 `OSError`；且被 `except OSError: pass` 吞掉 → 静默失败 |
| `rename` 到 `.stale-*` | `Device or resource busy`（挂载点不可重命名） |
| `chmod` / `chown` | 需要 root，容器以非 root 运行（不应为此降权） |
| 删光内容再建 | 目录自身 mode 仍是 555，照样写不进去；且**目录里可能挂着 20 个正常附件，删内容不可接受** |

结论：**应用层救不了这个故障，只能把它变干净。**
最终 `ensure_upload_dir()` 的行为是「能写就返回、不能写就记日志后返回」，
不动任何文件，把现场留给运维。

### 3.2 不把 `chmod 775 /data` 当唯一保障

`backend/Dockerfile` 加了：

```dockerfile
RUN groupadd --gid 10001 app \
    && useradd --uid 10001 --gid app --no-create-home --shell /usr/sbin/nologin app \
    && mkdir -p /data/uploads /app/scripts \
    && chown -R app:app /data /app \
    && chmod 775 /data
```

但注释明确写了这是**兜底而非唯一保障**，因为挂载点会覆盖它。
真正的保障是 `prepare-storage.sh`。

## 5. 本次踩到的认知误区

### 5.1 「属主正确」不等于「可写」

沙箱里跑 `prepare-storage.sh --check` 报 `65534:65534`。这是 user namespace
映射导致的（宿主 uid 1000 映射成容器内 10001，宿主认不出的 uid 落成 nobody），
真实服务器不会出现。但这恰好印证了脚本设计：**最终以能否真的写文件为准**。

### 5.2 「构建成功」不等于「部署生效」

这个教训在 C 路线已吃过一次（移动端 CSS 未生效，容器里跑的还是旧镜像）。
本次同样：改完 Dockerfile 必须 `docker compose up -d --build backend` 才生效。

### 5.3 图片显示异常未必是产品缺陷

调试中详情页第 1 步一度显示「加载失败」。查库发现三个步骤 `image_url` 全是 `None`，
但界面有预览元素。最终定位是**我造的测试 PNG 只有文件头、无有效数据**，
浏览器解码失败（`errorSlot: true`）。换成用 Python 生成的合法 8×8 PNG
（含 IHDR/IDAT/IEND chunk）后 `naturalWidth: 8`、`errorSlot: false`，确认不是产品缺陷。

**教训：验证素材本身要合法，否则会把测试造物的缺陷记到产品头上。**

### 5.4 同名测试函数会被静默覆盖（本次自审发现）

写报告时核对用例名，发现 `test_ensure_upload_dir_creates_missing` 在文件里
**被定义了 3 次**（第 170 / 183 / 232 行，内容完全一致）。Python 后定义覆盖前定义，
pytest 只收集最后一个——**另外两份从未执行，且没有任何报错、没有任何警告**。

```python
def test_a(): ...   # 被覆盖，永不执行
def test_a(): ...   # 被覆盖，永不执行
def test_a(): ...   # 只有这一个生效
```

危险之处在于它**不会被任何机制拦下**：

| 可能拦住它的机制 | 实际情况 |
|---|---|
| pytest | 收集阶段按函数名去重，静默取最后一个 |
| 测试数量断言 | 只是总数变小，总数没人逐次比对 |
| 覆盖率 | 代码被执行了，覆盖率照常是绿的 |
| lint | ruff/pyflakes 对测试函数重定义不报 |

已删除两份重复定义（保留最干净的一份），`test_upload.py` 从 240 → 216 行。
删除后 `pytest` 总数仍为 189、upload 单文件仍为 14——因为被删的两份本来就没执行过，
**这恰好反证了它们从未发挥作用**。

**教训：测试文件里的重复定义是"隐形空转"，比测试失败更危险——失败的测试会喊，
被覆盖的测试永远安静。此类问题只能靠人工核对用例名发现。**

#### 已落地的检查器：`scripts/dev/check_duplicate_tests.py`

写完报告后判断这个坑还会再踩，直接把检查做出来了（AST 解析模块顶层的
`def test_*` / `async def test_*`，同名即报，退出码 1）。

两个方向都验证过，不是"写完就交"：

| 验证 | 输入 | 结果 |
|---|---|---|
| 能抓真问题 | `git show 2eef367:backend/tests/test_upload.py`（修复前版本） | `✗ test_ensure_upload_dir_creates_missing 定义了 3 次（行 170、183、232）`，退出码 **1** |
| 不误报 | 两个类里各有 `test_x` + 模块级 `test_a` / `test_b` | `0 处重名`，退出码 0 |

只查模块顶层是刻意的：类内方法各自独立命名空间，不同类有同名方法很正常
（`TestProductAPI` 和 `TestPartAPI` 都可能有一个 `test_list`），
一律报重名会产生大量噪音，最后没人看。

**覆盖范围与局限（需知悉）**：当前只扫 `test_*.py`，即后端 9 个 pytest 文件；
前端 vitest 的 `*.spec.js`（13 个文件）**不在覆盖内**。原因是 JS 里重名直接是语法错误
（`const` 重复声明 / 函数声明会被提升覆盖），vitest 的 `describe` 块天然隔离命名空间，
风险远低于 Python，但并非为零（同一 `describe` 内两次 `it` 同名会被静默合并）。
若后续前端也踩到，再扩展到 `.spec.js`。

## 6. 遗留与建议

| 项 | 性质 | 建议 |
|---|---|---|
| 上传目录权限未纳入启动自检 | 可改进 | `prepare-storage.sh --check` 可挂到发布流水线的 pre-flight 步骤 |
| 其他挂载目录（`data/pg`）同理 | 需关注 | 本次只处理了 uploads；`data/pg` 若属主不对，PG 会直接起不来，反而容易发现 |
| 磁盘写满 | 未处理 | 目录可写但磁盘满时，`open` 也可能失败。当前会归到 503，语义可接受，但日志里应能区分 `ENOSPC` |
| 上传目录容量上限 | 未做 | 无限增长，长期需要清理策略（一期可不动，但运维手册应提示定期归档） |
