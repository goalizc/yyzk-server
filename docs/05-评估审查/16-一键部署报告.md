# 一键部署报告

> 需求来源：用户要求「此系统的全链路部署是傻瓜式的，一键就能完成所有需要的操作」。
> 本文记录实现、验证与**发现的问题**，不只写结论。

## 1. 问题定义

改造前的首次部署需要 5 个步骤、涉及 4 个脚本和 1 次 `sudo`：

```bash
cp .env.example .env                 # 还要手工改 3 个密钥
mkdir -p data/pg data/uploads
sudo ./scripts/prepare-storage.sh    # ← 唯一需要 root 的一步
docker compose up -d
docker compose run --rm init
# 另外还要记得手动跑 ./scripts/install-cron.sh（很容易忘）
```

四个实际痛点：

| 痛点 | 后果 |
|---|---|
| 手工改 `.env` 密钥 | 有人会留 `ChangeMe_123456`，或把 base64 的 `/` 写进 `DATABASE_URL` |
| 需要 `sudo` | 用 root 跑会把 `.env`、`data/` 变成 root 属主，之后维护很痛苦 |
| 忘了跑 `init` | 后台进不去，报「用户名或密码错误」，很难联想到是没初始化 |
| 忘了注册 cron | 上传残留永不回收，几个月后磁盘满（见报告 15） |

## 2. 实现

新增两个脚本，共 4 个文件改动：

| 文件 | 作用 |
|---|---|
| `deploy/deploy.sh` | 一键部署主脚本，10 步，幂等 |
| `deploy/scripts/install-cron.sh` | 幂等注册每日清理任务 |
| `docs/04-运维与运营/运维手册.md` | 「0. 首次部署」改为一条命令，原流程降为附录 |
| `README.md` | 快速开始同步 |

### 2.1 关键设计：取消 sudo

第一版打算保留 `sudo prepare-storage.sh`，但那样脚本就得让用户输密码，
「一条命令」就打折了。换个思路：

```bash
docker compose run --rm --no-deps -u root -T backend \
  sh -c "chown -R 10001:10001 /data/uploads && chmod 775 /data/uploads"
```

backend 镜像里有 `chown`，挂载的 `/data/uploads` 就是宿主机目录，
**容器内 root 改属主等价于宿主机 root，但不要求调用者是 root**。

这样 `deploy.sh` 全程普通用户权限，`.env` 和 `data/` 都归用户自己。

### 2.2 幂等性

| 动作 | 重复执行时 |
|---|---|
| `.env` | 已存在则保留，只让 `harden.sh` 替换占位/弱值 |
| 建目录 | `mkdir -p` |
| 构建 | 增量，通常 10 秒内 |
| chown | 幂等 |
| `init` | 脚本内判断用户已存在则跳过，**不覆盖已改密码** |
| cron | 标记行 `# fault-system:cleanup-uploads` 过滤旧条目后重写 |

cron 的幂等要特别小心：直接 `crontab -l | { cat; echo "$ENTRY"; } | crontab -`
会每跑一次多一条。这里的做法是先 `grep -v` 掉本项目的旧条目（标记行 + 命令行两处），
**用户其它定时任务完整保留**。

## 3. 自审发现的问题

写完先自审，找到 4 个缺陷——其中第 1 个会让部署在不报错的情况下漏掉关键步骤。

### 3.1 `if cmd | tail` 吞掉退出码（严重）

原始写法：

```bash
if ! docker compose build 2>&1 | tail -5; then
  die "镜像构建失败"
fi
```

管道退出码取自**最后一个命令**（`tail`），`docker` 构建失败会被 `tail` 的 0 掩盖。
结果是**构建失败却显示「✓ 镜像构建完成」**，然后起服时用旧镜像，
排查方向会被彻底带偏。`up -d` 那处也一样。

改为先落文件再取退出码：

```bash
set +e
docker compose build >"$LOG" 2>&1
BUILD_RC=$?
set -e
tail -5 "$LOG"
if [[ "$BUILD_RC" != "0" ]]; then ... die ... fi
```

**反向验证**：注入 `--bogus-flag-xyz` 后重跑，脚本如期终止并打印
`unknown flag: --bogus-flag-xyz`。

### 3.2 第 10 步静默终止（严重）

第一次完整跑，`[10/10] 部署完成` 后面**什么都没有**，但退出码是 0。
原因在这一行：

```bash
[[ -n "$LAN_IP" ]] && echo "    局域网 ： http://$LAN_IP/"
```

`hostname -I` 在本机返回空（沙箱内无常规网络接口），条件为假时整行返回 1，
在 `set -e` 下终止脚本。后面的汇总信息全部没打印。

改为 `if` 显式分支，并对 `hostname -I` 返回空做兜底：

```bash
LAN_IP=$(hostname -I 2>/dev/null | awk '{print $1}') || LAN_IP=""
if [[ -n "$LAN_IP" ]]; then
  echo "    局域网 ： http://$LAN_IP/"
else
  echo "    局域网 ： 未能自动识别本机 IP，用 ip addr 查看后访问 http://<IP>/"
fi
```

> 这个 bug 的迷惑点：**退出码是 0**（末尾还有别的命令兜底），日志上看不出报错，
> 只是"少了一段输出"。如果没完整跑一次是发现不了的。

### 3.3 定时清理失败时提示不可操作

原写法 `bash scripts/install-cron.sh 2>&1 | tail -5 || warn "..."` 有两个问题：
一是又踩了管道吞退出码（`tail` 恒返回 0，`||` 永不触发）；
二是即使触发，只说「注册失败」，用户不知道该干嘛。

现在把真实输出接出来，并按失败类型给不同指引：

```
! 定时清理未注册（不影响系统运行，但上传残留将不再自动回收）
    /var/spool/cron/...: 权限不够

· 原因：当前环境不允许写 crontab（常见于容器内、受限沙箱）
    在真实主机的普通用户下执行即可注册：
      cd /opt/fault-system/deploy && ./scripts/install-cron.sh
    在注册成功前，请定期手动执行：./scripts/cleanup-uploads.sh --apply
```

关键是**明确告诉用户这不影响系统运行**——否则看到「失败」会以为部署没成。

### 3.4 长步骤无进度反馈

构建和等 healthy 是仅有的两个耗时步骤，输出被重定向后用户会以为卡死。
现在构建前给预期（「首次约 3–6 分钟」），等 healthy 用单行动态刷新：

```
· 等待服务就绪：db 就绪 / backend 启动中（已等 12s）
```

不用每轮打一行——健康检查每 10 秒一次，180 秒最多 60 行，会把有用信息冲掉。

| 步骤 | 结果 |
|---|---|
| 1 前置检查 | ✓ Docker 29.7.2 / Compose 5.5.1，磁盘 60G，端口 80 可用 |
| 2 `.env` | ✓ 已存在，保留现有配置（未覆盖） |
| 3 数据目录 | ✓ |
| 4 构建镜像 | ✓ 增量构建 |
| 5 上传目录属主 | ✓ 已修正为 10001:10001 |
| 6 启动服务 | ✓ db / backend healthy |
| 7 初始化管理员 | ✓ 已存在（未改动密码） |
| 8 健康验证 | ✓ `/health` 200 / SPA 200 / 鉴权 401 / 登录接口 401 |
| 9 注册 cron | ! 沙箱权限不足，按预期降级并给出指引 |
| 10 汇总 | ✓ 三段信息完整打印 |

退出码 0，三次结果一致。

### 4.2 参数与边界

| 场景 | 结果 |
|---|---|
| `--help` | 正确打印用法 |
| `--bogus` | 退出码 **2**，提示「未知参数」 |
| `--check` | 只体检不起服，退出码 0 |
| 构建失败（注入） | 退出码非 0，打印真实错误 + 排查建议 |
| 以 root 运行 | 警告但不中断 |

### 4.3 本次未能验证的项

| 项 | 原因 | 替代验证 |
|---|---|---|
| 真实 crontab 写入 | 沙箱 `/var/spool/cron` 无权限 | 抽离幂等算法单独验证：跑 3 次只留 1 条；`--time 04:15` 正确更新；用户原有条目（`backup-other.sh`、`MAILTO`）完整保留 |
| 局域网 IP 识别 | 沙箱内 `hostname -I` 返回空 | 已加兜底提示；真机上 `hostname -I` 正常返回 |

> **需要用户在真机执行的确认**：`cd deploy && ./scripts/install-cron.sh`，
> 然后 `./scripts/install-cron.sh --show` 应看到一条 `30 3 * * *` 的记录。

## 5. 踩到的坑

**缺陷注入后备份丢失**。反向验证时用了 `cp deploy.sh /tmp/deploy_bak.sh`，
验证完 `cp /tmp/deploy_bak.sh deploy.sh` 报「没有那个文件或目录」——
`/tmp` 在沙箱里不可靠（此前装依赖时也遇到过 `/tmp` 仅 10MB）。
好在注入点唯一，手工改回即可。

**教训**：注入缺陷的备份要落在仓库内可写目录（`$PWD/.tmp/`，已 gitignore），
不要用 `/tmp`。改完后必须 `grep` 全文确认无残留。

## 7. 剩余风险

1. **`--check` 不校验上传目录属主**：check 模式下用 `alpine:3` 探测属主，但若镜像未
   提前拉取会失败并静默跳过。可接受——`--check` 的定位是快速体检，不是完整验收。
2. **cron 依赖宿主机的 `cron` 服务在跑**：脚本只负责写 crontab，不检查 `cron` 守护进程
   是否 enabled。若服务器从未启用 cron，任务写了也不会执行。建议在 `--check` 里加一条，
   但需要考虑非 systemd 发行版，暂缓。
3. **`deploy.sh` 假设 `deploy/` 在仓库根下**：脚本用 `$DEPLOY_DIR` 定位，但
   `docker compose` 的 `context: ..` 依赖父目录结构。若有人单独拷 `deploy/` 出去会失败，
   属非常规用法，未加防护。
