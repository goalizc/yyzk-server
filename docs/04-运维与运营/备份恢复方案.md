# 备份与恢复方案

## 1. 备份范围
| 数据 | 位置 | 备份频率 | 保留 |
|---|---|---|---|
| PostgreSQL 数据库 | `./data/pg` | 每日 03:00 | 30 天 |
| 上传附件 | `./data/uploads` | 每日 03:00（同一脚本，紧随数据库之后） | 30 天 |
| 配置文件（.env, docker-compose.yml, nginx.conf） | deploy 目录 | 每次变更 | Git 版本管理 |

> 数据库与附件在同一脚本内串行完成，不拆成两个时点（原文档写 03:30 单独跑附件，但脚本与 cron 都没有这一条，已统一）。

## 2. 自动备份脚本

创建 `/opt/fault-system/backup.sh`：

```bash
#!/bin/bash
# -u 未定义变量报错；-o pipefail 保证管道中 pg_dump 失败不会被 gzip 掩盖
set -euo pipefail

BACKUP_DIR="/opt/fault-system/backups"
DATE=$(date +%Y%m%d_%H%M%S)
RETENTION_DAYS=30
DB_USER="${DB_USER:-fault}"
DB_NAME="${DB_NAME:-fault_db}"

cd /opt/fault-system
mkdir -p "$BACKUP_DIR"

# 1. 数据库备份（临时文件 + 校验后再改名为正式文件）
TMP_DB="$BACKUP_DIR/.db_$DATE.sql.gz.tmp"
docker compose exec -T db pg_dump -U "$DB_USER" "$DB_NAME" | gzip > "$TMP_DB"
gzip -t "$TMP_DB"                                    # 校验 gzip 完整性
[ "$(stat -c%s "$TMP_DB")" -gt 1024 ] || { echo "[ERROR] db dump 过小，疑似失败"; rm -f "$TMP_DB"; exit 1; }
mv "$TMP_DB" "$BACKUP_DIR/db_$DATE.sql.gz"

# 2. 附件备份
TMP_UP="$BACKUP_DIR/.uploads_$DATE.tar.gz.tmp"
tar czf "$TMP_UP" -C /opt/fault-system data/uploads
tar tzf "$TMP_UP" > /dev/null                        # 校验可读
mv "$TMP_UP" "$BACKUP_DIR/uploads_$DATE.tar.gz"

# 3. 清理过期备份
find "$BACKUP_DIR" -name "db_*.sql.gz" -mtime +$RETENTION_DAYS -delete
find "$BACKUP_DIR" -name "uploads_*.tar.gz" -mtime +$RETENTION_DAYS -delete

echo "[$(date '+%F %T')] Backup completed: $DATE"
```

加执行权限：
```bash
chmod +x /opt/fault-system/backup.sh
```

> 关键点：`set -e` 单独用不够 —— `pg_dump | gzip` 是管道，最后退出码取 `gzip`，db 挂了也会"成功"生成几十字节的空文件。
> 脚本已改为 `set -euo pipefail` + `gzip -t` + 体积下限三重校验。

## 3. 配置定时任务

```bash
crontab -e
```

添加：
```
0 3 * * * cd /opt/fault-system && ./backup.sh >> /var/log/fault-backup.log 2>&1
```

### 3.1 备份失败告警

脚本失败会返回非 0，但 cron 默认只发本地邮件（干净 Ubuntu 没有 mailutils，等同静默）。至少补一道检查任务，检查**数据库与附件两类**都生成过：

```
30 3 * * * cd /opt/fault-system && \
  for p in "db_$(date +\%Y\%m\%d)_*.sql.gz" "uploads_$(date +\%Y\%m\%d)_*.tar.gz"; do \
    ls backups/$p >/dev/null 2>&1 || echo "[ALERT] 备份缺失: $p on $(date)" >> /var/log/fault-backup-alert.log; \
  done
```

若服务器已装 `mail` 或 `msmtp`，可在上述命令末尾追加 `| mail -s "备份告警" ops@example.com`；
没有邮件服务时，至少保证告警落到独立日志文件：

```bash
tail -50 /var/log/fault-backup.log
cat /var/log/fault-backup-alert.log
ls -lh /opt/fault-system/backups | tail -5
```

### 3.2 时区注意
备份窗口按容器/宿主机本地时区触发（`TZ=Asia/Shanghai`）。
`pg_dump` 导出的 `TIMESTAMPTZ` 带时区信息，恢复后展示正常；**不要手工改时区再恢复**，否则历史数据会整体偏移 8 小时。

## 4. 恢复流程

> ⚠️ 坑点：`schema.sql` 已在 initdb 时建好表。若直接 `psql < dump`，所有 `CREATE TABLE` 都会冲突；
> 而 `psql` 默认遇错继续，最后仍返回 0 —— 看起来成功，其实一条数据都没进去。
> 因此恢复**必须先清空 public schema**，并加 `ON_ERROR_STOP=1`。

### 4.1 数据库恢复
```bash
cd /opt/fault-system

# 1. 停后端，避免写入
docker compose stop backend

# 2. 备份当前库（防止恢复错了）
docker compose exec -T db pg_dump -U fault fault_db | gzip > /tmp/pre-restore_$(date +%Y%m%d_%H%M%S).sql.gz

# 3. 清空现有结构（关键步骤）
docker compose exec -T db psql -U fault -d fault_db -v ON_ERROR_STOP=1 \
  -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"

# 4. 恢复指定备份
gunzip -c backups/db_20261020_030000.sql.gz | \
  docker compose exec -T db psql -U fault -d fault_db -v ON_ERROR_STOP=1

# 5. 校验（应与备份前一致）
docker compose exec db psql -U fault -d fault_db \
  -c "SELECT (SELECT count(*) FROM faults) AS faults, (SELECT count(*) FROM tickets) AS tickets, (SELECT count(*) FROM users) AS users;"

# 6. 启动服务
docker compose start backend
```

### 4.2 附件恢复
```bash
cd /opt/fault-system
tar xzf backups/uploads_20261020_030000.tar.gz
chown -R 1000:1000 data/uploads    # uid 与 backend 镜像运行用户保持一致
```

### 4.3 整机迁移
新服务器上：
1. 安装 Docker 与 Compose
2. 拷贝 deploy 目录、backups 目录，`mkdir -p data/pg data/uploads`
3. 配置 `.env`
4. **先让 db 起一个空库**：临时把 compose 里 `./schema.sql:/docker-entrypoint-initdb.d/01-schema.sql` 这行注释掉，再 `docker compose up -d db`
5. 按 §4.1 恢复数据库（此时 public schema 为空，可直接 `psql` 导入，无需 DROP）
6. 按 §4.2 恢复附件
7. 恢复 compose 的 schema 挂载，`docker compose up -d` 启动全部服务
8. `docker compose run --rm init` 补建管理员（若备份里已含 users 记录，此步会跳过）

## 5. 备份验证
**每月一次恢复演练**（在测试环境做，不碰生产）：
- 用最近备份按 §4.1 完整恢复一次
- 校验数据量：产品数、故障数、工单数、`query_logs` 行数
- 校验附件可下载（抽查 3 个 `/uploads/*` 链接）
- 校验工单流转历史条数不为 0
- 记录恢复耗时，与 RTO 对比

## 6. 灾难恢复 RTO/RPO
| 指标 | 目标 |
|---|---|
| RTO（恢复时间目标） | < 4 小时 |
| RPO（数据丢失容忍） | < 24 小时（每日备份） |

> 单机部署无主从，服务器整体故障时 RTO 取决于「采购新机 + 恢复」，实际可能超过 4 小时。若要严格达标，需加一台备用机或改为云主机快照。
