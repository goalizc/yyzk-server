# 备份与恢复方案

## 1. 备份范围
| 数据 | 位置 | 备份频率 | 保留 |
|---|---|---|---|
| PostgreSQL 数据库 | `./data/pg` | 每日 03:00 | 30 天 |
| 上传附件 | `./data/uploads` | 每日 03:00（同一脚本，紧随数据库之后） | 30 天 |
| 配置文件（.env, docker-compose.yml, nginx.conf） | deploy 目录 | 每次变更 | Git 版本管理 |

> 数据库与附件在同一脚本内串行完成，不拆成两个时点（原文档写 03:30 单独跑附件，但脚本与 cron 都没有这一条，已统一）。

## 2. 自动备份脚本

脚本在仓库内：**`deploy/scripts/backup.sh`**（不再是文档里的代码块，直接可用）。

```bash
cd deploy

./scripts/backup.sh                      # 备份到 deploy/backups
./scripts/backup.sh --dir /mnt/nas/bak   # 备份到另一块盘（强烈建议）
./scripts/backup.sh --retention 7        # 保留 7 天（默认 30）
./scripts/backup.sh --dry-run            # 只打印动作，不落盘
```

产物：
- `db_YYYYmmdd_HHMMSS.dump` — `pg_dump -Fc` 自定义格式，支持并行/选择性恢复
- `uploads_YYYYmmdd_HHMMSS.tar.gz` — 附件目录

### 2.1 脚本做的四道防护

| 防护 | 为什么必须有 |
|---|---|
| `set -euo pipefail` | `pg_dump \| gzip` 的退出码取 gzip，db 挂了也返回 0 |
| 体积下限 1KB | 空库结构也有几 KB，低于此值必然是失败产物 |
| 文件头魔数 `PGDMP` | 确保不是空文件或被截断的内容 |
| 先写 `.tmp` 再 `mv` | 半截文件不会被当成有效备份 |

> **实测记录（2026-10-21）**：故意用不存在的库名执行，脚本正确返回 `exit 1`
> 并清理 `.tmp`，不会留下"看起来成功"的假备份。

### 2.2 环境变量优先级

脚本先读 `deploy/.env`，但**调用时显式传入的 `DB_USER` / `DB_NAME` 优先**，
方便排查问题时指向别的库。这一条曾写错（`source .env` 覆盖了调用方变量），
导致错误库名也能"备份成功"，已修。

## 3. 配置定时任务

```bash
crontab -e
```

添加（路径按实际部署目录改）：
```
0 3 * * * cd /opt/fault-system/deploy && ./scripts/backup.sh --dir /mnt/nas/bak >> /var/log/fault-backup.log 2>&1
```

### 3.1 备份失败告警

脚本失败会返回非 0，但 cron 默认只发本地邮件（干净 Ubuntu 没有 mailutils，等同静默）。至少补一道检查任务，检查**数据库与附件两类**都生成过：

```
30 3 * * * cd /opt/fault-system/deploy && \
  for p in "db_$(date +\%Y\%m\%d)_*.dump" "uploads_$(date +\%Y\%m\%d)_*.tar.gz"; do \
    ls backups/$p >/dev/null 2>&1 || echo "[ALERT] 备份缺失: $p on $(date)" >> /var/log/fault-backup-alert.log; \
  done
```

若服务器已装 `mail` 或 `msmtp`，可在上述命令末尾追加 `| mail -s "备份告警" ops@example.com`；
没有邮件服务时，至少保证告警落到独立日志文件：

```bash
tail -50 /var/log/fault-backup.log
cat /var/log/fault-backup-alert.log
ls -lh /opt/fault-system/backups | tail -5
```

### 3.2 时区注意
备份窗口按容器/宿主机本地时区触发（`TZ=Asia/Shanghai`）。
`pg_dump` 导出的 `TIMESTAMPTZ` 带时区信息，恢复后展示正常；**不要手工改时区再恢复**，否则历史数据会整体偏移 8 小时。

## 4. 恢复流程

恢复脚本在仓库内：**`deploy/scripts/restore.sh`**。

```bash
cd deploy

./scripts/restore.sh --db backups/db_20261021_030000.dump
./scripts/restore.sh --db backups/db_xxx.dump --uploads backups/uploads_xxx.tar.gz
./scripts/restore.sh --db backups/db_xxx.dump --dry-run    # 只校验，不动数据
```

### 4.1 脚本自动处理的四个坑

这些坑手工恢复时几乎必踩，脚本已内建：

| 坑 | 脚本的处理 |
|---|---|
| 直接 `pg_restore` 会与 `schema.sql` 建好的表冲突，且默认遇错继续、最后返回 0 | **先 `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`**，再用 `--exit-on-error` |
| 恢复错了无法回头 | **恢复前自动备份当前库**到 `db_pre-restore_*.dump` |
| `docker compose exec ... < file` 让宿主机重定向进 stdin 在某些组合下拿不到内容且不报错 | 改成 **`docker cp` 进容器后用本地路径**恢复 |
| 附件 tar 遇到已存在文件会报错退出；跨机器还原原 uid 会失败 | 先把现有附件移开；解包用 `--no-same-owner --no-same-permissions --touch` |

恢复后脚本会**立即做行数自检**（users/products/faults/query_logs），
`users` 为空直接判定失败——恢复出一个无法登录的系统没有意义。

### 4.2 手工恢复（脚本不可用时）

```bash
cd deploy

# 1. 停后端，避免写入
docker compose stop backend

# 2. 备份当前库（防止恢复错了）
docker compose exec -T db pg_dump -U fault -Fc fault_db > backups/db_pre_$(date +%Y%m%d_%H%M%S).dump

# 3. 清空现有结构（关键步骤，跳过必冲突）
docker compose exec -T db psql -U fault -d fault_db -v ON_ERROR_STOP=1 \
  -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"

# 4. 恢复（先把文件拷进容器，用本地路径读）
docker cp backups/db_20261021_030000.dump fault-db:/tmp/r.dump
docker compose exec -T db pg_restore -U fault -d fault_db \
  --no-owner --no-privileges --exit-on-error /tmp/r.dump

# 5. 校验（应与备份前一致）
docker compose exec db psql -U fault -d fault_db \
  -c "SELECT (SELECT count(*) FROM faults) AS faults, (SELECT count(*) FROM tickets) AS tickets, (SELECT count(*) FROM users) AS users;"

# 6. 启动服务
docker compose start backend
```

### 4.3 附件恢复（手工）

```bash
cd deploy
mv data/uploads data/uploads.old && mkdir -p data/uploads
tar xzf backups/uploads_20261021_030000.tar.gz -C . --no-same-owner --no-same-permissions --touch
chown -R 10001:10001 data/uploads    # uid 与 backend 容器运行用户一致
rm -rf data/uploads.old              # 确认无误后再删
```

### 4.4 整机迁移
新服务器上：
1. 安装 Docker 与 Compose
2. 拷贝整个仓库（含 `deploy/` 与 `backups/`），`mkdir -p deploy/data/pg deploy/data/uploads`
3. 配置 `deploy/.env`（**注意 `/data/uploads` 的 uid 10001 权限**）
4. 起 db：`docker compose up -d db`（此时 `schema.sql` 会建出空表结构，
   这没关系——`restore.sh` 会先 DROP 再恢复）
5. `./scripts/restore.sh --db backups/db_xxx.dump --uploads backups/uploads_xxx.tar.gz`
6. `docker compose up -d` 启动全部服务
7. `docker compose run --rm init` 补建管理员（若备份里已含 users 记录，此步会跳过）

> 第 4 步不再需要"注释掉 schema.sql 挂载"：脚本的 `DROP SCHEMA public CASCADE`
> 已经把空表结构清掉了。这一步是旧流程的残留复杂度，可以省。

## 5. 备份验证

**每月一次恢复演练**（在测试环境做，不碰生产）：

```bash
cd deploy
# 1. 记下当前行数
docker compose exec db psql -U fault -d fault_db -t -A -c \
  "SELECT (SELECT count(*) FROM faults), (SELECT count(*) FROM tickets), (SELECT count(*) FROM users);"

# 2. 用最近备份恢复（--dry-run 先校验文件）
./scripts/restore.sh --db backups/db_LATEST.dump --uploads backups/uploads_LATEST.tar.gz
```

验收要点：
- 脚本输出的行数与第 1 步一致
- 抽 3 个 `/uploads/*` 链接能打开
- 工单流转历史条数不为 0
- 记录耗时，与 RTO 对比

> **实测记录（2026-10-21，本机 docker）**：
> 基线 `users=1 products=2 faults=6 tickets=7 query_logs=21` → 故意删掉 2 条故障
> （faults 降为 4）→ 执行 `restore.sh` → **faults 恢复为 6、附件 2 个文件回来了、
> backend 健康，全程 9 秒**。远低于 RTO 4 小时。

## 6. 灾难恢复 RTO/RPO
| 指标 | 目标 |
|---|---|
| RTO（恢复时间目标） | < 4 小时 |
| RPO（数据丢失容忍） | < 24 小时（每日备份） |

> 单机部署无主从，服务器整体故障时 RTO 取决于「采购新机 + 恢复」，实际可能超过 4 小时。若要严格达标，需加一台备用机或改为云主机快照。
