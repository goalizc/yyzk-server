# 运维手册

## 0. 首次部署

### 一条命令

```bash
cd /opt/fault-system/deploy
./deploy.sh
```

就这一条。脚本会依次完成 10 个动作，**重复执行安全**（幂等）：

| 步骤 | 做什么 | 说明 |
|---|---|---|
| 1 | 检查前置条件 | docker、compose v2、docker 权限、磁盘 ≥5G、端口 80 |
| 2 | 准备 `.env` | 不存在则从 `.env.example` 创建，并把占位密码换成随机强值 |
| 3 | 建数据目录 | `data/pg`、`data/uploads` |
| 4 | 构建镜像 | 首次约 3–6 分钟，之后增量通常 10 秒内 |
| 5 | 修正上传目录属主 | **容器内** chown 到 10001，不需要宿主机 sudo |
| 6 | 启动服务 | 等 db healthy → **迁移前备份 → 执行迁移** → 起全部服务 → 等 backend healthy |
| 7 | 初始化管理员 | 幂等，不覆盖已改过的密码 |
| 8 | 健康验证 | `/health`、SPA 首页、鉴权校验、登录接口 |
| 9 | 注册每日清理 | 回收上传残留，见 §7.4 |
| 10 | 打印访问地址 | 含管理员账号与常用命令 |

跑完会打印本机与局域网访问地址。**首次登录后立即在后台「顶栏 → 修改密码」更换初始密码。**

**不要用 `sudo` 运行。** 以 root 跑会让 `.env` 归 root 所有，之后普通用户改不了；
需要 root 的唯一动作（改上传目录属主）已经改成在容器内执行，所以普通用户就够了。

### 其它用法

```bash
./deploy.sh --check      # 体检：只查环境、配置、健康状态，不改任何东西
./deploy.sh --rebuild    # 强制重建镜像（改了后端/前端代码后用）
./deploy.sh --skip-cron  # 不注册定时清理（改用人工或 systemd timer）
```

> `--check` 适合巡检和排障：它会告诉你哪些前提不满足、哪些接口不通，
> 但不会构建镜像、不会起服、不会改文件。

### 手动部署（脚本不可用时的兜底）

<details>
<summary>展开查看逐步操作</summary>

```bash
cd /opt/fault-system
cp .env.example .env

# 1. 改三个必填项：DB_PASSWORD / JWT_SECRET / ADMIN_INIT_PASSWORD
#    DB_PASSWORD : openssl rand -hex 24   （不要用 base64，含 / 会破坏 DATABASE_URL）
#    JWT_SECRET  : openssl rand -hex 32
vi .env

# 2. 预建数据目录 + 修正上传目录属主
mkdir -p data/pg data/uploads
sudo ./scripts/prepare-storage.sh

# 3. 起 db 并等健康
docker compose up -d db

# 4. 迁移前备份（迁移会删除 products.category，不可逆）
./scripts/backup.sh

# 5. 执行数据库迁移（必须先于 backend 启动）
docker compose run --rm migrate

# 6. 起全部服务
docker compose up -d

# 7. 初始化管理员账号（必须在首次访问后台前执行）
docker compose run --rm init

# 8. 注册每日清理（回收上传残留）
./scripts/install-cron.sh

# 9. 验证
curl -s http://localhost/health          # 期望 ok
docker compose ps                        # 期望 4 个容器 running，db/backend 为 healthy
```

`prepare-storage.sh` 会 chown 到 10001 并以真实写文件验证，幂等、可重复执行；
`--check` 只检查不改，适合巡检。它与 `deploy.sh` 第 5 步等价，区别是后者不需要 sudo。

</details>

> **为什么上传目录属主这么关键**：`data/uploads` 是宿主机目录挂载，会覆盖镜像里
> 的 chown，最终属主取决于这个目录**在宿主机上是哪个 uid 建的**。backend 容器以
> uid 10001 运行，属主不对就写不进去，表现为**后台上传图片/附件失败**（返回 503）。

> **为什么管理员要单独初始化**：bcrypt 哈希只能在运行时生成，`schema.sql` 里不写死密码。
> 脚本通过 `./scripts:/app/scripts` 挂载进容器，无需打进镜像。
> 这一步是幂等的，重复执行不会覆盖已改过的密码；未设置 `ADMIN_INIT_PASSWORD` 会直接退出（码 2），**没有默认口令**。

> **`.env` 里的 `ADMIN_INIT_PASSWORD` 是初始密码**，只在首次创建账号时用一次。
> 之后在后台改密码**不会回写** `.env`。所以重复执行 `deploy.sh` 时如果第 8 步
> 提示「用 .env 里的密码登录失败」，那是正常的——用你记得的密码登录即可；
> 忘了就跑 `docker compose run --rm init user passwd admin` 重设。

> 下文所有 `psql -U fault -d fault_db` 均按 `.env` 的默认值书写；若你改了 `DB_USER` / `DB_NAME`，请自行替换。

## 1. 日常操作

### 查看服务状态
```bash
cd /opt/fault-system
docker compose ps
```

### 查看日志

三层日志各管一件事，别混用：

| 层 | 位置 | 用来回答 |
|---|---|---|
| 操作审计 | 后台「操作日志」页 / `audit_logs` 表 | **谁**在什么时候做了什么、结果如何 |
| 后端运行日志 | `docker compose logs backend`（JSON 单行） | 某个请求为什么报错、耗时多少 |
| Nginx 访问日志 | `docker compose logs nginx` | 请求有没有到服务器、来源 IP、上游耗时 |

```bash
# 后端日志（结构化 JSON，可按 request_id / path / status 过滤）
docker compose logs -f backend
docker compose logs backend | grep '"status": 500'
docker compose logs backend | grep '"request_id": "8f3c..."'

# Nginx 日志（含 rid= 与上游耗时 urt=）
docker compose logs -f nginx

# 数据库日志
docker compose logs -f db
```

> **前后端日志可以按同一个 id 串起来**：Nginx 会把 `$request_id` 通过
> `X-Request-ID` 传给后端，后端沿用同一个值。Nginx 里看到 `rid=abc123`，
> 直接 `docker compose logs backend | grep abc123` 就能拿到这条请求的全部细节。
>
> ⚠ 从**宿主机本机**用 `curl localhost` 访问时，Nginx 看到的源 IP 是 Docker 网关
> （172.18.0.1），不是你的真实 IP；从局域网其它机器访问则记录真实来源 IP。

### 查「谁做了什么」（操作审计）

后台左侧「操作日志」（需要 `audit:read`，超管/主管/只读审计有，一线客服没有）。

三种典型查法：

```bash
# 1) 某个人最近干了什么（UI：账号筛选 + 时间范围；或直接查库）
docker compose exec db psql -U fault -d fault_db -c "
SELECT created_at, username, action, target_type, target_id, target_name, result
FROM audit_logs WHERE username = 'kefu01' ORDER BY created_at DESC LIMIT 50;"

# 2) 某条故障/工单被谁改过（UI：关键词填对象名）
docker compose exec db psql -U fault -d fault_db -c "
SELECT created_at, username, action, detail FROM audit_logs
WHERE target_type = 'fault' AND target_id = '7' ORDER BY created_at;"

# 3) 账号是不是被多人共用：看同一账号的 IP 分布
docker compose exec db psql -U fault -d fault_db -c "
SELECT username, ip, count(*) AS n, min(created_at) AS first, max(created_at) AS last
FROM audit_logs WHERE action = 'auth.login' AND result = 'success'
  AND created_at > now() - interval '30 days'
GROUP BY username, ip ORDER BY username, n DESC;"
```

第 3 条是排查账号外传的主路径：**一个账号在 30 天内出现多个互不相干的 IP**，
基本可以判定密码被给了别人。确认后立刻在「用户管理」里停用账号或重置密码
（重置会 bump `token_version`，该账号所有已登录端立刻失效）。

**保留期**：默认 180 天，每日 03:30 由 `./scripts/cleanup-audit.sh --apply` 回收。
手动预演（只看不删）：

```bash
./scripts/cleanup-audit.sh              # 报告待删条数
./scripts/cleanup-audit.sh --days 90 --apply
```

> 保留期下限 30 天：脚本会拒绝更小的值，避免手滑把近期记录删光。

### 重启服务
```bash
# 重启全部
docker compose restart

# 只重启后端
docker compose restart backend
```

### 更新版本
```bash
# 拉新代码后
cd /opt/fault-system
docker compose down

# 1) 先备份（迁移可能不可逆）
./deploy/scripts/backup.sh

# 2) 构建并迁移，再起服务
docker compose build
docker compose up -d db && sleep 5
docker compose run --rm migrate
docker compose up -d
```

> 顺序不能反：`/api/health` 只做 `SELECT 1`，旧表结构也能返回 ok。若先起 backend，新代码会在迁移前对外提供 500。

## 2. 常见问题排查

### 问题：访问页面 502
**排查步骤**：
1. `docker compose ps` 看 backend 是否 running
2. `docker compose logs backend` 看报错
3. 常见原因：数据库没起来 → `docker compose up -d db` 再重启 backend

### 问题：数据库连不上
**排查步骤**：
1. `docker compose logs db` 看是否 healthy
2. 检查 `.env` 里 DB_PASSWORD 是否和 db 容器环境变量一致
3. 如果数据卷损坏，不要删，先备份再排查

### 问题：上传附件后 404
**排查步骤**：
1. 检查 `./data/uploads` 目录是否存在
2. 检查 Nginx 配置里 `/uploads/` alias 路径
3. 检查 backend 容器内 UPLOAD_DIR 是否和挂载卷对应

### 问题：上传图片/附件失败（提示"服务器内部错误"或"暂时无法保存文件"）
**症状**：后台编辑故障时，解决步骤里点「上传图片」报错，附件上传同样失败。
**根因**：`data/uploads` 是宿主机挂载目录，属主不是容器运行的 uid 10001，
后端写不进去。日志里能看到：
```
PermissionError: [Errno 13] Permission denied: '/data/uploads/.xxxx.png.part'
```

**排查与修复**：
```bash
cd /opt/fault-system

# 1. 确认属主（应为 10001:10001）
ls -ldn data/uploads
docker compose exec backend ls -ldn /data/uploads

# 2. 一键修正并验证可写（幂等）
sudo ./scripts/prepare-storage.sh

# 3. 重新验证
docker compose exec backend touch /data/uploads/.probe && echo 可写
docker compose exec backend rm -f /data/uploads/.probe
```

> 这个目录是**挂载点**，容器内无法 rename/rmdir（报 `Device or resource busy`），
> 应用层也改不了它的属主（非 root 运行）。所以修复只能在宿主机做——
> 这也是为什么要把 `prepare-storage.sh` 写进部署流程。

> **错误码对照**：改造前这类故障返回 `500 INTERNAL_ERROR`（用户只看到"服务器内部错误"，
> 无法判断是权限问题）；现在返回 `503 SERVICE_UNAVAILABLE` + 中文提示，
> 运维看到 503 就应先查目录权限。

### 问题：页面样式错乱
**排查步骤**：
1. 强刷浏览器（Ctrl+Shift+R）
2. 检查 frontend 容器是否正常构建
3. `docker compose exec frontend ls /usr/share/nginx/html` 看静态文件是否在

### 问题：后台登录返回 401（密码确认没输错）
**排查步骤**：
1. 是否执行过 `docker compose run --rm init`？未初始化时 `users` 表为空
2. `docker compose exec db psql -U fault -d fault_db -c "SELECT username, role, is_active FROM users;"`
3. 表里没有记录 → 执行初始化；有记录但忘记密码 → `docker compose run --rm init --reset-password`
4. 确认 `.env` 的 `ADMIN_INIT_PASSWORD` 与登录时输入的一致（重置后会用它覆写）

### 问题：刷新 /admin 下的深层路由出现 404
**排查步骤**：
1. 确认 frontend 镜像里的 `/etc/nginx/conf.d/default.conf` 使用了 `try_files $uri $uri/ /index.html`
2. 参考 `deploy/frontend-nginx.conf`，重新构建 frontend 镜像

### 问题：上传大文件返回 413
**排查步骤**：
1. Nginx `client_max_body_size` 为 20M（`deploy/nginx.conf`）
2. 后端 `MAX_UPLOAD_MB` 环境变量也需为 20
3. 两处都改后 `docker compose up -d --force-recreate nginx backend`

### 问题：磁盘空间被 `data/uploads` 占满

**原因**：上传与删除是两个独立动作，中途没走完就会留下孤儿文件。
典型场景——上传后关页面、编辑时换了图、保存校验失败、删了步骤没保存。
这些情况后端无从得知，只能靠定期扫描回收。

**排查**：
```bash
du -sh deploy/data/uploads                   # 目录实际占用
ls -la deploy/data/uploads | wc -l           # 文件个数

cd deploy
./scripts/cleanup-uploads.sh                 # 先预演，只看不删
```

预演会打印「目录内文件总数 / 库中被引用数 / 待清理列表」。
确认列表里确实都是废弃文件后：

```bash
./scripts/cleanup-uploads.sh --apply
```

**关键参数**：
- `--min-age 60`（默认）：只清 60 分钟前的文件。**不要改成 0**——
  刚上传还没保存的图会被误删，用户点保存时就看到 404。
- `--max-ratio 0.5`（默认）：待删过半时拒绝执行，说明引用扫描可能失效
  （比如表结构改了），此时应先查代码而不是调大这个值。

**建议挂定时任务**（见 `docs/04-运维与运营/运维脚本说明.md` §4）。

> 若脚本报「拒绝执行」，说明待删比例异常，**不要直接加 --max-ratio 绕过**。
> 先跑预演确认「库中被引用文件名数」是否合理——如果这个数是 0 但库里明明有图，
> 说明引用扫描坏了，此时删除会造成大面积图片丢失。

## 3. 数据库操作

### 进入数据库
```bash
docker compose exec db psql -U fault -d fault_db
```

### 常用查询
```sql
-- 查看所有产品
SELECT * FROM products;

-- 查看某产品下的故障数
SELECT p.name, COUNT(f.id) 
FROM products p LEFT JOIN faults f ON p.id = f.product_id 
GROUP BY p.id;

-- 查看待处理工单
SELECT ticket_no, contact, created_at FROM tickets WHERE status = 'open';

-- 查看未命中查询
SELECT raw_query, COUNT(*) FROM query_logs 
WHERE hit = false AND raw_query IS NOT NULL 
GROUP BY raw_query ORDER BY COUNT(*) DESC LIMIT 20;
```

### 数据库迁移

迁移文件在 `deploy/migrations/`，执行记录在 `schema_migrations` 表。`deploy.sh` 与 `restore.sh` 已内置迁移，手工操作时按下面步骤：

```bash
cd /opt/fault-system/deploy

# 1) 迁移前必须备份（001 迁移会删除 products.category，不可逆）
./scripts/backup.sh

# 2) 执行（必须先起 db 并等 healthy）
docker compose up -d db
docker compose run --rm migrate

# 3) 查看已应用版本
docker compose exec db psql -U fault -d fault_db \
  -c "SELECT version, applied_at FROM schema_migrations ORDER BY version;"
```

- 迁移逐个文件在事务中执行，失败即退出非零码，不会留下半截结构；失败时不要起 backend，先看输出。
- 重复执行安全：已记录版本会跳过。
- **恢复后必须迁移**：`restore.sh` 是整库还原，若还原的是迁移前备份，库结构停留在旧版本。恢复脚本末尾已执行迁移；若手工用 `pg_restore` 还原，必须补跑 `docker compose run --rm migrate`，否则新代码对旧表。
- **回滚**：不写反向迁移脚本，以「备份还原 + 回退镜像」为准。

### 修改 admin 密码

**方式一（推荐）**：登录后台 → 顶栏用户下拉 → 修改密码。用户自助完成，无需运维介入。

**方式二：忘记密码时重置（用脚本，别手打 SQL）**
```bash
cd deploy

# 重置为 .env 中 ADMIN_INIT_PASSWORD 的值
docker compose run --rm init --reset-password

# 或给任意账号重置（自动生成随机密码并打印一次）
docker compose run --rm init user passwd admin
```

手工拼 bcrypt 哈希再 UPDATE 也能做，但哈希里含 `$`，在 shell 里容易被吃字符，
脚本已经处理好了。

### 账号维护（界面为主，脚本兜底）

**日常操作走后台 P-18 用户管理**（仅超级管理员 `user:write`）：

- 新建账号、修改姓名/角色、停用/启用、重置密码
- 分配产品线（支持长期与到期时间）
- 发放/收回临时授权（权限码、到期时间、事由）
- 不提供删除用户，只能停用；历史工单与流转记录保留归属

> 角色固定四种：`super_admin`（超管）、`supervisor`（售后主管）、`agent`（一线客服）、`auditor`（只读审计）。**权限按权限码实时生效**：停用、改角色、临时授权到期均在下一个请求生效。不要再用 `role` 手工做访问控制。

**脚本兜底（界面不可用 / 忘记密码 / 批量运维时）**：`deploy/scripts/init_admin.py`，通过 compose 的 `init` 服务调用。

```bash
cd deploy

docker compose run --rm init user list                      # 列出全部账号
docker compose run --rm init user add li --real-name 李工    # 新建客服（密码自动生成并打印一次）
docker compose run --rm init user add zhang --password 指定密码 --role supervisor
docker compose run --rm init user disable li                # 停用（离职）
docker compose run --rm init user enable li                 # 启用
docker compose run --rm init user passwd li                 # 重置密码
```

> **为什么停用而不是删除**：`tickets.assignee_id` 与 `ticket_status_logs.operator_id`
> 都指向 `users.id`，删账号会让历史工单的"谁处理的"变成悬空外键。
> 停用后 `is_active=false`，登录被拒且已签发 token 立即失效，但历史记录完整。

> 脚本的 `--role` 支持四个角色值；全新部署创建的管理员固定为 `super_admin`。
> 产品线与临时授权目前需在界面维护，脚本不提供。

### 停用立即生效（已实测）

`deps.py` 在**每次请求**都会查库校验 `is_active`，不只是登录时校验。所以停用账号后：

- 该账号新登录 → 403 `AUTH_USER_DISABLED`
- 该账号**已签发的 token** 访问受保护端点 → 同样 403，不用等 token 过期

> 旧版本文档写"已签发 token 在过期前仍可用（最长 24 小时）"，**这是错的**。
> 2026-10-21 实测：登录拿 token → 停用 → 用同一 token 请求 `/api/admin/tickets` → 403。
> 这点很重要：客服离职当天停用，权限当天收回，不存在 24 小时空窗。

## 4. 监控指标

### 磁盘空间
```bash
df -h
```
关注：`/` 分区剩余空间，低于 20% 要清理。

### 容器资源
```bash
docker stats
```
关注：
- backend：CPU < 50%，内存 < 1G
- db：内存 < 2G
- frontend/nginx：内存 < 100M

### 慢查询
```bash
docker compose exec db psql -U fault -d fault_db -c "SELECT query, mean_exec_time FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10;"
```
（`pg_stat_statements` 需要两件事：db 启动时 `shared_preload_libraries` 预加载（已在 compose 配好），以及库内执行 `CREATE EXTENSION`（`schema.sql` 已包含）。已有旧库升级时可能缺扩展，按下述 SQL 补建）

```sql
-- 若报 "relation pg_stat_statements does not exist"，先执行一次：
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
```
