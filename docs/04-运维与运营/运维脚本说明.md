# 运维脚本清单

> 位置：`deploy/scripts/`
> 这些脚本不是"文档里的参考代码"，是**实际跑过并验证过**的可执行文件。
> 每个脚本的关键决策都写在了源码注释里，改之前先读注释。

## 一览

| 脚本 | 用途 | 对应验收项 |
|---|---|---|
| `init_admin.py` | 初始化管理员 + 账号维护（列表/新建/停用/启用/重置密码） | 用户管理、安全验收 |
| `prepare-storage.sh` | 修正 `data/uploads` 属主并验证可写（起服前置） | 运维验收：上传可用 |
| `cleanup-uploads.sh` | 回收无人引用的上传残留文件（默认预演） | 运维验收：磁盘不无限增长 |
| `backup.sh` | 数据库 + 附件备份，带三重校验与过期清理 | 运维验收：每日备份 |
| `restore.sh` | 恢复数据库与附件，含自动预备份与行数自检 | 运维验收：可恢复、演练 |
| `harden.sh` | 生产密钥加固 + 上线前安全体检 | 安全验收：JWT/DB 密码 |
| `enable-https.sh` | 一键启用 HTTPS（改 compose、校验语法、自检） | 运维验收：HTTPS |

## 典型上线顺序

```bash
cd deploy

# 1. 配置加固（生成随机 JWT_SECRET / DB_PASSWORD / 管理员初始密码）
./scripts/harden.sh

# 2. 修正上传目录属主（漏了会导致后台上传图片失败）
sudo ./scripts/prepare-storage.sh

# 3. 记下 .env 里的 ADMIN_INIT_PASSWORD，然后起服务
docker compose up -d
docker compose run --rm init

# 4. 验证
curl -s http://localhost/api/health          # 期望 200
docker compose ps                             # 期望 4 个 healthy

# 5. 首次登录后立即改密码（后台 → 顶栏 → 修改密码）

# 6. 配好定时备份（见 docs/04-运维与运营/备份恢复方案.md §3）

# 7. 需要 HTTPS 时
./scripts/enable-https.sh --domain fault.example.com

# 8. 上线后挂每日清理（回收无人引用的上传残留，见下方 §4）
./scripts/cleanup-uploads.sh              # 先预演看一眼
./scripts/cleanup-uploads.sh --apply      # 确认无误再真删
```

## 脚本里藏着的坑（都是实测踩到的）

### 1. `pg_dump | gzip` 的退出码会骗人
管道的退出码取的是 `gzip`。数据库连不上时 `pg_dump` 立刻死掉，`gzip` 却
"成功"压缩 0 字节并返回 0，最后得到一个几十字节的空文件，看起来备份成功。

`backup.sh` 用三重校验拦住它：`pipefail` + 体积下限 1KB + 文件头魔数 `PGDMP`。

**实测**：用不存在的库名执行，脚本返回 `exit 1`，不留 `.tmp` 残留。

### 2. `source .env` 会覆盖调用方传的变量
```bash
DB_NAME=other_db ./backup.sh    # 想备份别的库
```
如果脚本里先取 `DB_NAME` 再 `source .env`，调用方传的值会被文件里的值覆盖。
结果是**备份了错误的库却报告成功**。

修法：`source` 前先把调用方的值存下来，`source` 完再盖回去。

### 3. `pg_restore` 不接受从 stdin 读列表
`pg_restore -l /dev/stdin` 不工作。而且 `docker compose exec -T ... < file`
让宿主机重定向进容器 stdin，在某些组合下拿不到内容**且不报错**。

修法：`docker cp` 进容器，用容器内的本地路径。

### 4. 恢复必须 `DROP SCHEMA` 在前
`schema.sql` 已在 initdb 时建好表，直接 `pg_restore` 全部冲突；而它默认遇错继续、
最后返回 0 —— 看起来成功，其实一条数据都没进去。

修法：先 `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`，再
`pg_restore --exit-on-error`。

### 5. `[[ ... ]] && cmd` 在 `set -e` 下会静默中断
如果这个条件为假，整条语句返回 1。当它正好是脚本最后一条命令时，
脚本会以"失败"退出；在中间时，后面的代码不再执行。

**实测**：`[[ -d "$OLD" ]] && rm -rf "$OLD"` 让脚本在打印"完成"之前就停了。
修法：统一写 `if [[ ... ]]; then ... fi`。

### 6. 改 `DB_PASSWORD` 是个单向操作
Postgres 的 `POSTGRES_PASSWORD` **只在数据目录为空时生效**。已有 `data/pg` 时
改 `.env`：

- 容器会重建，但库里的用户密码还是旧的
- `backend` 用新密码连库 → `password authentication failed` → 永远 unhealthy

`harden.sh` 检测到这种情况会给出可复制的两条命令：

```bash
docker compose exec -T db psql -U fault -d fault_db \
  -c "ALTER USER fault WITH PASSWORD '新密码';"
docker compose up -d --force-recreate backend
```

**实测**：跳过这步，backend 卡在 `health: starting`，日志里是
`FATAL: password authentication failed`；按上面的命令走一遍后恢复 healthy。

### 7. HTTPS 配置会让容器卡在 unhealthy
`nginx.conf` 的 80 端口默认 `return 301 https://...`，而 compose 的 healthcheck
是 `wget http://127.0.0.1/health` —— 拿到 301 就判定失败，整个栈起不来。

修法：80 端口保留一个 `location = /health { return 200 "ok"; }`，
HTTPS 示例配置里已经加上了。

### 8. 宿主机自检 HTTPS 会被代理变量骗
本机 `HTTPS_PROXY` 存在时，`curl --resolve` 仍然走代理，得到 502，
看起来像"HTTPS 配置坏了"。实际是代理连不到那个域名。

修法：自检改在**容器内**做（`docker compose exec nginx wget`）。

### 9. `compose` 里的注释会被 grep 误判
`docker-compose.yml` 本来就有 `# - "443:443"` 这条说明性注释。
用 `grep '"443:443"'` 判断"是否已开放 443"，会把注释当成已启用。

修法：用 `grep -E '^\s*-\s*"443:443"'` 排除注释行。

## 4. `cleanup-uploads.sh`：回收上传残留

### 为什么需要它

上传与删除是两个独立动作，中间任何一步没走完都会留下孤儿文件：

| 场景 | 是否可即时删除 |
|---|---|
| 上传后点"移除" | ✅ 前端会调删除接口（本次已修） |
| 上传后直接关页面 | ❌ 后端不知道这个文件没人要 |
| 编辑时换了另一张图 | ❌ 后端只收到新数组，无从判断是替换还是手滑 |
| 保存时校验失败 | ❌ 整个表单没提交 |
| 删了步骤但不保存 | ❌ 无法区分"撤销"与"真删" |

后四类**只能靠定期扫描兜底**，这也是本脚本存在的原因。

### 引用是怎么判定的

引用藏在 `faults` 表的两个 JSONB 字段里，没有独立附件表：

- `solution_steps[].image_url`
- `attachment_urls[].url`

脚本取全表的这两个字段，把 URL 的 basename 收成集合，再与磁盘文件名比对。
磁盘上有、集合里没有的，就是孤儿。

> 不拼 `LIKE` 查询的原因：文件名是随机 16 进制串，`%` 通配对 JSONB 无法走索引，
> 且 `_` 会被当通配符。当前 `faults` 是千级规模，全表取两列约百毫秒。
> 真到十万级再考虑建 `upload_files` 引用表。

### 三层安全机制

| 机制 | 默认值 | 作用 |
|---|---|---|
| dry-run | 默认开启 | 不加 `--apply` 绝不删文件 |
| 年龄下限 | 60 分钟 | 保护"刚上传还没保存"的图 |
| 比例闸门 | 50%（目录 ≥10 文件时生效） | 待删过半判定为扫描异常，拒绝执行 |

第二层最容易被忽略但最危险：清理任务若恰好在"用户上传完成、正在填表"时运行，
用户点保存就会看到图片 404。

第三层的门槛是 10 个文件：小目录里比例没有统计意义（1 个孤儿 = 100% 会被误拦），
而闸门防的是"扫描失效导致批量误删"，那必然是规模化现象。
—— 这条是实测发现的：第一版无条件按比例判定，单文件残留反而永远清不掉。

### 定时执行

```bash
# crontab -e，每天凌晨 3:30
30 3 * * * cd /opt/fault-deploy/deploy && ./scripts/cleanup-uploads.sh --apply >> /var/log/fault-cleanup.log 2>&1
```

退出码：`0` 正常；`1` 容器未运行；`3` 被比例闸门拒绝（需人工核查）。
